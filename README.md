# Poker Defense

포커 족보로 유닛을 소환해 웨이브를 막는 세로형 모바일 디펜스 게임입니다. 혼자 기획하고 개발한 개인 프로젝트입니다.

- 클라이언트: Unity 6000.4.0f1 · URP 2D · Input System · C#
- 랭킹 서버: C++ (`Server/`)

## 게임 규칙

1. 카드 5장을 받습니다. 자리마다 한 번씩 교체할 수 있습니다.
2. 족보를 확정하면 그 족보의 유닛이 1기 소환됩니다. 높은 족보일수록 강합니다.
3. 15칸 보드에 배치합니다. 같은 유닛끼리 합치면 한 단계 강해집니다(최대 ★3).
4. 적은 보드 바깥 트랙을 돕니다. 다 처치하지 못하면 라이프가 줄어듭니다.

50웨이브까지 진행하며, 10웨이브마다 보스가, 50웨이브에는 최종 보스가 나옵니다.

교체할 카드를 고르면 바꿨을 때 나올 수 있는 족보와 확률을 바로 보여줍니다.

## 구조

```
PokerDefense.Poker   카드, 덱, 족보 판정, 확률 계산 (Unity 없이 동작하는 순수 C#)
        ↑
PokerDefense.Game    라운드 진행, 보드, 전투, 스테이지
        ↑
PokerDefense.UI      화면, 입력, 사운드
```

아래층은 위층을 참조하지 않습니다. 게임 규칙은 MonoBehaviour가 아닌 일반 C# 클래스에 두고, 컴포넌트는 화면과 입력 연결만 맡습니다. 그래서 전투 한 판을 씬 없이 테스트 코드에서 돌릴 수 있습니다.

`Server/`는 게임 결과를 받아 순위를 돌려주는 C++ TCP 서버입니다. 서버가 꺼져 있어도 게임은 그대로 동작합니다.

## 확률 계산 스레드 분리

4장을 교체하는 경우 남은 47장에서 4장을 뽑는 178,365가지 조합을 전부 판정해야 합니다. 메인 스레드에서 돌리면 그동안 화면이 멈춥니다.

- 계산은 워커 스레드에서 돌리고, 메인 스레드는 매 프레임 완료 여부만 확인해 결과를 화면에 반영합니다(Unity API는 메인 스레드에서만 쓸 수 있습니다).
- 워커에는 손패와 덱의 복사본만 넘깁니다. 계산 중에 게임 데이터가 바뀌어도 영향을 받지 않습니다.
- 선택이 바뀌면 이전 계산을 취소하고, 늦게 끝난 결과가 현재 요청과 다르면 버립니다.
- 3장 이상 교체할 때는 첫 카드 기준으로 조합을 나눠 스레드 2개에서 계산합니다. 4개가 더 빨랐지만 게임의 다른 작업과 CPU를 나눠 써야 해서 2개로 제한했습니다.

3장 교체 기준 119ms에서 16ms로 줄었습니다(Windows 에디터, 워밍업 2회 후 9회 측정한 중앙값). 줄어든 시간의 대부분은 족보 종류만 판정하는 함수를 따로 만든 효과이고, 스레드를 2개로 나눈 효과만 보면 약 1.17배입니다. 첫 카드에 따라 묶음 크기가 크게 달라서 두 스레드에 일이 고르게 나뉘지 않습니다.

## 랭킹 서버

게임이 끝나면 결과를 서버로 보내고 순위를 받습니다. 모바일에서는 연결이 끊기거나 앱이 종료되는 일이 잦고, 응답을 못 받아 다시 보내면 기록이 중복될 수 있습니다.

- 결과를 먼저 파일에 저장하고, 서버 응답을 받은 뒤 지웁니다. 전송 중 종료되면 다음 실행 때 다시 보냅니다.
- 결과마다 고유 ID를 붙여, 같은 기록이 다시 와도 서버에는 한 번만 저장됩니다.
- 메시지는 [본문 길이][본문] 형식의 프레임으로 주고받습니다. 본문은 최대 256바이트이고, 길이 필드만 보고 먼저 거부해 거대한 길이로 메모리를 잡아 두는 입력을 막습니다.
- 서버는 스레드 하나에서 `select`로 여러 연결을 처리합니다. 나눠서 도착한 데이터를 이어 붙이고, 규칙상 나올 수 없는 값은 거부합니다. 기록을 파일에 쓴 뒤에 응답합니다.
- 10초 동안 아무것도 보내지 않는 연결과 동시 연결 63개를 넘는 연결은 끊습니다.
- 클라이언트 전송은 별도 스레드에서 하고, 결과 표시는 메인 스레드에서 합니다.

C++ 테스트 17개와 C# 테스트 21개로 조각난 데이터, 연결 끊김, 시간 초과, 중복 전송을 재현해 확인했습니다. 양쪽 테스트가 같은 고정 바이트열을 검사해 C#과 C++이 같은 바이트를 만드는지도 확인합니다.

## 프로파일링

Unity Profiler로 플레이 중 프레임을 확인해 보니, 사운드 관리 코드가 매 프레임 설정값을 반복해서 다시 읽으며 36회에 걸쳐 2.6KB를 할당하고 있었습니다. 프레임당 한 번만 읽도록 고쳐 할당은 4회 288B로, 실행 시간은 0.98ms에서 0.16ms로 줄였습니다.

## 테스트

기획을 자주 바꾸면서 규칙이 깨지는 걸 바로 알 수 있도록 EditMode 테스트를 작성했습니다.

- 족보 판정, 확률 계산, 라운드 규칙, 보드 · 전투 · 스테이지
- 스레드가 얽힌 코드는 계산 함수를 멈추거나 실패하는 함수로 바꿔 끼우고, 신호로 타이밍을 조절해 연타 · 취소 · 오류 상황을 매번 같은 순서로 재현합니다.
- 병렬 계산 결과가 순차 계산 결과와 같은지 비교합니다.

## 실행 방법

1. Unity 6000.4.0f1로 프로젝트를 엽니다.
2. `Assets/_Project/Scenes/Boot` 씬을 열고 Play를 누릅니다.
3. 테스트는 `Window > General > Test Runner`의 EditMode 탭에서 Run All을 누릅니다.
4. 랭킹 서버(선택): `Server\RankServer.sln`을 Visual Studio로 열고 F5를 누릅니다. 자세한 방법은 [Server/README.md](Server/README.md)에 있습니다.

## 한계

- 50웨이브 전체를 직접 끝까지 플레이해 난이도를 검증하지는 않았습니다.
- 성능 수치는 Windows 에디터에서 잰 값입니다. 모바일 실기기에서는 아직 측정하지 않았습니다.
- 진행 저장과 이어하기는 없습니다.
- 서버는 받은 값이 규칙 범위 안인지만 검사합니다. 전투를 다시 돌려 점수를 검증하지는 않습니다.
