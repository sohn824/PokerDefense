# Poker Defense

포커 족보로 유닛을 불러 적을 막는 모바일 세로형 디펜스 게임이다. 혼자 기획하고 개발한 개인 프로젝트다.

## 어떤 게임인가

한 라운드는 이렇게 흘러간다.

1. **카드 5장을 받는다.** 마음에 들지 않는 카드는 자리마다 한 번씩 바꿀 수 있다.
2. **족보를 확정한다.** 원페어면 원페어 유닛, 스트레이트면 스트레이트 유닛이 1기 나온다. 족보가 높을수록 강하다.
3. **보드에 배치한다.** 15칸 보드에 유닛을 놓고, 같은 유닛끼리 합치면 한 단계 강해진다(최대 ★3).
4. **웨이브를 막는다.** 적은 보드를 둘러싼 트랙을 빙글빙글 돈다. 다 처치하지 못하면 라이프가 깎인다.

이 과정을 50웨이브까지 반복한다. 10웨이브마다 보스가 나오고, 마지막 50웨이브에는 최종 보스가 나온다.

카드를 고르면 **그 카드를 바꿨을 때 어떤 족보가 몇 % 확률로 나오는지** 바로 보여준다. 운에만 맡기지 않고 확률을 보고 판단할 수 있게 하려는 장치다.

**개발 환경:** Unity 6000.4.0f1 · URP 2D · Input System · C#

## 코드 구조

코드는 세 층으로 나뉘고, 아래층은 위층을 모른다.

```
PokerDefense.Poker   카드, 덱, 족보 판정, 확률 계산 — Unity 없이 동작하는 순수 C#
        ↑
PokerDefense.Game    라운드 진행, 보드, 전투, 스테이지
        ↑
PokerDefense.UI      화면, 입력, 사운드
```

`Server/`에는 게임 결과를 받아 순위를 돌려주는 C++ TCP 서버가 따로 있다. 게임 진행에는 필요 없고, 서버가 꺼져 있어도 게임은 그대로 돌아간다.

게임 규칙은 Unity 컴포넌트(MonoBehaviour)가 아닌 일반 C# 클래스에 넣었다. Unity 컴포넌트는 규칙 클래스를 화면과 입력에 연결하는 역할만 맡는다. 이렇게 나눠둔 덕분에 전투 한 판도 씬을 띄우지 않고 코드만으로 돌려볼 수 있다.

## 기술적으로 고민한 부분

### 1. 확률 계산이 화면을 멈추지 않게 하기

**문제.** 카드 4장을 바꾸는 경우를 계산하려면 남은 덱 47장에서 4장을 뽑는 조합 178,365가지를 전부 판정해야 한다. 이걸 메인 스레드에서 돌리면 계산하는 동안 화면이 멈춘다.

**해결.**
- 계산을 별도 스레드로 옮겼다. 결과는 매 프레임 끝났는지 확인해서 메인 스레드에서만 화면에 반영한다(Unity API는 메인 스레드에서만 쓸 수 있다).
- 계산 스레드에는 손패와 덱을 복사한 값만 넘긴다. 계산 도중에 게임 쪽 데이터가 바뀌어도 서로 영향을 주지 않는다.
- 플레이어가 선택을 바꾸면 이전 계산에 멈추라는 신호를 보낸다. 늦게 끝난 결과는 지금 요청과 다르면 버린다.
- 3장 이상일 때는 조합을 첫 카드 기준으로 묶어 2개 스레드로 나눠 계산한다.

**결과.** 3장 기준 약 119ms에서 16ms로 줄었다. 다만 이 중 대부분은 계산 방식 개선(족보 종류만 빠르게 판정하는 함수를 따로 만듦) 덕분이고, 스레드를 2개로 늘린 효과만 따로 보면 약 1.17배다. 첫 카드에 따라 묶음 크기가 크게 달라서 두 스레드에 일이 고르게 나뉘지 않기 때문이다.

자세한 내용: [설계](Docs/THREADING_PLAN.md) · [측정 결과](Docs/THREADING_RESULTS.md)

### 2. 게임 결과를 서버로 보내 랭킹 매기기

**문제.** 게임이 끝날 때 결과를 서버로 보내고 싶은데, 모바일에서는 연결이 끊기거나 앱이 꺼지는 일이 흔하다. 응답을 못 받았다고 다시 보내면 기록이 두 번 들어갈 수도 있다.

**해결.**
- 결과를 **먼저 파일로 저장**하고, 서버가 받았다고 답해야 지운다. 전송 중에 꺼져도 다음 실행 때 다시 보낸다.
- 결과마다 고유 ID를 붙여, 같은 기록이 다시 와도 서버가 한 번만 저장하게 했다.
- 서버는 C++로 직접 만들었다. 스레드 하나에서 `select`로 여러 연결을 처리하고, 쪼개져 도착하는 데이터를 이어 붙이고, 비정상적인 길이나 규칙상 나올 수 없는 값을 거른다. 기록을 파일에 쓴 **뒤에** 응답한다.
- 전송은 별도 스레드에서 돌고, 결과는 메인 스레드에서만 화면에 반영한다.

**검증.** C++ 테스트 17개와 C# 테스트 21개로 조각난 데이터, 연결 끊김, 시간 초과, 중복 전송을 재현해 확인했다. C#과 C++이 같은 바이트를 만드는지는 양쪽 테스트가 같은 고정 바이트열을 검사해서 확인한다.

자세한 내용: [설계와 프로토콜](Docs/NETWORK.md) · [서버 빌드](Server/README.md)

### 3. 프로파일러로 불필요한 메모리 할당 찾기

Unity Profiler로 실제 플레이를 측정해 보니, 사운드를 관리하는 코드가 매 프레임 설정값을 수십 번 다시 읽으면서 메모리를 2.6KB씩 할당하고 있었다. 설정값을 프레임마다 한 번만 읽도록 고쳐 288B로 줄였다.

자세한 내용: [프로파일링 기록](Docs/PROFILING_RESULTS.md)

### 4. 자동 테스트로 규칙 지키기

혼자 개발하면서 기획을 자주 바꿨기 때문에, 바꿀 때마다 무엇이 깨졌는지 바로 알 수 있도록 규칙을 테스트로 고정했다.

- 족보 판정, 확률 계산, 라운드 규칙, 보드·전투·스테이지를 Unity의 EditMode 테스트로 검증한다.
- 여러 스레드가 얽힌 코드는 실행할 때마다 타이밍이 달라 테스트하기 어렵다. 그래서 테스트에서는 계산 함수를 일부러 멈추거나 실패하는 함수로 바꿔 끼우고, 신호를 보내 타이밍을 직접 조절한다. 그러면 연타, 취소, 오류 같은 상황을 매번 똑같이 재현할 수 있다.
- 병렬 계산 결과는 순차 계산 결과와 하나도 빠짐없이 같은지 비교한다.

## 실행 방법

1. Unity 6000.4.0f1로 프로젝트를 연다.
2. `Assets/_Project/Scenes/Boot` 씬을 열고 Play를 누른다.
3. 테스트는 `Window > General > Test Runner`에서 **EditMode** 탭을 고르고 **Run All**을 누른다.
4. 랭킹 서버(선택): `Server\RankServer.sln`을 Visual Studio로 열고 F5를 누르면 서버가 뜬다. 자세한 방법은 [Server/README.md](Server/README.md).

## 아직 부족한 점

- 50웨이브 전체를 사람이 끝까지 플레이하며 난이도를 검증하지는 못했다.
- 성능 수치는 Windows 에디터에서 잰 값이다. 모바일 실기기에서는 아직 측정하지 않았다.
- 게임 진행 저장과 이어하기는 아직 없다.
- 랭킹 서버는 받은 값이 규칙상 가능한지만 검사한다. 전투를 다시 돌려 점수가 정당한지 증명하지는 못하는 데모 수준이다.
