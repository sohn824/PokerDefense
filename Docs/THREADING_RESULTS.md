# 교체 확률 멀티스레드 구현·검증 (2026-09-20)

구조는 [THREADING_PLAN.md](THREADING_PLAN.md), 현행 게임 규칙은 [DESIGN.md](DESIGN.md) §19~20을 따른다. TCP는 아직 구현하지 않았다.

## 적용한 동작

- 일반/선택 교체 UI는 같은 RoundController/HandOddsWorker를 사용한다. 메인에서 불변 스냅샷을 만들고 Task.Run으로 넘긴다.
- 활성 작업 1개와 최신 대기 요청 1개만 유지한다. 선택·손패·단계 변경에서 취소하고, 완료가 늦어도 현재 요청 인스턴스가 아니면 버린다.
- 완료된 Task만 Update에서 읽고 이벤트로 UI를 갱신한다. 계산 중에도 선택·교체·확정은 가능하다. 워커는 Unity API를 호출하지 않는다.
- 1~2장은 워커 순차, 3~4장은 최대 병렬도 2. 병렬 임계값 3과 교체 상한 4를 분리한다. 분할별 손패/조합/카운터를 소유하고 완료 후 합산한다. 비활성화는 Cancel, 파괴는 Dispose이며 종료를 메인에서 기다리지 않는다.
- 계산 반복에서 승리 카드 배열이 불필요하므로 CategoryOf를 추가했다. 실제 족보 확정은 기존 Evaluate를 유지한다. 기본 표시 상한은 **4장** — 2026-09-21 재측정 후 3→4로 올렸다. 아래 "상한 4장 확장" 절 참조.

## 측정 방법과 결과

[원시 CSV](Benchmarks/2026-09-20-hand-odds.csv)는 **Unity 6000.4.0f1 Windows Editor / Mono / Ryzen 9 7950X3D (논리 CPU 32)**에서 테스트·Play·빌드와 겹치지 않게 실행한 최종 비교다. seed 17/42의 5장 손패, 남은 47장, 앞쪽 k개 자리를 사용한다. 각 경우/모드마다 워밍업 2회 후 9회 측정, 중앙값과 nearest-rank p95(이 표본에서는 최댓값)를 기록했다. 작고 제한된 표본이며 성능 보장이 아니다.

| 3장 / 중앙값 | seed 17 | seed 42 |
|---|---:|---:|
| 기존 Evaluate 기반 순차 기준 | 119.420ms | 112.778ms |
| 종류 전용 판정 + 순차 | 17.914ms | 18.693ms |
| 종류 전용 판정 + 워커 순차(dispatch 포함) | 18.954ms | 19.048ms |
| 종류 전용 판정 + 워커 병렬 2(dispatch 포함) | 16.010ms | 16.266ms |
| 종류 전용 판정 + 워커 병렬 4(dispatch 포함) | 11.038ms | 11.179ms |

주된 감소는 **종류만 판정하는 계산 경로**의 효과다. 같은 평가기로 워커 순차와 병렬 2를 비교한 추가 속도 개선은 약 1.17~1.18배다. 119→16ms 전체를 병렬화만의 성과로 쓰지 않는다. 초기 기존 Evaluate의 병렬 실험에서는 더 느린 구간도 관찰됐다. 최종 메뉴는 기존 Evaluate 기준 경로를 보존해 동일 입력으로 재측정할 수 있다.

4장(벤치마크에서만 명시적으로 maxSlots=4)은 병렬 2에서도 약 186~187ms였다. 모바일에서 검증하지 않았고 화면 정보량도 증가하므로 **4장 UI 노출을 보류**했다. 병렬 4가 이 PC에서 더 빨랐지만 다른 게임 작업과의 CPU 경합을 고려해 기본값은 2로 제한했다. 이 선택은 모바일 최적값을 확정한 것이 아니다.

`inline-sequential`은 벤치마크 작업 스레드 안에서 dispatch 없이 측정한 계산 시간이다. 게임 메인 프레임 시간과 같지 않다. 다른 모드는 내부 Task.Run의 대기/dispatch까지 포함한다. 여기의 대기는 Editor 측정 코드에만 있고 런타임 UI에는 없다. 스냅샷 생성·프레임 폴링·TMP 표시 비용은 이 표에 포함하지 않는다.

GC.GetAllocatedBytesForCurrentThread가 이 Editor 런타임에서 0을 반환해 할당량은 **NA**로 기록했다. 무할당 게임 전체 또는 GC 영향 0을 뜻하지 않는다. 실제 Player/모바일의 요청→표시 지연, 프레임 p95, GC/할당, 발열은 미측정이다.

### 다시 측정하기

1. Unity에서 Play를 멈추고 컴파일/테스트/빌드가 끝난 상태로 둔다.
2. `DevMode > 교체 확률 벤치마크`를 실행한다.
3. `Artifacts/Threading/category-comparison.csv`에 단계별 결과가 쌓인다. `HandOddsBenchmark.Pending`이 완료됐는지 확인한다. 실행 중 씬 전환/스크립트 수정/테스트를 시작하지 않는다.
4. Unity/CPU/백엔드와 표본 수를 함께 보존하고, 새 결과를 문서의 기존 결과와 구분한다. Artifacts는 로컬 출력이고 위 Docs CSV만 이번 최종 측정 기록이다.

## 빌드 검증

## 남은 확인

- 기존 Light SDF의 NativeFormatImporter 일관성 오류가 Play 검증 중 다시 관찰됐다. 신규 C# 컴파일 오류나 워커 예외와 구분한다.
- 후속 UI 보완(2026-09-20): 기본 화면은 높은/같은 족보 확률의 두 줄 요약으로 제한하고 분포·경우의 수는 스크롤 상세 창으로 분리했다. 750×1334 GameView에서 3장 교체 요약 2줄, TMP overflow=false 확인. 작은 양수는 `<0.1%`로 표시한다. EditMode 테스트 225/225 통과.
- 실제 모바일/Player 성능·프레임 QA, 긴 확률 문구 UX, TCP 결과 제출/랭킹은 후속 작업이다. Stand-Alone 게임과 저장 규칙은 바꾸지 않았다.

## 상한 4장 확장 (2026-09-21)

THREADING_PLAN §"상한과 측정"의 순서(상한 3 유지 → 비동기/병렬 구현 검증 → 측정 후 4장 UI 노출 결정)에 따라, 위 측정을 4장까지 재실행한 뒤 `HandOdds.MaxSlots`를 3에서 **4**로 올렸다. `HandOddsWorker.ParallelSlotThreshold`가 `HandOdds.MaxSlots`를 그대로 참조하므로 병렬 임계값도 함께 4로 올라갔다 — **3장 선택은 이제 워커 순차, 4장 선택만 병렬도 2**를 탄다(이전에는 3장이 병렬이었다). 둘 다 비동기라 프레임에는 영향이 없고, 계산 자체도 5~20ms대라 체감 차이는 없다.

[원시 CSV](Benchmarks/2026-09-21-hand-odds-4slots.csv)는 같은 환경(Unity 6000.4.0f1 / Windows Editor / Ryzen 9 7950X3D, 논리 CPU 32)에서 seed 17·42, k=1~4를 다시 측정한 값이다. samples=9(중앙값), warmup=2.

| 중앙값 (seed 17·42 평균) | 1장 | 2장 | 3장 | 4장 |
|---|---:|---:|---:|---:|
| 기존 Evaluate 기반 순차 (reference) | 0.29ms | 6.1ms | 105ms | 1195ms |
| CategoryOf 순차 (워커, dispatch 포함) | 0.06ms | 1.2ms | 18.0ms | 200ms |
| CategoryOf 병렬 2 (dispatch 포함) | 0.08ms | 0.8ms | 13.9ms | 168ms |

4장(신규 상한)의 워커 순차 대비 병렬 2 개선은 **약 16%**(200ms → 168ms) — 2026-09-20 측정한 3장의 약 17~18% 개선과 비슷한 폭이다. 4장이 3장보다 조합 수는 약 11배(C(47,3)=16,215 → C(47,4)=178,365) 크지만, 계산은 여전히 워커 스레드에서 비동기로 돈다는 점은 3장 때와 같다. 이 수치는 2026-09-20 기록과 같은 한계를 그대로 공유한다 — Editor 전용, 작은 표본, Player/모바일 미검증, 할당량 NA.

이번에 UI 노출을 결정한 근거는 계산 시간이 아니라 **비동기 구조 자체가 슬롯 수와 무관하게 메인 스레드를 막지 않는다는 점**이다. 다만 THREADING_PLAN이 제기했던 다른 두 우려 — 모바일 실기기 미검증, 4장 확률 표시 시 화면 정보량 증가(자세히 창의 행 수·스크롤) — 는 이번 측정으로 해소되지 않았다. POLISH PERF-01에 남긴다.

**아직 반영하지 않은 것**: 포트폴리오 문서(덱 17장, 경력기술서, QnA)는 여전히 "3자리 상한"으로 서술돼 있다. THREADING_PLAN §"상한과 측정"이 명시한 대로 채택 시 함께 갱신해야 하지만, 이번 작업 범위에는 포함하지 않았다.


## 병렬 적용 기준 조정 (2026-09-21 후속)

상한 확장 당시 정책을 변경해 현재는 1~2장 워커 순차, 3~4장 최대 병렬도 2다. 단일 논리 CPU는 순차 처리한다. ParallelSlotThreshold=3과 MaxSlots=4를 분리했다. 기존 CSV는 실행 모드별 측정값이므로 그대로 유지하며 새 성능 측정은 수행하지 않았다.
