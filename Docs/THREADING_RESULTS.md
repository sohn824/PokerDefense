# 교체 확률 멀티스레드 구현·검증

구조와 설계 이유는 [THREADING_PLAN.md](THREADING_PLAN.md), 현재 게임 규칙은 [DESIGN.md](DESIGN.md) §19~20을 따른다. TCP는 아직 구현하지 않았다.

이 문서는 2026-09-20 구현과 2026-09-21 조정 기록을 함께 담는다. **현재 동작은 바로 아래 "현재 동작"이 기준**이고, 그 아래 날짜별 절은 당시 상태를 기록한 것이다.

## 현재 동작 (2026-09-21 이후)

- **교체 상한은 4장, 병렬 기준은 3장이다.** 1~2장은 워커 스레드에서 순차로, 3~4장은 최대 2스레드 병렬로 계산한다. 논리 CPU가 하나면 순차로 돈다. 병렬 기준(`ParallelSlotThreshold` = 3)과 교체 상한(`MaxSlots` = 4)은 서로 독립된 값이다.
- **일반 교체와 선택 교체가 같은 경로를 쓴다.** 둘 다 같은 RoundController와 HandOddsWorker를 쓴다. 메인 스레드에서 복사본 요청을 만들어 `Task.Run`으로 넘긴다.
- **작업은 최대 둘만 유지한다.** 실행 중인 작업 하나와 가장 최근 대기 요청 하나다. 선택·손패·단계가 바뀌면 취소하고, 늦게 끝난 결과는 현재 요청 인스턴스와 다르면 버린다.
- **화면 반영은 메인 스레드에서만 한다.** 끝난 작업은 `Update`에서만 읽고 이벤트로 UI를 갱신한다. 계산 중에도 선택·교체·확정을 할 수 있다. 워커는 Unity API를 부르지 않는다.
- **공유 상태 없이 병렬 계산한다.** 묶음마다 손패·조합·집계를 따로 갖고, 모두 끝난 뒤 합산한다.
- **종료를 기다리지 않는다.** 비활성화되면 `Cancel`, 파괴되면 `Dispose`하며, 어느 쪽도 메인 스레드에서 작업 종료를 기다리지 않는다.
- **판정 함수를 둘로 나눴다.** 확률 계산에는 승리 카드 배열이 필요 없어서 족보 종류만 판정하는 `CategoryOf`를 추가했다. 실제 손패 확정은 기존 `Evaluate`를 그대로 쓴다.
- **화면 표시.** 기본 화면에는 높은 족보·같은 족보 확률을 두 줄로 요약하고, 전체 분포와 경우의 수는 스크롤 가능한 상세 창에서 보여준다. 0보다 크지만 0.1% 미만인 확률은 `<0.1%`로 표시한다.
- **최신 검증:** EditMode 225/225.

## 측정 방법과 결과 (2026-09-20, 3장)

[원시 CSV](Benchmarks/2026-09-20-hand-odds.csv)

**환경:** Unity 6000.4.0f1, Windows Editor, Mono, Ryzen 9 7950X3D(논리 CPU 32). 테스트·Play·빌드와 겹치지 않을 때 실행했다.
**입력:** seed 17과 42로 만든 5장 손패, 남은 47장, 앞쪽 k개 자리.
**방법:** 경우와 모드마다 워밍업 2회 후 9회 측정하고, 중앙값과 p95(nearest-rank, 이 표본에서는 최댓값)를 기록했다. 표본이 작고 조건이 제한적이므로 성능을 보장하는 수치는 아니다.

| 3장 / 중앙값 | seed 17 | seed 42 |
|---|---:|---:|
| 기존 Evaluate로 순차 (기준) | 119.420ms | 112.778ms |
| 종류 전용 판정 + 순차 | 17.914ms | 18.693ms |
| 종류 전용 판정 + 워커 순차 (dispatch 포함) | 18.954ms | 19.048ms |
| 종류 전용 판정 + 워커 병렬 2 (dispatch 포함) | 16.010ms | 16.266ms |
| 종류 전용 판정 + 워커 병렬 4 (dispatch 포함) | 11.038ms | 11.179ms |

**어디서 빨라졌나.** 줄어든 시간의 대부분은 **족보 종류만 판정하는 계산 경로** 덕분이다. 같은 판정 함수로 워커 순차와 병렬 2만 비교하면 추가 개선은 약 1.17~1.18배다. 그러므로 119ms → 16ms 전체를 병렬화 성과로 쓰지 않는다. 처음에 기존 `Evaluate`로 병렬화를 시험했을 때는 오히려 더 느린 구간도 있었다. 벤치마크 메뉴는 기존 `Evaluate` 경로를 남겨 두어 같은 입력으로 다시 비교할 수 있다.

**4장(당시 판단).** 벤치마크에서만 `maxSlots=4`를 지정해 재 보니 병렬 2에서도 약 186~187ms였다. 모바일에서 검증하지 않았고 화면에 보여줄 정보도 늘어나므로 **이때는 4장 노출을 보류했다**(다음 날 결정은 아래 "상한 4장 확장"). 이 PC에서는 병렬 4가 더 빨랐지만, 게임의 다른 작업과 CPU를 나눠 써야 하므로 기본값은 2로 제한했다. 모바일에 맞는 값을 확정한 것은 아니다.

**수치를 읽을 때 주의할 점.**
- `inline-sequential`은 벤치마크 스레드 안에서 dispatch 없이 잰 순수 계산 시간이며, 게임 메인 프레임 시간과 다르다. 나머지 모드는 내부 `Task.Run`의 대기와 dispatch까지 포함한다. 이 대기는 에디터 측정 코드에만 있고 실제 게임 UI에는 없다.
- 복사본 요청 생성, 프레임 폴링, TMP 표시 비용은 이 표에 들어 있지 않다.
- `GC.GetAllocatedBytesForCurrentThread`가 이 에디터 런타임에서 0을 돌려줘서 할당량은 **NA**로 기록했다. 할당이 없다거나 GC 영향이 0이라는 뜻이 아니다.
- 실제 Player·모바일의 요청→표시 지연, 프레임 p95, GC·할당, 발열은 측정하지 않았다.

### 다시 측정하기

1. Unity에서 Play를 멈추고, 컴파일·테스트·빌드가 끝난 상태로 둔다.
2. `DevMode > 교체 확률 벤치마크`를 실행한다.
3. 결과는 `Artifacts/Threading/category-comparison.csv`에 쌓인다. `HandOddsBenchmark.Pending`이 끝났는지 확인하고, 도는 동안에는 씬 전환·스크립트 수정·테스트 실행을 하지 않는다.
4. Unity 버전, CPU, 백엔드, 표본 수를 함께 남기고, 새 결과는 기존 기록과 구분해 적는다. Artifacts는 로컬 출력이고, 최종 측정 기록은 위 Docs의 CSV다.

## 정합성·수명 검증 (2026-09-20)

당시 EditMode **219/219 통과**(job `9da3bfaae0b9491d8adc4fce17c1d458`). 이후 표시 검증 6개가 추가돼 지금은 225개다.

- 기존 207개를 유지하고 새 테스트 12개를 더했다. 종류 전용 판정과 기존 판정을 족보 13종 예제와 시드 10,000개로 비교했다.
- 순차와 병렬 1·2·4의 집계·정렬·nCk 합이 여러 손패와 자리 수에서 모두 일치했다. 입력 복사와 당시 기본 상한(3장)도 확인했다.
- 시작 전과 실행 도중의 취소, 취소를 무시하고 끝난 이전 작업의 결과 폐기, 20회 연속 요청에서 처음과 마지막 요청만 실행되는지 확인했다.
- 예외를 거둔 뒤 새 요청이 정상 처리되는지, 종료 시 대기 요청이 지워지는지, 새 손패와 비활성화·재활성화 때 결과가 무효화되는지 확인했다.
- 처음 만든 컨트롤러 수명 테스트는 타임아웃으로 실패했다. EditMode에서는 일반 MonoBehaviour의 `OnEnable`이 자동으로 불리지 않기 때문이다. 테스트에서 수명 콜백을 직접 호출하도록 고쳤고, 실제 콜백 경로는 아래 Play 검증에서 따로 확인했다.

에디터 Play의 실제 Game 씬에서 확인한 것:

- 3장을 고르면 바로 계산 중 표시가 나오고, 끝난 뒤 문자열이 순차 계산 결과와 같다.
- 3장에서 1장으로 빠르게 바꾸면 이전 결과가 바로 사라지고 최신 선택의 결과만 나온다.
- 일반 교체에서 선택 교체 창으로 넘어가면 일반 패널이 숨고, 선택 교체 확률이 맞게 나온다.
- 후보를 공개하면 이전 확률이 사라지고, 후보를 고른 뒤 정상으로 돌아온다.
- 계산 중에 손패를 확정하면 Place 단계로 넘어가고, 작업은 Idle, 확률 패널은 숨는다.
- 계산 중에 타이틀로 나가면 RoundController가 0개가 되고, 새 워커나 UI 예외가 없다.

## 상한 4장 확장 (2026-09-21)

THREADING_PLAN "상한과 측정"에서 정한 순서(상한 3 유지 → 구현 검증 → 측정 후 4장 노출 결정)대로, 4장까지 다시 측정한 뒤 `HandOdds.MaxSlots`를 3에서 **4**로 올렸다.

> 당시에는 병렬 기준이 `MaxSlots`를 그대로 따라가서 "3장은 워커 순차, 4장만 병렬"이 됐다. 같은 날 바로 아래 "병렬 기준 조정"에서 기준을 3으로 분리해 3~4장 병렬로 되돌렸다.

[원시 CSV](Benchmarks/2026-09-21-hand-odds-4slots.csv) — 같은 환경(Unity 6000.4.0f1, Windows Editor, Ryzen 9 7950X3D, 논리 CPU 32)에서 seed 17·42, k=1~4를 다시 쟀다. 9회 측정 중앙값, 워밍업 2회.

| 중앙값 (seed 17·42 평균) | 1장 | 2장 | 3장 | 4장 |
|---|---:|---:|---:|---:|
| 기존 Evaluate로 순차 (기준) | 0.29ms | 6.1ms | 105ms | 1195ms |
| CategoryOf 순차 (워커, dispatch 포함) | 0.06ms | 1.2ms | 18.0ms | 200ms |
| CategoryOf 병렬 2 (dispatch 포함) | 0.08ms | 0.8ms | 13.9ms | 168ms |

4장에서 워커 순차 대비 병렬 2의 개선은 **약 16%**(200ms → 168ms)로, 전날 3장에서 잰 약 17~18%와 비슷하다. 4장은 3장보다 조합이 약 11배 많지만(C(47,3)=16,215 → C(47,4)=178,365), 계산이 워커 스레드에서 비동기로 돈다는 점은 같다. 이 수치도 전날 기록과 같은 한계가 있다. 에디터 전용이고, 표본이 작고, Player·모바일에서는 재지 않았고, 할당량은 NA다.

**4장을 열기로 한 근거**는 계산 시간이 아니라, 비동기 구조라서 자리 수와 상관없이 메인 스레드를 막지 않는다는 점이다. 다만 THREADING_PLAN에서 걱정했던 두 가지, 즉 모바일 실기기 미검증과 4장일 때 늘어나는 화면 정보량(상세 창의 행 수와 스크롤)은 이 측정으로 해결되지 않았다. 둘 다 POLISH PERF-01에 남겼다.

포트폴리오 문서(덱, 경력기술서, QnA)의 상한 설명은 이 작업에 포함하지 않았고, 이후 별도로 고쳤다.

## 병렬 기준 조정 (2026-09-21 후속)

병렬 기준(`ParallelSlotThreshold` = 3)을 교체 상한(`MaxSlots` = 4)과 분리했다. 그래서 지금은 1~2장 워커 순차, 3~4장 최대 2스레드 병렬이며, 논리 CPU가 하나면 순차다. 기존 CSV는 실행 모드별 측정값이므로 그대로 두었고, 새로 측정하지는 않았다.

## 남은 확인

- 기존 폰트(Light SDF)의 NativeFormatImporter 일관성 오류가 Play 검증 중 다시 보였다. 새 C# 컴파일 오류나 워커 예외와는 별개의 문제다.
- 확률 요약 UI(2026-09-20 보완): 750×1334 GameView에서 3장 교체 요약이 2줄로 나오고 TMP overflow가 없음을 확인했다. 당시 EditMode 225/225.
- 실제 모바일·Player에서의 성능과 프레임 QA, 긴 확률 문구 UX, TCP 결과 제출과 랭킹은 이후 작업이다. 오프라인 게임 구조와 저장 규칙은 바꾸지 않았다.
