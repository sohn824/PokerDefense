# 게임 결과 제출과 랭킹 (2026-09-27)

게임이 끝나면 결과를 C++ TCP 서버로 보내고, 서버가 돌려준 순위를 결과 화면에 한 줄로 보여준다. 설계의 출발점은 [THREADING_PLAN.md](THREADING_PLAN.md)의 "다음 단계: TCP 결과 제출"이다.

**이 기능은 클라이언트가 보낸 기록을 믿는 데모 랭킹이다.** 서버는 형식과 값의 범위를 검사하지만, 전투를 다시 돌려 점수가 정당한지 증명하지는 못한다(아래 "한계").

## 전체 흐름

```
게임 종료 ─→ RunResult 생성 ─→ outbox 파일 저장 ─→ 백그라운드 전송 ─→ C++ 서버
                                     ↑                     │           검증 → 파일 저장 → ACK
                                     └─ ACK 받으면 삭제 ←──┘
결과 화면 ←─ Update에서 전송 결과 확인 (메인 스레드)
```

1. `GameFlowController`가 게임 종료(`IsFinished`)를 알리면 `RunReporter`가 `RunResult`를 만든다. 새 `runId`(Guid)를 붙인다.
2. **먼저 파일로 저장한다**(`RunOutbox`). 전송 도중에 게임이 꺼져도 기록이 남고 다음 실행 때 다시 보낸다.
3. `Task.Run`에서 outbox에 남은 기록을 오래된 순으로 보낸다(`RunSubmitter`). 서버가 받았다고 답하면(Accepted·Duplicate) 파일을 지운다. 거부하면 `.rejected`로 옮겨 다시 보내지 않는다. 연결이 안 되면 거기서 멈추고 다음 기회(다음 실행, 다음 게임 종료)에 다시 보낸다.
4. 전송 결과는 `Update`에서 확인하고, 메인 스레드에서만 상태를 바꾸고 이벤트를 보낸다. 확률 계산 워커와 같은 방식이다.
5. 결과 화면(`ResultScreen`)이 상태를 한 줄로 보여준다: `기록 전송 중...` / `기록 12개 중 3위` / `서버 연결 실패 · 다음 실행 때 다시 전송` / `서버가 기록을 받지 않음`.

전송이 실패해도 게임 결과는 바뀌지 않는다. 개발용 웨이브 스킵을 쓴 판은 실제 플레이가 아니므로 보내지 않는다.

## 프로토콜 v1

TCP 위에 **[본문 길이 u32][본문]** 프레임을 올린다. 정수는 모두 네트워크 바이트 순서(빅엔디언)다. TCP는 보낸 단위를 지켜주지 않으므로(한 번에 반쪽이 오거나 두 개가 붙어 옴), 양쪽 모두 받은 바이트를 쌓아 두고 길이만큼 모였을 때 프레임 하나를 꺼낸다(`FrameReader` / `RunFrameReader`).

| 메시지 | 방향 | 본문 |
|---|---|---|
| SubmitRun (1) | 클라이언트 → 서버 | `u8 version` `u8 type` `u8[16] runId` `u8 rulesetLength` `ruleset(ASCII)` `u16 wave` `u16 totalWaves` `u8 cleared` `u16 life` `u16 summons` `u8 bestHand` `u32 elapsedMs` |
| SubmitAck (2) | 서버 → 클라이언트 | `u8 version` `u8 type` `u8[16] runId` `u8 status` `u8 reason` `u32 rank` `u32 total` |

- `status`: 0 Accepted(새로 저장), 1 Duplicate(이미 저장된 runId — 보낸 쪽에서는 성공과 같음), 2 Rejected(값이 규칙에 맞지 않음 — 다시 보내도 같음).
- `bestHand`는 `HandCategory` 값이며, 한 번도 확정하지 않았으면 `0xFF`.
- 본문 최대 크기는 256바이트다. **길이 필드만 보고 먼저 거부한다.** 본문이 다 오기를 기다렸다가 검사하면, 거대한 길이를 보내 메모리를 잡아 두는 입력을 막을 수 없다.
- 본문이 모자라거나 **남아도** 형식 오류로 본다. 남는 바이트를 무시하면 다른 버전의 메시지를 엉뚱하게 해석할 수 있다.
- C#과 C++이 같은 바이트를 만드는지는 양쪽 테스트가 **같은 고정 바이트열**을 검사해서 확인한다.

## 설계 결정

**바이너리 형식을 쓴다.** 메시지가 두 종류뿐이고 필드가 고정돼 있어 JSON 파서를 들일 이유가 없다. 대신 엔디언과 필드 순서를 문서와 테스트로 고정했다.

**runId로 중복을 막는다(멱등성).** 서버가 저장하고 ACK를 보냈는데 ACK가 유실되면, 클라이언트는 실패로 보고 같은 기록을 다시 보낸다. 서버는 같은 runId를 한 번만 저장하고 처음과 같은 순위를 Duplicate로 돌려준다. 그래서 "최소 한 번 전송 + 중복 제거"로 결과적으로 한 번만 반영된다. 다만 계정이 없으므로 이건 사용자 확인이나 치팅 방지가 아니다.

**서버는 파일에 쓴 뒤에 ACK를 보낸다.** 순서가 반대면 ACK를 받은 클라이언트가 기록을 지운 뒤 서버가 꺼질 때 기록이 사라진다. 기록은 한 줄씩 덧붙이고 `fflush` + `_commit`으로 디스크까지 내린다. 쓰는 도중 꺼져 잘린 마지막 줄은 다시 켤 때 건너뛴다. 그 줄은 ACK를 보내기 전이라 클라이언트가 다시 보낸다. 저장에 실패하면 ACK 없이 연결을 끊어 클라이언트가 다시 보내게 한다.

**클라이언트도 먼저 파일에 쓴다(outbox).** 임시 파일(`.tmp`)에 다 쓴 뒤 이름을 바꿔 넣으므로, 쓰다 만 파일이 대기열에 섞이지 않는다. 형식이 깨진 파일은 `.bad`로 옮기고 나머지는 계속 보낸다.

**서버는 스레드 하나에서 select로 돌린다.** 소켓은 논블로킹이고, 연결마다 받은 바이트 버퍼(`FrameReader`)와 보낼 바이트 버퍼를 따로 둔다. `send`가 일부만 보내면 남은 것은 소켓이 다시 쓰기 가능해질 때 이어서 보낸다. 보낼 게 남은 연결만 쓰기 대기에 넣는다(항상 넣으면 select가 바로 돌아와 CPU를 태운다). 일정 시간(기본 10초) 아무것도 안 보내는 연결과 동시 연결 한도(63개)를 넘는 연결은 끊는다. 이 규모의 요청에는 IOCP나 스레드 풀이 필요 없고, 한 스레드라 저장소에 락도 필요 없다.

**서버는 값이 말이 되는지 검사한다.** 형식은 맞아도 규칙상 나올 수 없는 값은 거부한다. `hand-loop-v1` 기준으로 전체 50웨이브, 도달 웨이브 1~50, 라이프 0~20, 소환 수 ≤ 도달 웨이브(라운드당 최대 1기), 족보 0~12 또는 없음이어야 한다. 또 클리어가 아니면 라이프가 0이어야 하고, 클리어면 도달 웨이브가 50이어야 한다. 해석조차 안 되는 메시지는 runId도 믿을 수 없으므로 ACK 없이 끊는다.

**클라이언트 전송에는 전체 시간 제한이 있다(기본 3초).** 소켓 비동기 작업은 취소 토큰을 받지 않으므로, 시간이 다 되면 소켓을 닫아 대기 중인 작업을 예외로 끝낸다. 모든 `await`에 `ConfigureAwait(false)`를 붙여 메인 스레드로 돌아오지 않게 했다.

**연결이 안 되면 그 자리에서 멈춘다.** 첫 기록이 연결에 실패하면 나머지도 실패할 가능성이 높으므로, 다음 기회까지 기다린다. 게임 종료가 곧 다음 재시도 시점이라 따로 재시도 타이머를 두지 않았다.

**순위.** 도달 웨이브가 높을수록, 같으면 남은 라이프가 많을수록, 같으면 빨리 끝낼수록 위다. 정렬하지 않고 "나보다 나은 기록 수 + 1"로 센다. 동점은 같은 순위이고, 기록 수천 개 규모에서는 충분하다.

## 실행 방법

1. 서버 빌드와 테스트: `Server/RankServer.sln`을 Visual Studio 2022로 열어 빌드한다. 명령줄에서는 `Server/build.bat`가 빌드 후 테스트까지 돌린다.
2. 서버 실행: 솔루션에서 F5(시작 프로젝트 RankServer), 또는 `Server/bin/Release/RankServer.exe --port 7777 --data runs.txt`
3. Unity에서 `Tools/Poker Defense/Install Run Reporter`를 한 번 실행한다(씬 연결).
4. 게임을 끝까지 하면 결과 화면에 순위가 나온다. 서버를 끄고 하면 "서버 연결 실패"가 나오고, 서버를 켠 뒤 게임을 다시 시작하면 남은 기록부터 보낸다.

접속 주소·포트·시간 제한·전송 여부는 Game 씬의 `RunReporter` 인스펙터에서 바꾼다. 클라이언트 outbox는 `Application.persistentDataPath/RunOutbox`에 있다.

## 검증 (2026-09-27)

- **C++ 서버 테스트 16개 통과**(`Server/build.bat`): 프로토콜 6(고정 바이트열, 왕복, 모자람·남음, 버전·종류, ACK, 값 검사), 프레임 조립 3(한 바이트씩, 붙어 온 두 프레임, 길이 0·과대), 저장소 3(순위, 중복, 잘린 마지막 줄), 실제 소켓 4(나눠 보낸 제출, 거부, 잘못된 길이로 끊기, 유휴 시간 초과).
- **C# 네트워크 테스트 21개**: 프로토콜 8, outbox 6, 전송 7(정상, 중복, 조각난 응답, 다른 runId의 ACK, 응답 전 끊김, 시간 초과, 서버 없음). 전송 테스트는 테스트 안에서 `TcpListener`로 가짜 서버를 띄워 상황을 만든다. Unity 밖에서 같은 테스트 코드를 .NET으로 컴파일해 먼저 확인했고, Unity Test Runner에서 EditMode 전체 246/246 통과를 확인했다.
- **실제 C++ 서버와 C# 클라이언트 통합**: 첫 전송 Accepted(1/1), 같은 기록 재전송 Duplicate(같은 순위), 규칙에 맞지 않는 기록 Rejected. 서버 파일에는 한 줄만 남았다.
- 아직 안 한 것: 모바일 기기에서의 전송.

## 한계

- **서버는 점수가 정당한지 증명하지 못한다.** RunJournal이 보드 배치, 모든 행동, 전투 재현 상태를 기록하지 않기 때문에 서버가 다시 시뮬레이션할 수 없다. 값의 범위와 규칙상 모순만 거른다.
- 계정이 없다. runId 중복 제거는 같은 기록의 재전송을 막을 뿐, 누가 보냈는지는 모른다.
- 암호화와 인증이 없다. 공개 네트워크에 띄울 용도가 아니다.
- 서버는 Windows(Winsock) 전용이다. `select`의 소켓 수 한도 때문에 동시 연결은 63개까지다.
- 재시도는 다음 실행과 다음 게임 종료 때만 한다. outbox의 용량과 보존 기간 제한은 아직 없다.
- 순위 조회만 따로 하는 메시지는 없다. 제출할 때 받은 순위만 보여준다.
