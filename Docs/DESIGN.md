# 포커 디펜스 — 기본 구조 설계

> 이 문서는 **구조 설계**만 다룬다. 수치 밸런싱은 ScriptableObject 데이터로 분리하며 이 문서에 고정하지 않는다.
> 작업 진행 기록은 [HISTORY.md](HISTORY.md), 필요한 이미지 목록은 [ART_REQUEST.md](ART_REQUEST.md) 참조.

## 0. 확정된 전제

| 항목 | 결정 |
|---|---|
| 게임 모드 | **싱글 PvE만.** 네트워크 코드 없음 |
| 렌더링 | **2D 스프라이트 (URP 2D Renderer)** |
| 소환 규칙 | **족보 1개 = 유닛 1기** |
| 배치 규칙 | **누적 배치 + 동일 유닛 머지** |
| 엔진 | Unity 6000.4.0f1 / URP 17.4 / Input System 1.19 |
| 타깃 | 모바일 세로 (레퍼런스와 동일한 9:16 기준) |
| 스테이지 | **50웨이브 = 50라운드. 10·20·30·40에 보스, 50에 최종 보스.** 무한 진행 없음 (2026-08-23, 20웨이브에서 확장 — [HISTORY.md](HISTORY.md)) |
| 재화 | **Chip.** 스테이지 안에서만 쓰고 종료 시 초기화. 메타 성장 없음 |
| 플레이 시간 | 1스테이지 12~18분이었던 20웨이브 기준 수치. 50웨이브 확장 후 실측치는 아직 갱신 전 |

**플레이어가 외워야 할 관계는 두 단계뿐이다.** 족보 → 어떤 유닛이 나오는가, 유닛 → 어떤 전투 역할인가. 이 원칙을 지키기 위해 카드 무늬·숫자에 따른 유닛 속성, 카드 강화, 덱빌딩, 장비, 속성 상성, 액티브 스킬, 상태이상은 넣지 않는다. 카드는 끝까지 **족보를 만드는 재료** 역할에만 집중한다.

## 1. 라운드 루프

```
        ┌──────────────────────────────────────────────┐
        ↓                                              │
 [Draw] → [Exchange] → [Evaluate] → [Place] → [Combat] → [Result]
   5장     자리당 1회    족보 판정    배치/머지   웨이브     클리어 판정
                                                          │
                                                          └→ 실패 시 [GameOver]
```

각 페이즈의 책임과 종료 조건:

| 페이즈 | 하는 일 | 종료 조건 |
|---|---|---|
| `Draw` | 52장 덱을 셔플해 5장 드로우 | 즉시 |
| `Exchange` | 카드를 골라 교체. **여러 번 가능하되 한 자리는 한 번만** | 플레이어 확정 입력 |
| `Evaluate` | 최종 5장 → 족보 판정 → 유닛 1기 결정 | 즉시 |
| `Place` | 소환된 유닛을 그리드 슬롯에 배치. 동일 유닛끼리 머지 | 플레이어 확정 입력 |
| `Combat` | 웨이브 스폰, 유닛 자동 전투, 제한시간 카운트 | 적 전멸 or 시간 초과 |
| `Result` | 클리어/실패 판정, 보상 정산 | 즉시 → 다음 `Draw` |

**라운드 N은 웨이브 N을 치른다.** 둘은 1:1이라 HUD는 라운드만 보여준다.

**자동으로 넘어가는 구간과 플레이어 입력이 필요한 구간이 갈린다.** `GameFlowController`는 자동 구간만 맡는다.

| 전이 | 방식 |
|---|---|
| `Draw` → `Exchange` | 자동 (드로우 즉시) |
| `Exchange` → `Evaluate` | **플레이어** — 확정 버튼 |
| `Evaluate` → `Place` | 자동 (판정 즉시 소환) |
| `Place` → `Combat` | **플레이어** — 전투 시작 버튼 |
| `Combat` → `Result` | 자동 (전멸 or 시간 초과) |
| `Result` → 다음 `Draw` | 자동 — 단 보스를 잡았으면 **플레이어**가 특전을 고를 때까지 멈춘다 (§11.2) |

**`Combat`으로 넘어가려면 두 조건을 모두 만족해야 한다.**

- `Place` 페이즈여야 한다. 교체 도중에 전투로 뛰면 그 라운드의 소환을 통째로 건너뛴다.
- 배치 대기 유닛이 없어야 한다. 남겨두고 넘어가면 다음 라운드의 소환이 덮어써서 조용히 사라진다.

**설계 결정: 교체는 자리 단위로 잠근다.** 라운드 안에서 몇 번이든 교체를 누를 수 있지만, 한 번 바꾼 자리는 그 라운드에 다시 못 바꾼다. 결과적으로 최대 교체 장수는 5장으로 "한 번에 몰아서 5장까지"와 같다. 나눠 바꾸게 한 이유는 **바뀐 결과를 보고 다음 선택을 하게** 만들기 위함이다. 한 장씩 열어보는 편이 기대감이 크다.

**설계 결정: 카드 페이즈는 순차적이지만 보드 조작은 전투와 병행한다.**

`Draw`~`Place`는 순서대로 한 번씩 지나간다. 하지만 **보드 조작(이동·머지·판매·Joker·지원 소환)은 전투 중에도 열려 있다.** 적이 도는 것을 보면서 배치를 고쳐 대응하는 것이 이 게임에서 가장 손이 바쁜 지점이고, 그걸 막으면 배치가 "전투 전에 한 번 정하고 구경하는 것"이 된다.

병행이 만드는 문제 두 가지는 짚고 넘어가야 한다.

- **공격 쿨다운을 슬롯이 아니라 유닛으로 들고 있어야 한다.** 슬롯으로 들면 빈 칸으로 옮길 때마다 그 칸의 쿨다운 0을 물려받아 **이동을 반복하는 것만으로 연사가 된다** (실측 10배). 위치를 고르는 선택이 딜 사이클 조작으로 변한다.
- **골라둔 슬롯은 라운드를 넘기지 않는다.** 유닛을 고른 채로 웨이브가 끝나면 카드 단계인데 화면은 "유닛 고른 상태"로 남아 포커를 건너뛴 것처럼 보인다. 새 라운드가 열리면 선택을 놓는다.

## 2. 어셈블리 / 레이어 구조

**asmdef를 쓰지 않는다.** 모든 코드가 Unity의 predefined assembly에 들어간다.

```
Assembly-CSharp           ← 게임 코드 전부 (Poker/Game/UI)
        ↑
Assembly-CSharp-Editor    ← Editor/ 폴더 밑. EditMode 테스트
```

`Assembly-CSharp-Editor`는 `Assembly-CSharp`을 자동으로 참조하므로 테스트가 게임 코드를 볼 수 있다. 에디터에서 폴더만 만들면 되고 설정할 것이 없다.

### 레이어는 폴더와 네임스페이스로만 표현한다

```
PokerDefense.Poker      ← 포커 규칙 전용
        ↑
PokerDefense.Game       ← 런타임 전체 (플로우/보드/유닛/적/데이터 SO)
        ↑
PokerDefense.UI         ← 카드 UI, HUD, 팝업
```

- `Poker`는 `Game`을 모른다. `Game`은 `UI`를 모른다 (UI가 `Game`을 구독).
- **이 방향을 컴파일러가 강제하지 않는다.** 한 어셈블리이므로 어느 쪽이든 서로를 참조할 수 있다. 지키는 것은 전적으로 관례다.

### 관례로 지킬 것

- **역방향 참조 금지.** `Poker` 네임스페이스 안에서 `PokerDefense.Game`/`PokerDefense.UI`를 `using` 하지 않는다. `Game`에서 `PokerDefense.UI`를 `using` 하지 않는다.
- **셔플에 `UnityEngine.Random`을 쓰지 않는다.** 전역 정적 상태라 인스턴스별 시드를 잡을 수 없고, 그러면 `Deck(int seed)`의 재현성 테스트가 성립하지 않는다. `System.Random` 주입을 유지한다.
- **`Poker`에 ScriptableObject·MonoBehaviour를 두지 않는다.** 족보 → 유닛 매핑처럼 게임 밸런스에 속하는 것은 `Game`의 `HandUnitTable`이 담당한다.

컴파일러가 막아주지 않으므로 이 세 줄이 유일한 방어선이다. 어겨도 빌드는 통과한다.

**테스트 폴더 이름은 정확히 `Editor`여야 한다.** 테스트 러너는 asmdef가 아니라 `nunit.framework`를 참조하는 로드된 어셈블리를 스캔해 `EditorOnly`면 EditMode로 분류하기 때문이다. 대신 `[UnityTest]`·`LogAssert` 등 `UnityEngine.TestTools`와 PlayMode 테스트는 쓸 수 없다 — 순수 NUnit만 가능하다.

**개발 도구도 같은 자리에 둔다.** `Editor/` 밑은 빌드에 들어가지 않으므로 치트·검증 창을 여기 두면 뺄 것이 없다. 게임 코드에 진입점이 필요하면 **`#if UNITY_EDITOR`로 감싸고 최소한만** 남긴다 — 도구가 아는 것(무엇을 소환할지, 어떤 카드가 어떤 족보인지)은 전부 `Editor/`에 두고, 게임 코드는 "이대로 바꿔라"만 안다.

### 폴더 구조

## 3. 포커 코어 (`PokerDefense.Poker`)

### 3.1 카드

```csharp
public enum Suit  { Spade, Heart, Diamond, Club }        // 4
public enum Rank  { Two = 2, ..., Ten = 10, Jack, Queen, King, Ace = 14 }  // 13

public readonly struct Card { public readonly Suit Suit; public readonly Rank Rank; }
```

- `Ace = 14` 로 두고, 백스트레이트(A-2-3-4-5) 판정 시에만 A를 1로 재해석한다. 조커 없음 → 52장.

### 3.2 덱

```csharp
public sealed class Deck
{
    public Deck(int seed);      // System.Random 시드 주입 → 테스트 재현 가능
    public Card Draw();
    public int Remaining { get; }
}
```

**설계 결정: 덱은 라운드마다 새로 셔플한다.** 라운드 간 덱을 이어가면 카드 카운팅이라는 전략 축이 생기지만, 후반 라운드에서 덱 고갈 처리·리셋 타이밍 등 규칙이 붙는다. 지금은 라운드 독립이 단순하다. (교체는 같은 덱에서 뽑으므로 **한 라운드 안에서는 중복 카드가 나오지 않는다.**)

### 3.3 족보 판정

```csharp
public enum HandCategory
{
    HighCard, OnePair, TwoPair, ThreeOfAKind,
    Straight, Flush, FullHouse, FourOfAKind, StraightFlush,
    // 특수 (기본 카테고리의 하위 분류를 별도 승격)
    BackStraight,        // A-2-3-4-5
    Mountain,            // A-K-Q-J-10
    BackStraightFlush,   // A-2-3-4-5 동일 무늬
    RoyalStraightFlush,  // A-K-Q-J-10 동일 무늬
}

public readonly struct HandResult
{
    public readonly HandCategory Category;
    public readonly IReadOnlyList<Card> KeyCards;   // 연출용 하이라이트 (페어 2장 등)
}

public static class HandEvaluator
{
    public static HandResult Evaluate(IReadOnlyList<Card> five);
}
```

**주의: `HandCategory`의 enum 순서를 "강함"으로 쓰지 않는다.** 백스트레이트는 정통 포커에서 가장 약한 스트레이트지만 이 게임에서는 특수 유닛을 준다. 즉 **판정 결과(Category)와 보상 세기(유닛)는 별개 축**이며, 연결은 코드가 아니라 데이터 테이블(`HandUnitTable`)이 담당한다. 밸런싱을 코드 수정 없이 바꾸기 위함이다.

족보끼리 비교해야 할 때(결과 화면의 "최고 족보" 등)는 enum 값 대신 `HandRarity.RankOf`를 쓴다. 등장 확률로 정해지는 포커의 사실이라 Poker에 두고, 보상 세기와는 여전히 별개다.

**참고 — 5장 드로우 시 등장 확률** (밸런싱 시작점):

| 족보 | 확률 |
|---|---|
| 하이카드 | 50.1% |
| 원페어 | 42.3% |
| 투페어 | 4.75% |
| 트리플 | 2.11% |
| 스트레이트(마운틴·백스 제외) | 0.31% |
| 플러시 | 0.197% |
| 풀하우스 | 0.144% |
| 마운틴 / 백스트레이트 | 각 0.039% |
| 포카드 | 0.024% |
| 스트레이트 플러시(특수 제외) | 0.00123% |
| 로열 / 백스트레이트 플러시 | 각 0.000154% |

→ **90% 이상이 하이카드·원페어로 몰린다.** 교체 1회로 이 분포가 다소 완화되지만, 저등급 유닛 위주 전개가 기본값이 된다. 그래서 머지 재료 수급은 포커가 아니라 Chip 지원 소환이 맡는다 (§9.3).

## 4. 데이터 (ScriptableObject)

수치는 전부 여기로 뺀다. 코드에는 하드코딩된 밸런스 값을 두지 않는다.

| SO | 필드 |
|---|---|
| `UnitDefinition` | id, 표시명, 플레이스홀더 색, 공격력, 공격속도, 사거리, 성급 배수(★1/★2/★3), 공격 패턴 + 패턴 수치(Multi 타겟 수 / Splash 반경 / Pierce 관통 길이), **방향별 아트 4장**(§10.4) |
| `HandUnitTable` | `HandCategory → UnitDefinition` 매핑 1개 (에셋 1개, 전역) |
| `EnemyDefinition` | id, 표시명, 플레이스홀더 색, 최대HP, 이동속도, 타입 |
| `WaveDefinition` | 스폰 엔트리 리스트(적, 수량, 간격, 시작 지연), 제한시간, 웨이브 번호, Joker 보상, 특전 보상 여부 |
| `StageDefinition` | `WaveDefinition` 순서 리스트, 시작 라이프, 시작 Chip, 웨이브당 라이프 피해 상한 |
| `EconomyDefinition` | 유지 보너스 상한, 지원 소환 비용·확률·횟수, 판매 가격 |
| `PerkTable` | 딜러 특전 전체 목록 (에셋 1개, 전역). 행마다 id, 이름, 설명, 계열, 수치 2개 |

**아직 넣지 않은 필드가 있다.** 쓰이지 않는 필드를 미리 두면 추측 코드가 된다.

- **아트가 없는 유닛은 플레이스홀더 색으로 떨어진다.** M11이 13종을 한 번에 채우지 않으므로 아트가 있는 칸과 색 사각형인 칸이 섞인다. 네 방향이 다 찬 유닛만 아트로 그린다.
- **투사체 프리팹 없음.** 공격은 여전히 즉시 히트다 (§5.5).
- **처치 보상 필드 없음.** 적 처치로는 Chip을 주지 않는다 (§9.2). 웨이브 구성만 바꿔도 경제가 흔들리는 것을 막기 위함이다.

## 5. 전투 (`Combat` 페이즈)

### 5.1 보드

- 중앙 **5열 × 3행 = 15슬롯** 그리드. 슬롯 하나에 유닛 하나.
- 적은 그리드를 감싸는 **고정 웨이포인트 트랙**을 순회한다. 유닛은 사거리 안에 들어온 적을 자동 공격한다.
- `GridBoard`가 점유 상태와 배치·머지 규칙을 소유한다. 슬롯은 `UnitInstance[15]`이고 인덱스로만 다룬다.
- 유닛/적은 서로를 직접 찾지 않고 활성 적 목록을 통해 조회한다 — 매 프레임 `FindObjectsOfType` 호출을 막기 위함. 이 목록은 `CombatContext`가 직접 들고 있으며 별도 클래스로 빼지 않는다.

**보드는 월드 스페이스다.** 카드 UI와 HUD만 uGUI로 남는다. 적이 월드를 이동하고 유닛이 사거리로 조준하므로, 보드가 캔버스에 있으면 사거리를 픽셀로 다뤄야 하고 URP 2D 렌더러·2D 물리·스프라이트 도구를 쓸 수 없다.

슬롯 클릭은 `Pointer` → `ScreenToWorldPoint` → `Physics2D.OverlapPoint`로 잡고, 카드 UI 위 클릭은 `EventSystem.IsPointerOverGameObject()`로 거른다. 누를 수 없는 칸은 `hitbox.enabled = false`로 검사에서 뺀다.

### 5.2 머지

**설계 결정: 머지는 티어 상승이 아니라 "성급(★) 상승"이다.**
동일 `UnitDefinition` + 동일 성급 유닛 2기 → 같은 유닛의 ★+1 (최대 ★3). 스탯은 `UnitDefinition`의 성급 배수를 적용한다.

대안으로 "동일 티어 2기 → 상위 티어 1기"가 있지만, 그러면 *하이카드 2기 = 원페어 1기*가 되어 족보를 맞춘 가치가 희석된다. 족보 축(유닛 종류)과 머지 축(성급)을 직교시키는 편이 낫다.

**머지 경로는 두 가지다. 둘 다 있어야 한다.**

1. **소환 유닛 → 보드**: 배치할 때 같은 유닛·같은 성급 칸을 고르면 합쳐진다.
2. **보드 → 보드**: 이미 놓인 두 유닛을 합친다 (`GridBoard.TryMergeSlots`). 재료 쪽 칸이 비워진다.

2번이 없으면 **★3에 도달할 수 없다.** 소환되는 유닛은 항상 ★1이라 ★2에 얹을 수 없고, 보드 위의 ★2 두 기를 합칠 방법이 사라지기 때문이다. UI에서는 유닛을 탭해 고르고 상대를 탭해 합친다.

성급은 공격력·공격속도에만 곱해지고 **사거리에는 곱해지지 않는다.** 성급으로 사거리까지 늘면 배치 위치를 고르는 의미가 줄어든다.

### 5.2.1 Joker — 희귀 유닛의 유일한 성장 수단

**Joker는 아무 유닛의 성급을 한 단계 올린다.** 동일 유닛이 필요 없다.

- 획득: **Wave 10·20·30·40 보스 각 ×1.** 한 스테이지에 최대 4개. Wave 50은 게임 종료라 주지 않는다. (2026-08-23, 5·10·15·20 4회 주기에서 변경 — [HISTORY.md](HISTORY.md))
- ★1 → ★2, ★2 → ★3. ★3에는 쓸 수 없다.

포카드는 0.024%, 로열 스트레이트 플러시는 0.000154%다. ★3에 같은 유닛 4기가 필요하므로 중복 소환만으로는 도달할 수 없고, **희귀 족보를 뽑은 기쁨이 "어차피 못 키우는 ★1"로 끝난다.** Joker가 이 구멍을 메운다.

공급을 스테이지당 3개로 고정한 이유는 통제 때문이다. Chip으로 같은 유닛을 복제 구매하는 안도 검토했으나, 로열 스트레이트 플러시 복제에 값을 매기는 순간 싸면 착취되고 비싸면 무의미해진다. 보스 드롭은 그 문제가 없다.

Joker를 어디에 쓸지가 그 자체로 선택이 된다 — 지금 주력인 원페어 ★2를 ★3으로 만들 것인가, 방금 뜬 풀하우스를 ★2로 만들어 길게 쓸 것인가.

### 5.3 트랙과 적 이동

**트랙은 닫힌 루프다.** 적은 골에 도달해 빠져나가지 않고 죽을 때까지 계속 돈다. §5.4대로 라이프는 "적이 새어나갔을 때"가 아니라 "제한시간이 끝났을 때 잔여 적 수만큼" 깎이기 때문이다. 일반적인 타워 디펜스와 다른 지점이다.

- **웨이포인트를 씬 오브젝트로 두지 않는다.** 그리드를 감싸는 사각 루프라 `GridBoard`가 그리드 크기에서 계산하면 된다. 씬에서 점을 찍어 관리할 이유가 없다.
- **적 위치는 트랙 위 진행도(0~1) 하나로 표현한다.** 월드 좌표는 화면에 그릴 때만 변환한다. 상태가 순수 C#으로 유지되고, "가장 앞선 적"이 진행도 비교 한 번으로 끝난다.

### 5.4 클리어 판정

- 제한시간 내 웨이브 전멸 → 클리어, 다음 라운드. **제한시간을 기다리지 않고 마지막 적이 죽는 즉시 넘어간다.**
- 시간 초과 → 잔여 적 수만큼 라이프 감소. 라이프 0 → `GameOver`.
- 잔여 적은 다음 웨이브로 넘기지 않고 제거한다 (누적으로 인한 데스 스파이럴 방지).

**웨이브는 스폰 스케줄이라 "화면이 비었다"와 "웨이브가 끝났다"가 다르다.** 보이는 적을 다 잡아도 아직 안 나온 적이 남아 있으면 그 스폰까지 기다린다. 스폰 간격이 곧 웨이브 난이도라 남은 스폰을 당기지 않는다. 대신 **HUD가 그 구간에 "다음 적까지 n초"를 보여준다** — 그러지 않으면 게임이 멈춘 것처럼 보인다.

**한 웨이브의 최대 피해는 5로 제한한다.**

```
LifeDamage = 보스가 남았으면 5, 아니면 Min(RemainingEnemies, 5)
```

시작 라이프는 12다. 상한이 없으면 Swarm 웨이브(적 10기 이상)를 한 번 놓치는 순간 게임이 즉시 끝난다. 실수 한 번이 곧 패배가 되면 보드를 실험해 볼 여지가 사라진다.

**12는 실측으로 정했다.** 15에서는 자동 진행이 11을 남기고 끝나 "지지 않는 판"이 됐다. 상한 5와 함께 보면 **완전 실패 2회 + 부분 실패 하나가 한계**다 — 이 게임의 긴장이 실제로 사는 곳이 초반(보드가 빈 구간)과 보스 셋이라는 실측 결과에 맞춘 값이다.

반대로 **보스는 한 기만 남아도 상한만큼 친다.** 잔여 수로만 세면 보스 웨이브를 실패해도 라이프 1만 잃어 보스가 벽으로 기능하지 못한다.

상한 값은 `StageDefinition`에 있고 판정은 `StageContext.LifeDamageFor` 한 곳에만 둔다. 화면 표기도 같은 함수를 부른다 — 두 곳에 두면 "12마리 남음, 라이프 -12"처럼 어긋난다.

### 5.5 타겟팅과 공격

- **겨냥하는 대상은 언제나 사거리 안에서 가장 앞선 적** 하나다. 패턴(§10.1)은 그 한 발이 **몇 기를 함께 때리는가**만 정한다. 대상 선정 규칙이 유닛마다 갈리면 "왜 저기를 쐈는지"를 읽을 수 없게 된다.
- **공격은 즉시 히트다.** 투사체는 비행 시간과 빗나감 처리가 따라붙는데 클리어 판정과 무관하다. 연출 단계에서 붙인다.
- 성급 배수는 공격력·공격속도에 곱해지고 **사거리·패턴 수치에는 곱해지지 않는다** (§5.2). 성급으로 범위까지 늘면 배치 위치를 고르는 의미가 줄어드는 것은 같은 이유다.
- **한 발의 피해는 대상 수와 무관하게 공격력 그대로다.** 나눠 주면 Multi·Splash가 단일과 같아져 패턴이 사라진다. 대신 이 유닛들은 단일 대상 DPS를 낮게 잡는다.

### 5.6 시뮬레이션 방식

PvE 전용이므로 결정론적 고정 틱을 도입하지 않는다. 일반적인 `Update` + `deltaTime` 으로 충분하다. (PvP를 나중에 붙일 경우 이 결정을 재검토해야 하며, 영향 범위는 `Units/`·`Enemies/`에 한정된다.)

**단, `deltaTime`은 인자로 받는다.**

```csharp
public sealed class CombatContext          // 순수 C#. MonoBehaviour가 아니다
{
    public void Tick(float deltaTime);     // Update()에서 Time.deltaTime을 넘긴다
    public CombatOutcome Outcome { get; }  // InProgress / Cleared / TimedOut
    public int RemainingEnemies { get; }
}
```

고정 틱을 강제하지 않으므로 위 결정과 충돌하지 않으면서, 테스트에서 `Tick(0.1f)`를 원하는 만큼 돌려 전투 한 판을 통째로 시뮬레이션할 수 있다. 포커 코어·라운드·보드와 같은 방식이다.

### 닫은 것 (M10 실측)

- **유지 보너스는 이중 보상이 아니라 지배 전략이었다.** 걱정했던 것은 "좋은 패가 Chip까지 받는다"였는데, 실측은 반대쪽이 훨씬 심했다 — **교체하면 Chip이 0이 되어 지원 소환이 20회에서 1회로 무너진다.** Chip 획득처가 유지 보너스 하나뿐이라 교체가 곧 경제를 끊는 행동이었다. 유지 보너스 상한 4 → 3, 지원 소환 라운드당 2 → 1회로 파이프라인을 좁혔다.
- **성급 배수가 DPS를 16배로 만들고 있었다.** `{1, 2, 4}`가 공격력과 공격속도에 **동시에** 곱해져 ★3 = 4×4배였다. `하이카드 스카우트 ★3`(DPS 320)이 `로열 스트레이트 플러시 소버린 ★1`(162)을 이겨 §10.2의 "상위 족보가 모든 면에서 낫지는 않다"가 "하위 족보 머지품이 항상 낫다"로 뒤집혀 있었다. `{1, 1.6, 2.25}`(DPS ×1 / ×2.56 / ×5.06)로 내렸다 — 4기를 합쳐 5배면 머지는 여전히 이득이고 칸도 아낀다.
- **사거리 2 유닛의 중앙 3칸.** 스카우트·건슬링어를 2.5로 올려 닫았다. 보드 중앙에서 트랙까지가 2.4다.
- **시작 라이프를 15 → 12로 내렸다.** 15에서는 자동 진행이 11을 남기고 끝나 "지지 않는 판"이었다. 12에서 두 번 연속 9·8로 끝나 검증 밴드(3~10) 안에 들어왔다. 상한 5와 함께 보면 완전 실패 2회 + 부분 실패 하나가 한계다.
- **★3 목표를 20웨이브 기준으로 다시 잡았다.** 옛 목표 1~3기는 15웨이브 시절 숫자다. **개수를 정하는 것은 배수도 경제도 아니라 유입 유닛 수**여서 — 20라운드가 포커만으로 20기를 공급하고 손패의 92%가 하이카드·원페어 2종에 몰린다 — 지원 소환을 절반으로 줄여도 10 → 9로만 움직였고, 지원 소환이 0인 판도 4기가 나왔다. 라운드를 20으로 늘리기로 정한 이상 ★3이 늘어나는 것은 결과가 아니라 전제다. §12를 4~9기로 고치고 **"보드가 ★3으로만 차지 않는가"**를 함께 본다. 1~3기로 되돌리려면 머지 축 자체를 다시 설계해야 한다(★3 요구 수 상향 / 라운드마다 유닛을 주지 않음).

### 폐기한 것

**카드 특성** (무늬·숫자가 유닛 능력을 결정) — 채택하지 않는다. 13종 × 조합의 밸런싱 비용, 같은 이름의 유닛이 매번 다른 성능을 갖는 학습 비용, 그리고 **머지 규칙과의 충돌**(특성을 매칭에 포함하면 머지가 사망하고 무시하면 특성 선택이 무의미) 때문이다. 목적이었던 "낮은 족보에도 고민 만들기"는 **유지 보너스(§9.1)가 대신한다.**

## 8. 남은 마일스톤

각 단계는 **검증 조건을 통과해야** 다음으로 넘어간다. M0~M10(포커 코어 → 그리드·머지 → 전투 → 라운드 루프 → Chip 경제 → 웨이브·보스·Joker → 유닛 역할·적 타입 → 딜러 특전 → 밸런싱)은 완료했다. 각 단계에서 무엇을 정했는지는 [HISTORY.md](HISTORY.md)에 있다.

| # | 내용 | 검증 조건 |
|---|---|---|
| M11 | 아트 교체 | **유닛·적·카드** 셋이 전부 스프라이트로 대체되고 슬롯의 이름 라벨이 사라짐. 배경·트랙도 함께 넣는다 |

**M10을 아트와 나눈 이유:** 둘은 서로를 막지 않고, §10.4가 "성급이 올라도 구조 숫자를 바꾸지 않는다"로 못 박아 밸런싱 결과가 아트 사양을 바꾸지 않는다. 아트가 먼저 들어가면 밸런싱을 한 번 돌릴 때마다 렌더링 검증이 따라붙는다.

**M10 검증 조건 — 2026-08-12에 넷 다 통과했다** (실측값은 [HISTORY.md](HISTORY.md)). 밸런싱을 다시 만지면 이 넷을 다시 잰다. 전부 숫자로 답한다 — "작동하게 만들기"로는 끝났는지 알 수 없다.

1. 클리어 시 **잔여 라이프 3~10** (§9.5). 12/12로 끝나면 난이도가 없는 것이고 0이면 벽이다.
2. 한 판에 **★3이 4~9기**이고 **★1·★2가 3칸 이상 남는다** (§12). 보드가 ★3으로만 차면 머지가 다른 축을 전부 덮은 것이다.
3. 보스 5·10·15를 **전부 클리어해 특전을 3회 받는다.** 하나라도 시간 초과로 놓치면 §11이 검증되지 않는다.
4. **교체 정책이 한쪽으로 지배되지 않는다.** 교체 0장과 전부 교체를 같은 조건으로 돌려 결과가 갈리되, 한쪽이 다른 쪽을 압도하면 포커 축이 죽은 것이다.

M10까지는 **플레이스홀더 도형/색상 스프라이트**로 진행한다. 생성형 AI 이미지는 M11에서 한꺼번에 교체하며, 필요 목록은 [ART_REQUEST.md](ART_REQUEST.md)에 정리해 두었다.

Perk 수정자를 어디에 둘지가 M9의 첫 결정이었다. 답은 §11.1의 `PerkSet`이다.

## 9. 스테이지와 경제

### 9.1 유지 보너스 — 이 게임의 핵심 선택

교체를 **덜 쓸수록** Chip을 받는다.

| 사용한 교체 | Chip |
|---|---|
| 0장 | +3 |
| 1장 | +2 |
| 2장 | +1 |
| 3~5장 | 0 |

`Chip = Max(0, 상한 - 사용한 교체 수)`. 상한은 `EconomyDefinition`에 있고 현재 3이다. 사용한 교체 수는 `5 - RoundContext.ExchangeableCount`라 **새 상태가 필요 없다.**

이것이 교체를 "공짜 리롤"에서 **"현재 이득을 포기하고 더 높은 족보에 거는 행동"** 으로 바꾼다. 게임 이름값을 하게 만드는 지점이다.

> **전제조건: 교체 단계에서 현재 족보와 소환될 유닛을 실시간으로 보여줘야 한다.**
> "확정하면 원페어 = 건슬링어 + Chip 4개"를 모르면 유지 보너스는 감으로 찍는 도박이 된다.
> `HandEvaluator.Evaluate`는 순수 함수라 교체 중 아무 때나 현재 손패로 부를 수 있다.

### 9.2 Chip

스테이지 안에서만 쓰고 종료 시 초기화한다. 메타 성장 없음.

| 획득 | 사용 |
|---|---|
| 유지 보너스 | **지원 소환 6 Chip** |
| 유닛 판매 (★1/★2/★3 = 1/2/4) | |
| 일부 딜러 특전 · 보스 보상 | |

**적 처치로는 Chip을 주지 않는다.** 처치 하나하나가 경제와 엮이면 웨이브 구성만 바꿔도 경제가 흔들려 밸런싱이 급격히 어려워진다. 덕분에 `EnemyDefinition`에 보상 필드를 추가할 필요도 없다.

판매 가격은 **유닛 종류와 무관하게 성급으로만 정한다.** 고급 족보라고 판매가까지 외우게 하지 않는다.

### 9.3 지원 소환

6 Chip → 랜덤 하위 유닛 ★1 한 기. 포커를 거치지 않는다.

| 등장 | 확률 |
|---|---|
| 하이카드 유닛 | 40% |
| 원페어 유닛 | 30% |
| 투페어 유닛 | 20% |
| 트리플 유닛 | 10% |

스트레이트 이상은 지원 소환에 나오지 않는다. **라운드당 최대 1회**로 제한한다 — 제한이 없으면 Chip을 모아 한 번에 쏟는 것이 정답이 되어 라운드별 판단이 사라진다.

**횟수를 2회에서 1회로 줄인 것은 실측 결과다.** 2회일 때 한 판에 들어오는 유닛이 40기(포커 20 + 소환 20)가 되어 ★3이 10기 나왔고, 무엇보다 *교체 0장 → Chip → 지원 소환 → 머지* 파이프라인이 상위 족보를 노리는 것보다 강해 **포커 축이 지배당했다.** 유입을 줄이는 것이 두 문제를 동시에 친다.

### 9.4 보드에서 가능한 행동

1. 새 유닛 배치 (빈 슬롯)
2. 새 유닛 즉시 머지 (같은 유닛·같은 성급 슬롯)
3. 보드 유닛 이동
4. 보드 유닛끼리 머지
5. 유닛 판매
6. 지원 소환
7. Joker로 성급 +1 (§5.2.1)

**보드 탭은 모드를 늘리지 않는다.** 대기 유닛이 있으면 칸을 눌러 배치·머지한다. 없으면 **유닛을 고르는 순간 이동 가능 칸과 머지 가능 칸이 함께 강조되고 판매·조커 버튼이 뜬다.** 빈 칸을 누르면 이동, 짝을 누르면 머지다. 다섯 행동이 한 선택으로 흡수된다.

1~5번은 **전투 중에도 된다** (§1). 6번 지원 소환만 `Place` 페이즈로 제한된다 — 라운드당 횟수를 세는 행동이라 페이즈 경계가 필요하다.

**골라둔 슬롯은 UI 상태지 규칙이 아니다.** 보드는 슬롯 탭 말고도 바뀌므로(지원 소환이 빈 칸을 채우는 등) 선택이 빈 칸을 가리킬 수 있다. 그 경우 선택을 버린다.

### 9.5 50웨이브 구성

2026-08-23에 20웨이브 → 50웨이브로 늘렸다(§7-1의 "중반 웨이브가 안 위협적이다" 진단에 대응). 1~19웨이브는 그대로 두고 21~50을 새로 썼다. 보스 주기도 5 → 10으로 늘어나 Act가 5개, 각 10웨이브(일반 9 + 보스 1)로 정리된다. 자세한 수치·근거·검증 결과는 [HISTORY.md](HISTORY.md) 참고.

| Act | 웨이브 | 구성 | 의도 |
|---|---|---|---|
| 1 | 1~9 | Normal → Runner 혼합 | 흐름 학습. 엉성해도 통과 (기존 그대로) |
| | **10 보스** | Boss + Tank ×2 | 첫 실패 가능 구간. **Joker ×1 + 특전 선택** (기존 그대로) |
| 2 | 11~19 | Runner·Swarm·Tank 복합, 전 타입 고밀도 | Perk·머지·Chip 운영이 난이도에 반영됨 (기존 그대로) |
| | **20 보스** | Boss ×2 + Tank·Normal | 두 번째 벽. **Joker ×1 + 특전 선택** (원래 최종 보스였으나 주기 변경으로 중간 보스로 전환, Final Boss 몫은 50으로 넘김) |
| 3 | 21~29 | 신규. Brute 비중 20%→30%로 서서히 상승 | Act1·2 이후의 완만한 확장 |
| | **30 보스** | Boss ×3 + Tank·Normal | 세 번째 벽. **Joker ×1 + 특전 선택** |
| 4 | 31~39 | 신규. Brute 비중 30%→40%, 스폰 밀도도 상승 | 유닛 성장(머지)을 못 따라가면 균열이 보이기 시작 |
| | **40 보스** | Boss ×5 + Tank·Normal | 네 번째 벽. **Joker ×1 + 특전 선택** |
| 5 | 41~49 | 신규. Brute 비중 42%→54%, 최대 밀집 | 단일 유닛 캐리로는 버티기 힘든 구간 |
| | **50 최종 보스** | Final Boss ×3 + Boss ×6 + 소량 | 클리어. 보상 없음(마지막 라운드라 쓸 곳이 없음) |

**보스 웨이브를 10 주기로 두면 특전 선택이 4회(10·20·30·40)가 된다.** 특전 6종으로 3회까지는 매번 3칸 중에서 고르지만(§11), 4회째(40)에는 남은 3종이 전부 제시돼 고르는 행위가 사실상 사라진다 — 6종 중 2종은 한 판에서 아예 못 뽑는다. 특전 종류를 늘리는 것은 이번 확장 범위 밖으로 남겨 뒀다.

Joker 보상은 `WaveDefinition.jokerReward`에 적는다. **웨이브를 클리어해야 들어오고**, 시간 초과로 넘어가면 받지 못한다.

### 9.6 결과 화면

패배해도 성과를 보여준다. 메타 성장 없이도 "지난번보다 잘했다"를 느끼게 하는 유일한 장치다.

도달 웨이브 / 최고 족보 / 최고 유닛 / 총 소환 수 / 사용한 Chip / 남은 라이프. 클리어 시 클리어 시간 추가.

- **최고 족보는 `HandRarity`로 고른다** (§3.3). enum 순서로 고르면 백스트레이트가 스트레이트보다 낮게 잡힌다.
- **최고 유닛은 DPS(공격력 × 공격속도)로 고른다.** 상위 족보가 모든 면에서 하위보다 좋지는 않으므로(§10.2) 성급만으로도 족보만으로도 정할 수 없다.
- 이 기록은 규칙에 관여하지 않아 `StageContext`가 아니라 `RunStats`가 따로 들고 있다.

**재시작은 씬을 다시 로드한다.** 상태를 손으로 되돌리면 새 상태가 생길 때마다 하나씩 빠뜨린다.

## 10. 유닛 역할과 적 (M8)

### 10.1 공격 패턴 5종

13종 유닛이 **각자 다른 시스템을 쓰지 않는다.** 패턴 5개를 나눠 쓴다.

| 패턴 | 내용 | 대상 선정 | 데이터 |
|---|---|---|---|
| Rapid | 빠른 단일 | 타겟 1기 | — |
| Heavy | 느리고 강한 단일 | 타겟 1기 | — |
| Multi | 여러 적 동시 | 사거리 안, 첫 타겟에서 `multiSpread` 거리 안의 적을 앞선 순으로 N기 | 타겟 수 + 타겟 간 최대 거리 |
| Splash | 작은 범위 | 착탄 지점 반경 안 전부 | 반경 |
| Pierce | 진행 방향 관통 | 타겟에서 **트랙 뒤로** 길이 L 안 전부 | 관통 길이 |

Slow·Poison·Stun 같은 상태이상은 넣지 않는다.

**Rapid와 Heavy는 대상 선정이 같다.** 갈리는 것은 공격력·공격속도 배분뿐이고, 그것만으로 역할이 갈린다 — **오버킬 낭비** 때문이다. 25HP 잔챙이에게 Heavy는 한 발에 100을 꽂아 75를 버리고, 같은 DPS의 Rapid는 버리는 것이 없다. 반대로 단일 고HP 상대로는 손해가 없다(오히려 첫 발에 화력을 몰아 넣어 한 사이클 앞선다). 상성 배수 같은 별도 규칙 없이 이 비대칭이 §10.5의 유불리를 그대로 만든다.

**Pierce가 월드 직선이 아니라 트랙 기준인 이유:** 적 위치는 설계상 진행도 하나다(§5.3). 트랙을 따라 재면 "앞뒤"가 이미 정의돼 있고, Splash(반경)와 형태가 확실히 갈린다. 월드 직선으로 만들면 좌표를 다시 들여와야 하는데 얻는 것이 없다.

**Splash는 유닛 사거리 밖의 적도 휘말리게 한다.** 기준이 착탄 지점이라서다. 사거리는 "누구를 겨냥하는가"만 정한다.

**Multi는 사거리 하나만으로는 부족하다.** 사거리가 넓은 유닛(예: 4 = 트랙의 66%)이 "사거리 안에서 앞선 순 N기"만으로 대상을 고르면, 트랙 반대편에 있는 적들까지 한 발에 같이 맞아 화면에서 서로 멀리 떨어진 적이 동시에 맞는 것처럼 보인다. 그래서 Multi는 **먼저 고른 1번 타겟에서 `multiSpread` 거리 안에 있는 적만** 나머지 후보로 두고, 그 안에서 앞선 순 N기를 고른다 — 사거리는 여전히 "발동 가능한가"만 정하고, `multiSpread`가 "그중 몇 기가 뭉쳐 있어야 같이 맞는가"를 정한다.

### 10.2 족보별 유닛

**설계 원칙: 유닛이 족보의 기억 장치가 된다.** 이름과 실루엣이 족보의 구조를 그대로 보여주면 플레이어는 외우는 대신 알아본다. 13종을 서로 다른 판타지 캐릭터로 만들지 않고 **하나의 카드 군단**으로 통일한다.

| 족보 | 이름 | 구조 | 역할 |
|---|---|---|---|
| 하이카드 | 하이카드 스카우트 | 카드 1장 | Rapid — 빠른 단일 |
| 원페어 | 원페어 건슬링어 | **2** (쌍권총) | Rapid — 2연타 |
| 투페어 | 투페어 트윈레인저 | **2+2** (양팔 2연장) | Multi — 2타겟 |
| 트리플 | 트리플 마크스맨 | **3** (3총구) | Heavy — 3발을 모아 한 발 |
| 백스트레이트 | 백스트레이트 에이스 | A→2→3→4→5 계단 | Rapid — 초고속 연사 |
| 스트레이트 | 스트레이트 롱바렐 | **무늬가 섞인** 카드 5장이 박힌 아주 긴 총열 1정 | Pierce — 직선 관통 |
| 마운틴 | 마운틴 킹 | ▲ 산 왕관, 꼭대기에 A | Heavy — 보스 특화 |
| 플러시 | 플러시 보머 | 같은 무늬 반복 | Splash — 범위 |
| 풀하우스 | 풀하우스 배터리 | **3+2** (주포 3 + 보조포 2) | Multi — 3타겟 연사 |
| 포카드 | 포카드 쿼드캐논 | **4** (4연장 중포) | Heavy — 초고화력 저속 |
| 백스트레이트 플러시 | 백스트레이트 플러시 템페스트 | 같은 무늬 A-5가 원형 회전 | Multi — 빠른 다중 |
| 스트레이트 플러시 | 스트레이트 플러시 레일거너 | **같은 무늬** 5장 일렬 = 레일 | Pierce — 강력한 관통 |
| 로열 스트레이트 플러시 | 로열 스트레이트 플러시 소버린 | 10-J-Q-K-A 왕좌, 왕관 | Multi — 초고속 다중 (Splash에서 변경, [HISTORY](HISTORY.md) 참고) |

**핵심은 굵게 표시한 다섯이다.** 2 / 2+2 / 3 / 3+2 / 4를 실루엣으로 읽을 수 있어, 이름을 몰라도 무엇인지 알 수 있다.

- **스트레이트와 스트레이트 플러시는 무늬의 통일성으로 가른다.** 둘 다 *5장 일렬*이고 둘 다 Pierce라 이것 말고 갈릴 축이 없다. 롱바렐은 무늬가 섞이고 레일거너는 하나로 통일된다 — **족보 정의 그대로다.** 크기로도 갈라 롱바렐은 가는 선, 레일거너는 굵은 기둥이다.
- **원페어와 투페어를 시각적으로 구분한다.** 건슬링어는 `1×2`, 트윈레인저는 `2×2`다. 트윈레인저가 한 대상에게 4발을 쏘면 포카드처럼 보이므로, **적 둘에게 각각 한 쌍씩** 쏜다. Pair + Pair가 연출에서도 그대로 보인다.
- **마크스맨은 3연타가 아니라 3발을 모아 한 발이다.** 3연타로 만들면 건슬링어와 역할이 겹친다. 셋이 하나로 모이는 연출이 Three of a Kind와도 맞고 Heavy 역할도 지킨다.
- **배터리는 실루엣만 3+2고 판정은 Multi다.** 주포 3문 → 보조포 2문 순으로 무작위 발사하되(총구 목록은 그대로 5개), 한 발이 서로 다른 적 3기를 때린다. **처음엔 Splash(착탄 지점에 반경만큼 폭발)로 만들었는데, 실제로 넣어 보니 초당 2.5회씩 폭발이 반복되는 것이 "연사"가 아니라 "난사"로 보였다** — 총구는 한 번에 하나만 반짝이는데 화면 저편에서 큰 폭발이 그만큼 자주 터지니 총구와 폭발이 따로 노는 느낌이었다. 총구 화염 연출은 패턴과 무관하게 데이터(§10.4)로만 정해지므로, Splash를 걷어내도 5총구 무작위 발사는 그대로 남는다 — 폭발만 사라지고 기관총이 여러 표적을 훑는 그림이 된다.

**상위 족보가 모든 면에서 하위보다 좋지는 않다.** 쿼드캐논 ★1은 보스·Tank에 강하지만 잔챙이 떼에는 비효율이고, 스카우트 ★3은 빠른 적 처리에 매우 좋다. 그래서 후반에도 하위 족보 유닛을 머지해 쓸 가치가 남는다.

### 10.3 슬롯에 두는 것과 이름 규칙

**슬롯에는 무엇인지와 몇 성인지만 둔다. 수치는 전부 상세로 뺀다.**

| 자리 | 담는 것 |
|---|---|
| 보드 슬롯 | 유닛 아트 + 성급(★). **그뿐이다** |
| 상세 (유닛을 고르면) | 이름, 공격 패턴, 공격력, 공격속도, DPS, 사거리 |
| 소환 안내 | `확정하면 원페어 건슬링어 소환` — 이 시점에만 족보와 유닛이 연결되면 된다 |

**슬롯은 더 못 키운다.** 트랙이 이미 화면 가로 7.425 월드유닛 중 6.8을 쓴다. 5열 세로 화면에서 145px이 상한이고, 늘리려면 열을 줄이거나 트랙을 잘라야 한다. **그 145px에 이름·성급·공격력·공격속도를 다 밀어 넣으면 아트가 들어갈 자리가 없다.** 그래서 정보를 두 층으로 나눈다 — 슬롯은 알아보는 곳, 상세는 비교하는 곳.

**아트가 오기 전까지는 이름이 아트의 대역이다.** M11에서 스프라이트로 교체하며 이름 라벨을 지운다. 지금 미리 지우면 M9 내내 색 사각형 15칸을 색으로만 구분해야 한다.

**상세는 모달 창이 아니다.** 전투 중에도 배치를 고치므로(§1) 보드를 덮으면 적이 안 보이고, 이동·머지 대상 칸을 누를 수도 없다. 화면에 빈 자리가 없어 **기존 안내 문구 자리를 두 줄짜리 정보 블록으로 승격**했다 — 새로 가리는 것이 없다.

**공격력·공격속도·DPS를 셋 다 띄운다.** 하나로 뭉칠 수 없어서다. 패턴마다 배분이 크게 다른데(§10.1) DPS만 보면 오버킬 낭비가 안 보이고, 공격력만 보면 발사 주기가 사라진다.

**이름은 하나뿐이다.** `원페어 건슬링어`처럼 족보와 유닛을 붙여 쓴다. 슬롯이 이름을 담지 않게 된 순간 짧은 이름이 필요한 자리가 없어졌고, **유닛 하나에 이름이 둘이면 플레이어가 외울 것만 늘어난다**(§0). 길이 제한도 없앤다.

**단, 400px 버튼에는 안 들어간다.** 확정 버튼은 `확정 +4`만 띄우고 소환 안내는 폭이 넓은 문구 줄이 맡는다.

**유닛 이름은 한글로 쓴다.** UI 전체가 한글이고 족보명도 `원페어`·`트리플`이다. 여기에 영문 `Pair Gunslinger`를 붙이면 플레이어가 *원페어 = One Pair = Pair* 라는 번역을 한 번 거쳐야 해서, **이름을 기억 장치로 만들려던 목적이 오히려 깨진다.**

**백스트레이트 계열에 "Wheel"을 쓰지 않는다.** A-2-3-4-5를 휠이라 부르는 것은 영어권 관습이고, 한국식 포커에서는 백스트레이트다(§3.3). 한국 플레이어에게 아무것도 연상시키지 못한다.

### 10.4 외형 언어 규칙

- **카드 문양은 장식이지 능력이 아니다.** 유닛마다 고정 심볼 하나를 쓰고, **실제 손패의 무늬에 따라 외형이 바뀌지 않는다.**
  **예외는 스트레이트와 스트레이트 플러시 둘뿐이다** — 이 둘은 무늬의 통일성이 곧 족보라, 롱바렐은 섞고 레일거너는 통일한다. 무늬가 능력과 연결된다는 오해는 안 생긴다. *같은 무늬 = 플러시*는 속성이 아니라 포커 규칙이기 때문이다. 나머지 11종은 고정 심볼 하나를 지킨다. 카드 속성 시스템은 §7에서 폐기했고 외형이 그 오해를 만들면 안 된다. 같은 이유로 하이카드 유닛에 A 카드를 붙이지 않는다 — 랭크가 성능과 연결되는 것처럼 보인다.
- **성급이 올라도 구조 숫자는 절대 바꾸지 않는다.** 건슬링어 ★3에게 총 4자루를 들리면 족보 언어가 깨진다. **페어는 영원히 2, 트리플은 영원히 3, 쿼드는 영원히 4다.**
  성급은 갑옷 장식, 카드 오라, 무기 크기·화려함, 이펙트 강도로만 표현한다. 슬롯의 `★` 표기가 이미 성급을 담당하므로 **구조는 실루엣, 성급은 별**로 두 축이 분리된다.
- **소버린만 예외적으로 크게 만든다.** 13종 중 유일한 군주급이며 등장 확률이 0.000154%다. 등장 연출은 과해도 된다.
  단 이 연출을 소버린 전용으로 만들면 **평생 한 번도 못 보는 플레이어가 생긴다.** 스트레이트 플러시 이상(합계 약 0.0015%)에 등급별 3단계로 스케일하는 편이 실제로 발동한다.

**유닛은 방향별 스프라이트 4장을 쓴다.** 적은 닫힌 루프를 360도로 돌지만 유닛은 회전하지 않는다(§5.3). 정면 한 장으로 두면 오른쪽 적을 쏠 때도 왼쪽을 겨눈 그림이 남는다. 아래(정면)·위(후면)·좌·우를 만들고 **`CombatContext`가 기록한 조준 방향**으로 갈아 끼운다.

- 방향은 유닛을 키로 들어 기록한다 — 슬롯으로 들면 전투 중 이동할 때 어긋난다. 공격 쿨다운과 같은 이유다(§1).
- **좌우를 플립으로 대신하지 않는다.** 장수는 절반이 되지만 총을 든 손이 바뀐다.
- 판정은 `|dx| > |dy|`로 좌우·상하를 가르는 4분할이면 충분하다.
- 전투 중이 아니면 정면으로 세운다. 배치 단계에서 유닛이 제각각을 보고 있으면 이유를 알 수 없다.

**총구 화염은 방향마다 "총구 목록"으로 적는다.** 한 곳에만 띄우면 §10.2의 구조 숫자가 연출에서 사라진다 — 쌍권총인데 늘 같은 손만 번쩍이면 총이 하나로 읽힌다.

좌표를 낱개로 들다가 **세 번 한계에 부딪혀** 목록으로 바꿨다. 늘어난 것이 아니라 매번 표현할 수 없는 배치가 나왔다.

| 못 담은 것 | 드러난 곳 | 오차 |
|---|---|---|
| 방향마다 무기 자리가 다르다 | 마크스맨은 총을 어깨에 메서 후면 총구가 등 한가운데가 아니다. 스카우트도 후면 권총이 오른쪽으로 벗어나 있었다 | 21.6px / 23px |
| 무기가 둘이다 | 건슬링어·트윈레인저 | — |
| **총구가 다섯으로 흩어진다** | 배터리는 주포 3문이 머리 위, 보조포 2문이 허리라 **좌우 반전으로는 두 점이 한 자리로 붕괴한다** | 51px |

- **측면 / 정면 / 후면 세 목록을 둔다.** 좌우만은 대칭으로 묶는다 — 실측 차이가 대개 1.7~3.6px이라 나눌 값어치가 없다.
  **단 묶는 값은 좌우 실측의 중점이어야 한다.** 보머는 좌향 무기가 우향보다 짧게 그려져 좌우 차가 5.5px이었고, 한쪽 값을 그대로 쓰면 반대쪽만 4.9px 어긋났다. 차이가 이보다 더 벌어지는 시트가 오면 좌우를 나눌지 다시 본다.
- **총구가 하나인 유닛은 목록에 하나만 넣는다.** 특별 취급이 없다.

**한 발에 전부 터뜨릴지, 하나만 터뜨릴지는 무기 수가 아니라 §10.2의 공격 방식이 정한다.**

| 유닛 | 방식 | 왜 |
|---|---|---|
| 건슬링어 | 순서대로 | 한 대상을 2연타한다. 번갈아 쏴야 쌍권총으로 읽힌다 |
| 트윈레인저 | **동시** | **적 둘에게 각각 한 쌍씩** 쏜다. 교대로 쏘면 Pair + Pair가 사라진다 |
| 배터리 | **무작위** | 총구가 다섯이라 순서대로 돌면 규칙적으로 보인다. 흩어져야 연사로 읽힌다 |

- **패턴에서 유추하지 않고 데이터로 받는다.** 무기가 둘이라고 다 동시가 아니고, 같은 Multi라도 배터리는 동시가 아니다. 코드에 규칙을 박으면 셋 중 하나에서 반드시 깨진다.
- **어느 총구가 쏠 차례인지는 전투가 센 발사 횟수로 정한다.** 무작위도 그 횟수를 흩어서 만든다 — 뷰가 프레임마다 뽑으면 화염이 0.06초 동안 떨린다. 조준 방향·공격 쿨다운과 같은 이유로 **유닛을 키로** 든다.

**화염은 반동에 같이 커져야 한다.** 아트는 발끝을 피벗으로 커지는데 화염 좌표를 고정해 두면, **화염이 보이는 0.06초가 정확히 반동이 가장 큰 구간이라** 늘 어긋난 상태로만 보이고 그 사이 간격까지 변한다. 총구가 높을수록 크게 벌어진다(마크스맨 7.6px).

**모션은 프레임 애니메이션이 아니라 코드가 낸다.** 슬롯이 124px이라 프레임 사이클이 지각되지 않고, 공격속도가 초당 0.4~6.75회로 갈려(성급 배수 포함) 최속 유닛은 한 발이 148ms다. 발사 반동과 대기 호흡을 **스케일**로 준다 — 총구가 카메라를 향해 화면상 "뒤로 밀림"이 정의되지 않고, 위아래로 흔들면 점프처럼 보인다.

실루엣과 VFX는 M11 아트 단계다. 그때 §10.2 표가 그대로 제작 기준이 된다.

### 10.5 적 종류

특수 능력을 넣지 않는다. **HP·이동속도·수량만 바꿔도 역할이 갈린다.**

| 적 | 특성 | 유리한 유닛 |
|---|---|---|
| Normal | 기준 | — |
| Runner | HP↓ 속도↑ | Rapid, Multi |
| Tank | HP↑ 속도↓ | Heavy |
| Swarm | HP 매우 낮음, 다수 | Splash, Multi |
| Boss | HP 매우 높음, 소수 | 단일 고화력 |

**`EnemyDefinition`(HP·이동속도·타입)으로 전부 표현된다.** 코드가 `EnemyType`으로 분기하는 곳은 라이프 피해 상한의 보스 예외(§5.4) 하나뿐이고 나머지는 표기용이다. Shield·Armor·회복·순간이동 같은 기믹은 넣지 않는다.

**적의 남은 HP는 체력 바로 보여준다.** M10까지는 스프라이트 색에 잔여 비율만큼 밝기를 곱했지만, 그것은 적이 단색 사각형이라 성립하던 방식이다. M11에서 컬러 스프라이트가 들어오면 죽어갈수록 검게 뭉개져 **"죽어간다"가 아니라 "안 보인다"** 가 된다. 틴트를 걷어내고 바를 붙인다.

**`EnemyType`에 값을 더할 때는 반드시 뒤에 붙인다.** 기존 에셋이 이 enum을 정수로 들고 있어 중간에 끼우면 모든 적의 타입이 조용히 어긋난다.

**적 타입은 §10.1 없이는 무의미했다.** 타겟팅이 "사거리 내 가장 앞선 적" 한 종류인 동안에는 어떤 적이 나와도 "총 DPS가 충분한가"로 귀결된다. 패턴이 생긴 지금은 속도가 느린 발사 주기를 벌하고(Runner ↔ Heavy), HP 총량이 오버킬을 벌한다(Swarm ↔ Heavy).

## 11. 딜러 특전 (M9)

Wave 10·20·30·40 보스를 잡으면 3개 중 하나를 고른다. 스테이지 끝까지 유지되며 **한 게임에 최대 4개**다. (2026-08-23, 5·10·15 3회 주기에서 변경 — [HISTORY.md](HISTORY.md))

**화면에는 `딜러 특전`으로 나온다.** 코드의 타입·필드 이름(`PerkSet`, `PerkTable`, `PerkId`, `perkReward`)은 영문 `Perk`를 그대로 쓴다 — 식별자와 표기가 같아야 할 이유가 없고, 이 문서에서 `Perk`라고만 쓴 곳은 전부 이 시스템을 가리킨다.

목적은 규칙을 뒤엎는 것이 아니라 **이번 런에서 어떤 플레이를 더 가치 있게 만들지**를 정하는 것이다.

**선택지 3칸은 카테고리를 섞어 뽑는다** — 포커/경제에서 1, 유닛/머지에서 1, 완전 랜덤 1. 비슷한 것 셋만 나오는 상황을 줄인다.

**먼저 6개만 만들어 "고르는 것 자체가 재미있는가"를 검증한다.** 재미가 확인되면 늘린다.

**6종은 선택 3회까지만 성립한다.** 1·2·3회차(10·20·30)에 남는 특전이 5·4·3종이라 매번 3칸을 채울 수 있지만, 4회차(40)에는 남은 3종이 전부 제시돼 고르는 행위가 사실상 사라진다 — 6종 중 2종은 한 판에서 아예 못 뽑는다. 특전을 더 늘리는 것은 확장 후보를 먼저 구현해야 하는 별도 작업으로 남겨 뒀다 (§9.5).

**이름은 한글 하나뿐이다** (§10.3의 유닛 이름과 같은 이유). 괄호 안은 코드의 `PerkId`이고 화면에는 나오지 않는다.

| 계열 | Perk | 효과 |
|---|---|---|
| 포커 | 뚝심 (`Patience`) | 교체 0장이면 유지 보너스 +3 → +5 |
| 포커 | 위로금 (`Insurance`) | 3장 이상 교체했는데 하이카드로 끝나면 +3 Chip |
| 경제 | 흥정 (`Bargain`) | 지원 소환 6 → 5 Chip |
| 경제 | 이자 (`Interest`) | 웨이브 종료 시 보유 Chip 10당 +1 (최대 +2) |
| 머지 | 신병 훈련 (`RookieTraining`) | ★1 공격력 +20% |
| 머지 | 고참 (`Veteran`) | ★2 이상 공격력 +15% |

확장 후보: Second Chance(교체한 자리 재교체) / Pair Collector(원페어 종료 시 Chip) / Recycler(★1 판매가 인상) / Reinforcement(지원 소환 확률 상향) / Perfect Merge(★3 공격속도) / Full Board(10기 이상 시 전체 공격속도) / High Roller(스트레이트 이상 공격력) / Premium Hand(풀하우스 이상 공격속도) / Wild Joker(Joker 사용 유닛 공격력).

### 11.1 수정자를 두는 곳 — `PerkSet`

특전은 `RoundContext`·`GridBoard`·`CombatContext`를 가로질러 규칙을 바꾼다. **호출부마다 "이 특전이 있으면"을 물으면 `if`가 곳곳에 흩어진다.** 그래서 **묻는 창구를 하나로 고정한다.**

`PerkSet`은 `StageContext`가 소유한다 — 수명이 스테이지와 정확히 같고, `RunStats`와 달리 **규칙을 바꾸므로** 따로 떼지 않는다.

| 창구 | 답하는 값 | 부르는 곳 |
|---|---|---|
| `HoldBonus(base, used)` | 유지 보너스 | `StageController.HoldBonusFor` |
| `ConfirmBonusChip(category, used)` | 확정 시 별도 Chip | `GameFlowController` |
| `SupportSummonCost(base)` | 지원 소환 비용 | `PlacementController` |
| `WaveEndChip(chip)` | 웨이브 종료 이자 | `StageContext.ApplyResult` |
| `AttackPowerOf(unit)` | 특전이 붙은 공격력 | `CombatContext.Fire`, `BoardScreen` |

- **호출부는 어떤 특전이 걸렸는지 모른다.** "지금 값이 얼마인가"만 묻는다. 특전을 늘릴 때 손대는 곳은 `PerkTable`(수치)과 `PerkSet`(조건) 둘뿐이다.
- **`AttackPowerOf`가 `UnitInstance`에 없는 이유:** 유닛은 스테이지를 모르는 불변 객체다. 그런데 전투가 실제로 넣는 피해와 상세 블록의 표기는 **반드시 같은 수**여야 하므로(§10.3), 두 곳이 같은 함수를 부른다.
- **유지 보너스만 `StageController`가 한 번 더 감싼다.** 지급하는 쪽과 미리 보여주는 쪽(§9.1의 전제조건)이 각자 조합하면 언젠가 어긋난다.

### 11.2 언제 고르는가

`WaveDefinition.perkReward`가 켜진 웨이브를 **클리어**하면 `GameFlowController`가 다음 라운드를 열지 않고 3칸을 내놓는다. 고르면 그때 라운드가 열린다.

- **Joker 보상과 별도 필드다.** 지금은 둘 다 10·20·30·40에만 켜져 있지만, 한쪽만 주는 웨이브가 생겨도 데이터로 끝난다.
- **최종 보스(20)는 특전을 주지 않는다.** 받아도 쓸 라운드가 없다.
- **이것이 §1의 "플레이어 입력이 필요한 지점"에 셋째를 더한다.** 한 판에 세 번뿐이고, 고르기 전에 라운드가 열리면 선택이 무의미해진다.
- 전면 패널로 띄운다. 웨이브 사이라 보드에 볼 것이 없고, 화면을 덮는 판이 보드 클릭까지 함께 막아 준다.

### 11.3 고른 특전은 어디에 남는가

**상단 줄의 라이프·Chip과 라운드 사이에 이름만 띄운다.** 특전은 라이프·Chip과 같은 "판이 끝날 때까지 유지되는 상태"라 같은 줄이 맞다.

효과 자체는 이미 다른 숫자에 드러난다 — `확정 +5`, `지원 소환 5`, 상세 블록의 공격력. **하지만 그것이 무엇 때문인지는 이 줄에서만 알 수 있다.** 이자만은 웨이브가 끝나는 순간에만 보인다.

**빈 자리는 rect가 아니라 실제로 그려지는 폭으로 재야 한다.** 좌우 라벨의 rect는 크게 잡혀 있지만 실제로 그리는 폭은 그보다 훨씬 좁아서, rect만 보면 가운데가 비어 있는지 알 수 없다.

**보스가 셋이 되면서 특전도 한 판에 3개가 됐고, 그 순간 이 줄이 넘쳤다.** 2개 기준 최악값은 263px이었지만 3개는 338px이라 320px rect를 넘겨 **두 줄로 개행되며 아래를 침범했다.** rect를 400px로 넓혀 닫았다. 실측한 상단 줄 전체는 이렇다.

| 라벨 | 최악 문자열 | 그려지는 범위 |
|---|---|---|
| 라이프 (좌·왼쪽 정렬) | `라이프 12   Chip 120   조커 3` | 482px, x [-520, -38] |
| 특전 (가운데) | `특전  신병 훈련 · 위로금 · 뚝심` | 338px, x [6, 344] |
| 라운드 (우·오른쪽 정렬) | `라운드 20` | 161px, x [359, 520] |

**남은 여유가 좌 44px / 우 15px뿐이다.** 특전을 늘리거나 이름을 길게 지으면 이 줄부터 다시 재야 한다.

> 이 자리를 재면서 **조커를 들고 있으면 라이프 줄이 rect를 넘겨 개행되던 것**을 찾아 고쳤다(폭 380 → 500). 좌측 끝은 x=-520 그대로 두고 폭만 넓힌다.
