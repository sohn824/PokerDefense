## 0. 확정된 전제

| 항목 | 결정 |
|---|---|
| 게임 모드 | **싱글 PvE만.** 게임 진행에는 네트워크를 쓰지 않는다. 끝난 결과만 선택적으로 서버에 보낸다([NETWORK.md](NETWORK.md)) |
| 렌더링 | **2D 스프라이트 (URP 2D Renderer)** |
| 소환 규칙 | **족보 1개 = 유닛 1기** |
| 배치 규칙 | **계속 쌓아 배치하고, 같은 유닛끼리 합친다** |
| 엔진 | Unity 6000.4.0f1 / URP 17.4 / Input System 1.19 |
| 타깃 | 모바일 세로 (레퍼런스와 같은 9:16 기준) |
| 스테이지 | **50웨이브 = 50라운드. 10·20·30·40웨이브에 보스, 50웨이브에 최종 보스.** 무한 진행 없음 (2026-08-23, 20웨이브에서 확장 — [HISTORY.md](HISTORY.md)) |
| 보조 수단 | **손패마다 선택 교체 1회 + 보스 보상 승급권.** Chip 경제와 상점은 제거. 판을 넘어 이어지는 성장(메타 성장) 없음 |
| 플레이 시간 | 20웨이브 시절 1스테이지 12~18분. 50웨이브로 늘린 뒤 실측값은 아직 없다 |

**플레이어가 외워야 할 관계는 두 단계뿐이다.** 족보를 맞추면 어떤 유닛이 나오는지, 그 유닛이 전투에서 무슨 역할을 하는지. 이 원칙을 지키려고 카드 무늬나 숫자에 따른 유닛 속성, 카드 강화, 덱빌딩, 장비, 속성 상성, 액티브 스킬, 상태이상은 넣지 않는다. 카드는 끝까지 **족보를 만드는 재료**로만 쓴다.

## 1. 라운드 루프

```
        ┌──────────────────────────────────────────────┐
        ↓                                              │
 [Draw] → [Exchange] → [Evaluate] → [Place] → [Combat] → [Result]
   5장     자리당 1회    족보 판정    배치/머지   웨이브     클리어 판정
                                                          │
                                                          └→ 라이프 소진 시 [GameOver]
```

각 단계가 하는 일과 끝나는 조건:

| 단계 | 하는 일 | 끝나는 조건 |
|---|---|---|
| `Draw` | 52장 덱을 섞어 5장을 뽑는다 | 즉시 |
| `Exchange` | 카드를 골라 바꾼다. **여러 번 할 수 있지만 한 자리는 한 번만** | 플레이어가 확정 |
| `Evaluate` | 최종 5장의 족보를 판정해 유닛 1기를 정한다 | 즉시 |
| `Place` | 소환된 유닛을 배치하거나, 합치거나, 기존 유닛과 교체하거나, 소환을 포기한다 | 대기 유닛이 없는 상태에서 전투 시작 |
| `Combat` | 웨이브가 나오고, 유닛이 자동으로 싸우고, 제한시간이 흐른다 | 적 전멸 또는 시간 초과 |
| `Result` | 클리어·시간 초과를 정산하고 결과를 짧게 보여준다 | 1.8초 뒤 자동으로 또는 탭하면 다음 `Draw`. 최종 승패는 결과 화면에서 |

**라운드 N에서 웨이브 N을 치른다.** 둘이 1:1이라 HUD에는 라운드만 표시한다.

**자동으로 넘어가는 구간과 플레이어 입력이 필요한 구간이 나뉜다.** `GameFlowController`는 자동 구간만 맡는다.

| 전환 | 방식 |
|---|---|
| `Draw` → `Exchange` | 자동 (뽑자마자) |
| `Exchange` → `Evaluate` | **플레이어** — 확정 버튼 |
| `Evaluate` → `Place` | 자동 (판정하자마자 소환) |
| `Place` → `Combat` | **플레이어** — 전투 시작 버튼 |
| `Combat` → `Result` | 자동 (전멸 또는 시간 초과) |
| `Result` → 다음 `Draw` | 결과 화면이 자동으로 끝나거나 탭하면 진행. 시간 초과여도 라이프가 남으면 다음 라운드 |

**`Combat`으로 넘어가려면 두 조건을 모두 만족해야 한다.**

- `Place` 단계여야 한다. 교체 도중에 전투로 넘어가면 그 라운드의 소환을 통째로 건너뛰게 된다.
- 배치를 기다리는 유닛이 없어야 한다. 남겨 둔 채 넘어가면 다음 라운드 소환이 덮어써서 소리 없이 사라진다.

**설계 결정: 교체는 자리 단위로 잠근다.** 한 라운드 안에서 교체 버튼은 몇 번이든 누를 수 있지만, 일반 교체로 한 번 바꾼 자리는 일반 교체로 다시 바꿀 수 없다. 선택 교체 1회는 이 잠긴 자리 하나에만 쓸 수 있는 예외다(§9.1). 그래서 최대 교체 장수는 5장이고, 한 번에 5장을 몰아 바꾸는 것과 같다. 그래도 나눠 바꾸게 한 이유는 **바뀐 결과를 보고 다음 선택을 하게** 만들기 위해서다. 한 장씩 열어볼 때 기대감이 더 크다.

**설계 결정: 카드 단계는 순서대로 가지만, 보드 조작은 전투와 동시에 할 수 있다.**

`Draw`~`Place`는 순서대로 한 번씩 지나간다. 하지만 **보드 조작(이동·합치기·퇴장·승급권)은 전투 중에도 할 수 있다.** 적이 도는 것을 보면서 배치를 고쳐 대응하는 순간이 이 게임에서 손이 가장 바쁜 지점이다. 이걸 막으면 배치는 "전투 전에 한 번 정하고 구경하는 것"이 된다.

동시에 조작할 수 있게 하면서 생기는 문제가 두 가지 있다.

- **공격 쿨다운은 슬롯이 아니라 유닛이 들고 있어야 한다.** 슬롯이 들고 있으면, 빈 칸으로 옮길 때마다 그 칸의 쿨다운 0을 물려받는다. 그러면 **이동만 반복해도 연사가 된다**(실측 10배). 배치 위치를 고르는 선택이 공격 주기를 조작하는 꼼수로 바뀐다.
- **골라 둔 슬롯은 다음 라운드로 넘기지 않는다.** 유닛을 고른 채 웨이브가 끝나면, 카드 단계인데도 화면은 "유닛을 고른 상태"로 남아 포커를 건너뛴 것처럼 보인다. 새 라운드가 시작되면 선택을 푼다.

## 2. 어셈블리 / 레이어 구조

**asmdef를 쓰지 않는다.** 모든 코드는 Unity가 기본으로 만드는 어셈블리에 들어간다.

```
Assembly-CSharp           ← 게임 코드 전부 (Poker/Game/UI)
        ↑
Assembly-CSharp-Editor    ← Editor/ 폴더 밑. EditMode 테스트
```

`Assembly-CSharp-Editor`는 `Assembly-CSharp`를 자동으로 참조하므로 테스트가 게임 코드를 볼 수 있다. 에디터에서 폴더만 만들면 되고 따로 설정할 것이 없다.

### 레이어는 폴더와 네임스페이스로만 나눈다

```
PokerDefense.Poker      ← 포커 규칙 전용
        ↑
PokerDefense.Game       ← 런타임 전체 (흐름/보드/유닛/적/데이터 SO)
        ↑
PokerDefense.UI         ← 카드 UI, HUD, 팝업
```

- `Poker`는 `Game`을 모르고, `Game`은 `UI`를 모른다(UI가 `Game`의 이벤트를 구독한다).
- **이 방향을 컴파일러가 강제하지 않는다.** 한 어셈블리 안이라 어느 쪽이든 서로를 참조할 수 있다. 오직 관례로 지킨다.

### 관례로 지킬 것

- **거꾸로 참조하지 않는다.** `Poker` 안에서 `PokerDefense.Game`이나 `PokerDefense.UI`를 `using`하지 않고, `Game` 안에서 `PokerDefense.UI`를 `using`하지 않는다.
- **카드 섞기에 `UnityEngine.Random`을 쓰지 않는다.** 전역 정적 상태라 인스턴스마다 시드를 줄 수 없고, 그러면 `Deck(int seed)`의 재현성 테스트가 성립하지 않는다. `System.Random`을 주입하는 방식을 유지한다.
- **`Poker`에 ScriptableObject나 MonoBehaviour를 두지 않는다.** 족보 → 유닛 매핑처럼 게임 밸런스에 속하는 것은 `Game`의 `HandUnitTable`이 맡는다.

컴파일러가 막아 주지 않으므로 이 세 가지가 유일한 방어선이다. 어겨도 빌드는 통과한다.

**테스트 폴더 이름은 정확히 `Editor`여야 한다.** 테스트 러너는 asmdef가 아니라 `nunit.framework`를 참조하는 어셈블리를 찾고, 그 어셈블리가 에디터 전용이면 EditMode 테스트로 분류하기 때문이다. `[UnityTest]`도 이 구성에서 동작한다(멀티스레드 수명 테스트 4개가 사용). PlayMode 테스트는 없다.

**개발 도구도 같은 자리에 둔다.** `Editor/` 밑은 빌드에 들어가지 않으므로 치트·검증 창을 여기 두면 출시 전에 뺄 것이 없다. 게임 코드에 진입점이 필요하면 **`#if UNITY_EDITOR`로 감싸 최소한만** 남긴다. 무엇을 소환할지, 어떤 카드가 어떤 족보인지처럼 도구가 알아야 하는 것은 모두 `Editor/`에 두고, 게임 코드는 "이대로 바꿔라"만 받는다.

### 폴더 구조

## 3. 포커 코어 (`PokerDefense.Poker`)

### 3.1 카드

```csharp
public enum Suit  { Spade, Heart, Diamond, Club }        // 4
public enum Rank  { Two = 2, ..., Ten = 10, Jack, Queen, King, Ace = 14 }  // 13

public readonly struct Card { public readonly Suit Suit; public readonly Rank Rank; }
```

- A는 `Ace = 14`로 두고, 백스트레이트(A-2-3-4-5)를 판정할 때만 1로 본다. 조커 카드는 없으므로 52장이다.

### 3.2 덱

```csharp
public sealed class Deck
{
    public Deck(int seed);      // System.Random에 시드를 넣어 테스트를 재현할 수 있게 한다
    public Card Draw();
    public int Remaining { get; }
}
```

**설계 결정: 덱은 라운드마다 새로 섞는다.** 덱을 라운드 사이에 이어 쓰면 카드 카운팅이라는 전략이 생기지만, 후반에 덱이 떨어졌을 때의 처리나 리셋 시점 같은 규칙이 따라붙는다. 지금은 라운드마다 독립적인 쪽이 단순하다. 교체 카드는 같은 덱에서 뽑으므로 **한 라운드 안에서는 같은 카드가 두 번 나오지 않는다.**

### 3.3 족보 판정

```csharp
public enum HandCategory
{
    HighCard, OnePair, TwoPair, ThreeOfAKind,
    Straight, Flush, FullHouse, FourOfAKind, StraightFlush,
    // 특수 (기본 족보의 하위 경우를 따로 떼어 낸 것)
    BackStraight,        // A-2-3-4-5
    Mountain,            // A-K-Q-J-10
    BackStraightFlush,   // A-2-3-4-5 같은 무늬
    RoyalStraightFlush,  // A-K-Q-J-10 같은 무늬
}

public readonly struct HandResult
{
    public readonly HandCategory Category;
    public readonly IReadOnlyList<Card> KeyCards;   // 연출용 강조 카드 (페어 2장 등)
}

public static class HandEvaluator
{
    public static HandResult Evaluate(IReadOnlyList<Card> five);
}
```

**주의: `HandCategory`의 enum 순서를 "강함"으로 쓰지 않는다.** 백스트레이트는 정통 포커에서 가장 약한 스트레이트지만 이 게임에서는 특수 유닛을 준다. 즉 **판정 결과(Category)와 보상의 세기(유닛)는 별개**이며, 둘을 잇는 것은 코드가 아니라 데이터 테이블(`HandUnitTable`)이다. 코드를 고치지 않고 밸런스를 바꾸기 위해서다.

족보끼리 비교해야 할 때(결과 화면의 "최고 족보" 등)는 enum 값 대신 `HandRarity.RankOf`를 쓴다. 나올 확률로 정해지는 포커의 사실이라 Poker에 두며, 이것도 보상 세기와는 별개다.

**참고 — 처음 5장을 뽑았을 때 각 족보가 나올 확률** (밸런싱 출발점):

| 족보 | 확률 |
|---|---|
| 하이카드 | 50.1% |
| 원페어 | 42.3% |
| 투페어 | 4.75% |
| 트리플 | 2.11% |
| 스트레이트(마운틴·백스 제외) | 0.31% |
| 플러시 | 0.197% |
| 풀하우스 | 0.144% |
| 마운틴 / 백스트레이트 | 각 0.039% |
| 포카드 | 0.024% |
| 스트레이트 플러시(특수 제외) | 0.00123% |
| 로열 / 백스트레이트 플러시 | 각 0.000154% |

→ **90% 이상이 하이카드와 원페어다.** 교체로 이 쏠림이 조금 완화되지만, 기본적으로는 낮은 등급 유닛 위주로 전개된다. 이 표는 처음 뽑은 5장 기준이다. 일반 교체와 선택 교체를 거친 뒤 확정되는 족보 분포는 따로 측정해야 한다(§9.3).

## 4. 데이터 (ScriptableObject)

수치는 모두 여기로 뺀다. 코드에 밸런스 값을 하드코딩하지 않는다.

| SO | 필드 |
|---|---|
| `UnitDefinition` | id, 표시명, 공격력, 공격속도, 사거리, 성급 배수(★1/★2/★3), 공격 패턴과 패턴 수치(Multi 타겟 수 / Splash 반경 / Pierce 관통 길이), **방향별 아트 4장**(§10.4) |
| `HandUnitTable` | `HandCategory → UnitDefinition` 매핑 (전역 에셋 1개) |
| `EnemyDefinition` | id, 표시명, 대체 색, 최대 HP, 이동속도, 타입, 방향별 아트 4장, 표시 배율(`visualScale`) |
| `WaveDefinition` | 스폰 목록(적, 수량, 간격, 시작 지연), 제한시간, 웨이브 번호, Joker 보상 |
| `StageDefinition` | `WaveDefinition` 순서 목록, 시작 라이프, 웨이브당 라이프 피해 상한 |
| `CardVisualSet` | 손패 카드 스프라이트 묶음 (전역 에셋 1개). 테두리·강조 + 무늬 4장. **수치가 아니라 표시용**이다 — `RoundScreen`이 `CardView` 5장에 넘겨준다(§10.4의 카드 아트) |

**아직 넣지 않은 필드가 있다.** 쓰지 않는 필드를 미리 두면 추측으로 짠 코드가 된다.

- **아트가 없는 적은 대체 색으로 그린다.** 적 7종 모두 아트를 갖췄으므로(2026-08-27 기준 그런트·러너·스웜·브루트·레이스·베히모스·아바돈) 지금은 이 대체 경로를 쓰지 않는다. 다만 유닛과 달리 코드(`EnemyDefinition.PlaceholderColor`, `CombatScreen`의 아트 없음 분기)는 남겨 뒀다. 새 적을 추가하고 아트를 아직 붙이지 않았을 때를 대비해서다. 네 방향 아트가 다 있는 적만 아트로 그린다. **유닛은 13종 모두 아트가 있어 이 대체 경로를 아예 없앴다.** 아트가 없으면 콘솔 경고만 남긴다(2026-08-24).
- **투사체 프리팹은 없다.** 공격은 여전히 즉시 명중이다(§5.5).
- **처치 보상 필드는 없다.** 적을 잡아도 재화가 없다. Chip 경제 전체를 제거했다(§9.2).

## 5. 전투 (`Combat` 단계)

### 5.1 보드

- 가운데 **5열 × 3행 = 15칸** 격자. 한 칸에 유닛 하나.
- 적은 격자를 둘러싼 **고정 트랙**을 돈다. 유닛은 사거리에 들어온 적을 자동으로 공격한다.
- `GridBoard`가 칸의 점유 상태와 배치·합치기 규칙을 가진다. 칸은 `UnitInstance[15]` 배열이고 인덱스로만 다룬다.
- 유닛과 적은 서로를 직접 찾지 않고 살아 있는 적 목록으로 조회한다. 매 프레임 `FindObjectsOfType`를 부르지 않기 위해서다. 이 목록은 `CombatContext`가 직접 들고 있으며 별도 클래스로 빼지 않는다.

**보드는 월드 공간에 둔다.** 카드 UI와 HUD만 uGUI다. 적이 월드를 이동하고 유닛이 사거리로 조준하므로, 보드를 캔버스에 두면 사거리를 픽셀로 다뤄야 하고 URP 2D 렌더러, 2D 물리, 스프라이트 도구를 쓸 수 없다.

칸 클릭은 `Pointer` → `ScreenToWorldPoint` → `Physics2D.OverlapPoint`로 잡는다. 카드 UI 위를 누른 경우는 `EventSystem.IsPointerOverGameObject()`로 거른다. 누를 수 없는 칸은 `hitbox.enabled = false`로 검사에서 뺀다.

### 5.2 합치기

**설계 결정: 합치면 등급이 오르는 게 아니라 "성급(★)"이 오른다.**
같은 `UnitDefinition`, 같은 성급 유닛 2기를 합치면 그 유닛의 ★+1이 된다(최대 ★3). 스탯은 `UnitDefinition`의 성급 배수를 적용한다.

"같은 등급 2기 → 윗등급 1기"도 생각해 볼 수 있지만, 그러면 *하이카드 2기 = 원페어 1기*가 되어 족보를 맞춘 가치가 흐려진다. 족보(유닛 종류)와 합치기(성급)를 서로 독립된 축으로 두는 편이 낫다.

**합치는 경로는 두 가지이고, 둘 다 있어야 한다.**

1. **소환 유닛 → 보드**: 배치할 때 같은 유닛·같은 성급이 있는 칸을 고르면 합쳐진다.
2. **보드 → 보드**: 이미 놓인 두 유닛을 합친다(`GridBoard.TryMergeSlots`). 재료가 된 칸은 비워진다.

2번이 없으면 **★3에 도달할 수 없다.** 소환되는 유닛은 항상 ★1이라 ★2에 얹을 수 없고, 보드 위의 ★2 두 기를 합칠 방법이 없어지기 때문이다. 화면에서는 유닛을 눌러 고르고, 합칠 상대를 눌러 합친다.

성급은 공격력과 공격속도에만 곱하고 **사거리에는 곱하지 않는다.** 성급으로 사거리까지 늘어나면 배치 위치를 고르는 의미가 줄어든다.

### 5.2.1 승급권(Joker) — 희귀 유닛을 키우는 보조 수단

**Joker는 아무 유닛의 성급을 한 단계 올린다.** 같은 유닛이 없어도 된다.

- 얻는 곳: **10·20·30·40웨이브 보스에서 하나씩.** 한 스테이지에 최대 4개다. 50웨이브는 게임이 끝나므로 주지 않는다. (2026-08-23, 5·10·15·20웨이브 4회에서 변경 — [HISTORY.md](HISTORY.md))
- ★1 → ★2, ★2 → ★3. ★3에는 쓸 수 없다.

포카드가 나올 확률은 0.024%, 로열 스트레이트 플러시는 0.000154%다. ★3을 만들려면 같은 유닛이 4기 필요하므로 중복 소환만으로는 도달할 수 없고, **희귀 족보를 뽑은 기쁨이 "어차피 못 키우는 ★1"로 끝난다.** Joker가 이 빈틈을 메운다.

승급권은 보스를 클리어해야 받으며, 몇 개를 주는지는 웨이브 에셋의 JokerReward가 정한다. 예전 20웨이브 기준 공급량을 지금 50웨이브의 고정값으로 쓰지 않는다.

Joker를 어디에 쓸지도 하나의 선택이 된다. 지금 주력인 원페어 ★2를 ★3으로 올릴지, 방금 뜬 풀하우스를 ★2로 올려 오래 쓸지.

### 5.3 트랙과 적 이동

**트랙은 닫힌 고리다.** 적은 출구로 빠져나가지 않고 죽을 때까지 계속 돈다. §5.4에서 보듯 라이프는 "적이 새어 나갔을 때"가 아니라 "제한시간이 끝났을 때 남은 적 수만큼" 깎이기 때문이다. 일반적인 타워 디펜스와 다른 점이다.

- **경로 지점을 씬 오브젝트로 두지 않는다.** 격자를 둘러싼 사각형 고리라서 `GridBoard`가 격자 크기로 계산하면 된다. 씬에 점을 찍어 관리할 이유가 없다.
- **적 위치는 트랙 위 진행도(0~1) 하나로 나타낸다.** 월드 좌표는 화면에 그릴 때만 계산한다. 그래서 상태가 순수 C#에 머물고, "가장 앞선 적"도 진행도 비교 한 번으로 찾는다.

### 5.4 클리어 판정

- 제한시간 안에 웨이브를 전멸시키면 클리어하고 다음 라운드로 간다. **제한시간이 다 되기를 기다리지 않고, 마지막 적이 죽는 순간 넘어간다.**
- 시간이 다 되면 남은 적 수만큼 라이프가 깎인다. 라이프가 0이 되면 `GameOver`다.
- 남은 적은 다음 웨이브로 넘기지 않고 없앤다. 적이 쌓여 점점 더 불리해지는 악순환을 막기 위해서다.

**웨이브는 스폰 일정이라서, "화면이 비었다"와 "웨이브가 끝났다"가 다르다.** 보이는 적을 다 잡아도 아직 나오지 않은 적이 있으면 그 스폰까지 기다린다. 스폰 간격이 곧 난이도라 남은 스폰을 앞당기지 않는다. 대신 **그 사이에 HUD가 "다음 적까지 n초"를 보여준다.** 그렇지 않으면 게임이 멈춘 것처럼 보인다.

**한 웨이브에서 잃는 라이프에는 상한이 있다.**

```
LifeDamage = 보스가 남았으면 상한, 아니면 Min(RemainingEnemies, 상한)
```

**시작 라이프 20, 웨이브당 상한 3**이다(M12 Phase 6, 2026-09-02에 12/5에서 20/3으로). 결과가 클리어(피해 0)와 시간 초과(피해 1~상한) 둘로만 갈리고 중간이 없어서, 보드가 난이도 곡선에 밀리기 시작하면 상한 5로는 3웨이브 만에 게임오버였다. 시뮬레이션에서 "라이프 17로 클리어"와 "W32 전멸"이 같은 곡선에서 함께 나왔다. 상한 3과 라이프 20은 밀리는 구간에서 웨이브마다 약 3씩 천천히 깎이게 해서 "간신히 버티는" 구간을 만든다. 그래도 덱 운에 따라 보드 차이가 커서 완전히 잡히지는 않았다(HISTORY 2026-09-02).

반대로 **보스는 한 기만 남아도 상한만큼 깎는다.** 남은 수로만 세면 보스 웨이브를 실패해도 라이프 1만 잃어 보스가 벽 역할을 못 한다.

상한 값은 `StageDefinition`에 있고, 판정은 `StageContext.LifeDamageFor` 한 곳에서만 한다. 화면 표시도 같은 함수를 부른다. 두 곳에서 따로 계산하면 "12마리 남음, 라이프 -12"처럼 표시와 실제가 어긋난다.

### 5.5 타겟팅과 공격

- **겨냥하는 대상은 언제나 사거리 안에서 가장 앞선 적** 하나다. 패턴(§10.1)은 그 한 발이 **몇 기를 함께 때리는지**만 정한다. 대상을 고르는 규칙이 유닛마다 다르면 "왜 저기를 쐈는지" 알아볼 수 없다.
- **공격은 즉시 명중이다.** 투사체를 쓰면 비행 시간과 빗나감 처리가 따라오는데, 클리어 판정과는 관계가 없다. 연출 단계에서 붙인다.
- 성급 배수는 공격력과 공격속도에 곱하고 **사거리와 패턴 수치에는 곱하지 않는다**(§5.2). 성급으로 범위까지 늘면 배치 위치를 고르는 의미가 줄어든다는 같은 이유다.
- **한 발의 피해는 맞는 적의 수와 상관없이 공격력 그대로다.** 나눠 주면 Multi와 Splash가 단일 공격과 같아져 패턴의 의미가 사라진다. 대신 이런 유닛은 단일 대상 DPS를 낮게 잡는다.

### 5.6 시뮬레이션 방식

PvE 전용이므로 결정론적 고정 틱을 쓰지 않는다. 일반적인 `Update` + `deltaTime`으로 충분하다. (나중에 PvP를 붙인다면 이 결정을 다시 봐야 하며, 영향 범위는 `Units/`와 `Enemies/`로 한정된다.)

**단, `deltaTime`은 인자로 받는다.**

```csharp
public sealed class CombatContext          // 순수 C#. MonoBehaviour가 아니다
{
    public void Tick(float deltaTime);     // Update()에서 Time.deltaTime을 넘긴다
    public CombatOutcome Outcome { get; }  // InProgress / Cleared / TimedOut
    public int RemainingEnemies { get; }
}
```

고정 틱을 강제하지 않으니 위 결정과 부딪히지 않으면서, 테스트에서 `Tick(0.1f)`를 원하는 만큼 돌려 전투 한 판을 통째로 시뮬레이션할 수 있다. 포커 코어, 라운드, 보드도 같은 방식이다.

## 7. 열린 이슈

- 선택 교체를 이해하는지, 목표 안내가 쓸모 있는지는 사람이 직접 플레이해 봐야 알 수 있다.
- 랜덤 소환을 없애면서 유닛 공급이 손패당 1기로 줄었다. 초반 생존, 합치기 속도, 희귀 유닛 성장, 50웨이브 전체 난이도를 다시 측정해야 한다.
- Rapid 역할이 상대적으로 쓸모 있는지, 좁은 화면의 상세 정보와 트랙·보드가 잘 읽히는지는 계속 본다. 예전 배치 구조에서 잰 사거리 커버율은 새 트랙에서 다시 잰다.
- TMP 폰트 임포터의 일관성 오류가 남아 있다. 최근 빌드는 성공했지만 기술 부채로 추적한다.
- 카드 무늬·숫자별 유닛 능력, 경제 복원, 메타 성장은 지금 범위가 아니다.

## 8. 현재 마일스톤

M0~M12는 개발 이력이다. 삭제한 상점을 다시 완성해야 할 작업으로 보지 않는다. 지금의 손패 중심 구조 개편은 코드·씬 반영과 EditMode 검증을 마쳤다. 다음은 정상 플레이로 재미와 밸런스 기준을 재고, 기기에서 UX를 확인하고, 그다음 저장·이어하기를 만드는 것이다. 정확한 순서와 완료 기준은 POLISH.md, 검증 범위는 HANDOFF.md를 따른다.

## 9. 스테이지와 손패 선택

### 9.1 일반 교체와 선택 교체

일반 교체는 자리마다 한 번이고, 여러 번에 나눠 쓸 수 있다. 비용도, 쓰지 않았을 때의 보상도 없다. **선택 교체는 손패마다 한 번** 주어지며, 일반 교체했던 자리 하나에 후보 3장 중 한 장을 넣는다. 후보를 공개하기 전에는 무료로 취소할 수 있고, 공개한 뒤에는 반드시 한 장을 골라야 한다. 쓰지 않은 횟수는 다음 손패로 넘어가지 않는다.

### 9.2 Chip 제거

Chip, 유지 보너스, 판매 수입, 구매, 랜덤 소환 비용 API와 EconomyDefinition 에셋을 모두 없앴다. 숫자만 0으로 만든 임시 상태가 아니다. 손패를 확정하면 곧바로 유닛이 소환되고, 경제 정산 단계는 없다.

### 9.3 소환 수

라운드마다 손패로 유닛 1기를 소환한다. 따로 랜덤 소환은 없다. 보스 보상 승급권은 같은 유닛을 다시 얻기 어려운 희귀 유닛을 키우는 수단으로 유지한다. 랜덤 소환이 있던 시절의 밸런스 측정값은 새 루프에 적용하지 않는다.

### 9.4 보드에서 할 수 있는 것

- 빈 칸 배치, 같은 유닛·같은 성급 합치기, 이동, 자리 맞바꾸기는 그대로 있다.
- 새 유닛을 다른 유닛이 있는 칸에 놓으면, 퇴장할 유닛과 새 유닛을 보여주는 확인 창이 뜬다. 취소하면 아무것도 바뀌지 않는다. 확인하면 기존 유닛을 없애고 새 유닛을 놓는다. 합칠 수 있는 조합이면 교체하지 않고 합친다.
- 15칸이 모두 차도 교체로 계속 진행할 수 있다. 소환 포기와 선택한 유닛의 퇴장도 따로 확인을 거친 뒤 실행하며, 되돌려 받는 재화는 없다.
- 확인 창이 떠 있는 동안에는 진행과 뒤쪽 입력을 멈춘다. 확인하는 사이 대상이 바뀌었다면 엉뚱한 유닛을 지우지 않는다.

### 9.5 50웨이브 구성

2026-08-23에 20웨이브를 50웨이브로 늘렸다("중반 웨이브가 위협적이지 않다"는 진단에 대한 대응). 1~19웨이브는 그대로 두고 21~50을 새로 만들었다. 보스 주기도 5에서 10으로 늘어나, Act 5개가 각각 10웨이브(일반 9 + 보스 1)로 정리됐다.

**M12 Phase 6(2026-09-02)에 11~50웨이브의 적 수를 전부 다시 맞췄다.** 50웨이브로 늘린 뒤 밸런스를 다시 검증하지 못해 난이도 곡선이 망가져 있었기 때문이다(W11→12에서 3.2배로 뛰는 절벽, 보스 웨이브 뒤의 톱니 모양, Brute가 14마리에서 112마리로 폭증). 아래 표의 Act 구조, 적 종류, 보스 수는 그대로 두고, 각 웨이브의 적 수만 초당 필요한 화력 곡선(W11~30은 62→470, W31~49는 490→740, W50은 약 400)에 맞춰 다시 계산했다. 시뮬레이션 결과와 아직 남은 편차는 [HISTORY.md](HISTORY.md) 2026-09-02에 있다.

### 9.6 결과 화면

져도 무엇을 해냈는지 보여준다. 메타 성장 없이 "지난번보다 잘했다"를 느끼게 하는 유일한 장치다.

도달 웨이브, 최고 족보, 최고 유닛, 총 소환 수, 남은 라이프를 보여주고, 클리어했다면 클리어 시간도 보여준다. Chip 사용 통계는 없앴다.

- **최고 족보는 `HandRarity`로 고른다**(§3.3). enum 순서로 고르면 백스트레이트가 스트레이트보다 낮게 잡힌다.
- **최고 유닛은 DPS(공격력 × 공격속도)로 고른다.** 윗족보 유닛이 모든 면에서 아랫족보보다 낫지는 않으므로(§10.2) 성급만으로도, 족보만으로도 정할 수 없다.
- 이 기록은 규칙에 관여하지 않으므로 `StageContext`가 아니라 `RunStats`가 따로 갖는다.

**재시작은 씬을 다시 불러온다.** 상태를 손으로 되돌리면 새 상태가 생길 때마다 하나씩 빠뜨리게 된다.

## 10. 유닛 역할과 적 (M8)

### 10.1 공격 패턴 5종

유닛 13종이 **저마다 다른 시스템을 쓰지 않는다.** 패턴 5개를 나눠 쓴다.

| 패턴 | 내용 | 대상 선정 | 데이터 |
|---|---|---|---|
| Rapid | 빠른 단일 공격 | 타겟 1기 | — |
| Heavy | 느리고 강한 단일 공격 | 타겟 1기 | — |
| Multi | 여러 적 동시 공격 | 사거리 안에서, 첫 타겟으로부터 `multiSpread` 거리 안의 적을 앞선 순으로 N기 | 타겟 수 + 타겟 사이 최대 거리 |
| Splash | 좁은 범위 공격 | 착탄 지점 반경 안 전부 | 반경 |
| Pierce | 진행 방향으로 관통 | 타겟에서 **트랙 뒤쪽으로** 길이 L 안 전부 | 관통 길이 |

감속·중독·기절 같은 상태이상은 넣지 않는다.

**Rapid와 Heavy는 대상을 고르는 방식이 같다.** 다른 것은 공격력과 공격속도의 배분뿐인데, 그것만으로 역할이 갈린다. 이유는 **남는 피해(오버킬)** 다. HP 25짜리 잔챙이에게 Heavy가 한 발에 100을 넣으면 75가 버려지지만, DPS가 같은 Rapid는 버리는 게 없다. 반대로 HP가 높은 단일 적에게는 손해가 없다(오히려 첫 발에 화력이 몰려 한 주기 앞선다). 상성 배수 같은 규칙을 따로 두지 않아도 이 차이가 §10.5의 유불리를 그대로 만든다.

**Pierce를 월드 직선이 아니라 트랙 기준으로 재는 이유:** 적 위치는 설계상 진행도 하나다(§5.3). 트랙을 따라 재면 "앞뒤"가 이미 정해져 있고, Splash(반경)와 모양도 확실히 달라진다. 월드 직선으로 만들면 좌표를 다시 들여와야 하는데 얻는 것이 없다.

**Splash는 유닛 사거리 밖의 적도 휘말리게 한다.** 기준이 착탄 지점이기 때문이다. 사거리는 "누구를 겨냥하는가"만 정한다.

**Multi는 사거리만으로는 부족하다.** 사거리가 넓은 유닛(예: 4 = 트랙의 66%)이 "사거리 안에서 앞선 순 N기"로만 고르면, 트랙 반대편 적까지 한 발에 맞는다. 화면에서 멀리 떨어진 적들이 동시에 맞는 것처럼 보인다. 그래서 Multi는 **먼저 고른 첫 타겟에서 `multiSpread` 거리 안에 있는 적만** 나머지 후보로 삼고, 그중 앞선 순으로 N기를 고른다. 사거리는 "쏠 수 있는가"만 정하고, `multiSpread`는 "얼마나 뭉쳐 있어야 같이 맞는가"를 정한다.

### 10.2 족보별 유닛

**설계 원칙: 유닛이 족보를 기억하게 해 준다.** 이름과 실루엣에 족보의 구조가 그대로 드러나면 플레이어는 외우지 않고 알아본다. 그래서 13종을 서로 다른 판타지 캐릭터로 만들지 않고 **하나의 카드 군단**으로 통일한다.

| 족보 | 이름 | 구조 | 역할 |
|---|---|---|---|
| 하이카드 | 하이카드 스카우트 | 카드 1장 | Rapid — 빠른 단일 |
| 원페어 | 원페어 건슬링어 | **2** (쌍권총) | Rapid — 2연타 |
| 투페어 | 투페어 트윈레인저 | **2+2** (양팔에 2연장) | Multi — 2타겟 |
| 트리플 | 트리플 마크스맨 | **3** (총구 3개) | Heavy — 3발을 모아 한 발 |
| 백스트레이트 | 백스트레이트 에이스 | A→2→3→4→5 계단 | Rapid — 초고속 연사 |
| 스트레이트 | 스트레이트 롱바렐 | **무늬가 섞인** 카드 5장이 박힌 아주 긴 총열 1정 | Pierce — 직선 관통 |
| 마운틴 | 마운틴 킹 | ▲ 산 모양 왕관, 꼭대기에 A | Heavy — 보스 특화 |
| 플러시 | 플러시 보머 | 같은 무늬 반복 | Splash — 범위 |
| 풀하우스 | 풀하우스 배터리 | **3+2** (주포 3 + 보조포 2) | Multi — 3타겟 연사 |
| 포카드 | 포카드 쿼드캐논 | **4** (4연장 중포) | Heavy — 초고화력 저속 |
| 백스트레이트 플러시 | 백스트레이트 플러시 템페스트 | 같은 무늬 A-5가 원을 그리며 회전 | Multi — 빠른 다중 |
| 스트레이트 플러시 | 스트레이트 플러시 레일거너 | **같은 무늬** 5장 일렬 = 레일 | Pierce — 강력한 관통 |
| 로열 스트레이트 플러시 | 로열 스트레이트 플러시 소버린 | 10-J-Q-K-A 왕좌, 왕관 | Multi — 초고속 다중 (Splash에서 변경, [HISTORY](HISTORY.md) 참고) |

**핵심은 굵게 표시한 다섯이다.** 2 / 2+2 / 3 / 3+2 / 4를 실루엣으로 읽을 수 있어서 이름을 몰라도 무엇인지 알 수 있다.

- **스트레이트와 스트레이트 플러시는 무늬가 통일됐는지로 구분한다.** 둘 다 *5장 일렬*이고 둘 다 Pierce라 이것 말고 가를 기준이 없다. 롱바렐은 무늬가 섞이고 레일거너는 하나로 통일된다. **족보의 정의 그대로다.** 크기로도 구분해서 롱바렐은 가는 선, 레일거너는 굵은 기둥이다.
- **원페어와 투페어를 눈으로 구분한다.** 건슬링어는 `1×2`, 트윈레인저는 `2×2`다. 트윈레인저가 한 대상에게 4발을 쏘면 포카드처럼 보이므로, **적 둘에게 한 쌍씩** 쏜다. 연출에서도 Pair + Pair가 그대로 보인다.
- **마크스맨은 3연타가 아니라 3발을 모아 한 발로 쏜다.** 3연타로 만들면 건슬링어와 역할이 겹친다. 셋이 하나로 모이는 연출이 Three of a Kind와도 맞고 Heavy 역할도 지킨다.
- **배터리는 실루엣만 3+2이고 판정은 Multi다.** 주포 3문 → 보조포 2문 순으로 무작위로 쏘되(총구 5개), 한 발이 서로 다른 적 3기를 때린다. 처음에는 Splash였지만, 초당 2.5번 터지는 폭발이 "연사"가 아니라 "난사"로 보여서(총구는 하나씩 반짝이는데 화면 저편에서 큰 폭발이 그만큼 자주 터짐) Multi로 바꿨다. 폭발만 사라지고 총구 5개 무작위 발사는 그대로다. 소버린도 나중에 같은 이유로 Splash에서 Multi로 바꿨다.

**윗족보 유닛이 모든 면에서 아랫족보보다 낫지는 않다.** 쿼드캐논 ★1은 보스와 Tank에 강하지만 잔챙이 떼에는 비효율적이고, 스카우트 ★3은 빠른 적을 처리하기에 아주 좋다. 그래서 후반에도 낮은 족보 유닛을 합쳐 쓸 가치가 남는다.

### 10.3 슬롯에 두는 것과 이름 규칙

**슬롯에는 무엇인지와 몇 성인지만 둔다. 수치는 모두 상세 정보로 뺀다.**

| 자리 | 담는 것 |
|---|---|
| 보드 슬롯 | 유닛 아트 + 성급(★). **그게 전부다** |
| 상세 (유닛을 고르면) | 이름, 공격 패턴, 공격력, 공격속도, DPS, 사거리 |
| 소환 안내 | `확정하면 원페어 건슬링어 소환` — 족보와 유닛은 이 순간에만 연결되면 된다 |

**슬롯은 더 키울 수 없다.** 트랙이 이미 화면 가로 7.425 월드 유닛 중 6.8을 쓴다. 5열 세로 화면에서 145px이 최대이고, 더 키우려면 열을 줄이거나 트랙을 잘라야 한다. **그 145px에 이름, 성급, 공격력, 공격속도를 다 넣으면 아트가 들어갈 자리가 없다.** 그래서 정보를 두 층으로 나눈다. 슬롯은 알아보는 곳이고, 상세는 비교하는 곳이다.

**아트가 들어오기 전에는 이름이 아트를 대신했다.** 13종 아트가 다 갖춰진 뒤(2026-08-24) 이름 라벨 대체 경로를 없앴다. 이제 슬롯은 아트만 그리고, 아트가 없는 예외 상황은 콘솔 경고로만 남긴다.

**상세는 모달 창이 아니다.** 전투 중에도 배치를 고치므로(§1), 보드를 덮으면 적이 안 보이고 이동·합치기 대상 칸을 누를 수도 없다. 화면에 빈 자리가 없어서 **기존 안내 문구 자리를 두 줄짜리 정보 블록으로 바꿨다.** 새로 가리는 것이 없다.

**공격력, 공격속도, DPS를 셋 다 보여준다.** 하나로 합칠 수 없어서다. 패턴마다 배분이 크게 다른데(§10.1), DPS만 보면 남는 피해가 안 보이고, 공격력만 보면 발사 주기가 사라진다.

**이름은 하나뿐이다.** `원페어 건슬링어`처럼 족보와 유닛 이름을 붙여 쓴다. 슬롯에서 이름을 빼면서 짧은 이름이 필요한 자리가 없어졌고, **유닛 하나에 이름이 둘이면 외울 것만 늘어난다**(§0). 길이 제한도 없앴다.

**단, 폭 400px 버튼에는 들어가지 않는다.** 확정 버튼에는 `확정 +4`만 쓰고, 소환 안내는 폭이 넓은 문구 줄이 맡는다.

**유닛 이름은 한글로 쓴다.** UI 전체가 한글이고 족보 이름도 `원페어`, `트리플`이다. 여기에 영문 `Pair Gunslinger`를 붙이면 플레이어가 *원페어 = One Pair = Pair*라는 번역을 한 번 거쳐야 해서, **이름으로 족보를 기억하게 하려던 목적이 오히려 깨진다.**

**백스트레이트 계열에 "Wheel"을 쓰지 않는다.** A-2-3-4-5를 휠이라 부르는 것은 영어권 관습이고, 한국식 포커에서는 백스트레이트다(§3.3). 한국 플레이어에게는 아무것도 떠올리게 하지 못한다.

### 10.4 외형 규칙

- **카드 문양은 장식이지 능력이 아니다.** 유닛마다 고정된 심볼 하나를 쓰고, **실제 손패의 무늬에 따라 모습이 바뀌지 않는다.**
  **예외는 스트레이트와 스트레이트 플러시 둘뿐이다.** 이 둘은 무늬가 통일됐는지가 곧 족보라서, 롱바렐은 무늬를 섞고 레일거너는 통일한다. 그래도 무늬가 능력과 관련 있다는 오해는 생기지 않는다. *같은 무늬 = 플러시*는 속성이 아니라 포커 규칙이기 때문이다. 나머지 11종은 고정 심볼 하나를 지킨다. 카드 속성 시스템은 넣지 않기로 했으므로(§0) 외형이 그런 오해를 만들면 안 된다. 같은 이유로 하이카드 유닛에 A 카드를 붙이지 않는다. 카드 숫자가 성능과 관련 있는 것처럼 보이기 때문이다.
- **성급이 올라도 구조 숫자는 절대 바꾸지 않는다.** 건슬링어 ★3에게 총 4자루를 들리면 족보의 언어가 깨진다. **페어는 언제나 2, 트리플은 언제나 3, 쿼드는 언제나 4다.**
  성급은 갑옷 장식, 카드 오라, 무기 크기와 화려함, 이펙트 세기로만 나타낸다. 슬롯의 `★`가 이미 성급을 보여주므로 **구조는 실루엣, 성급은 별**로 두 축이 나뉜다.
- **소버린만 예외적으로 크게 만든다.** 13종 중 유일한 군주급이고, 처음 5장에서 나올 확률은 0.000154%다(교체를 거쳐 확정될 확률은 따로 측정해야 한다). 등장 연출은 과해도 된다.
  단 이 연출을 소버린 전용으로 만들면 **평생 한 번도 못 보는 플레이어가 생긴다.** 스트레이트 플러시 이상(합계 약 0.0015%)에 등급별로 3단계로 키우면 실제로 볼 일이 생긴다.

**유닛은 방향별 스프라이트 4장을 쓴다.** 적은 닫힌 트랙을 360도로 돌지만 유닛은 회전하지 않는다(§5.3). 정면 한 장만 두면 오른쪽 적을 쏠 때도 왼쪽을 겨눈 그림이 남는다. 아래(정면), 위(뒷면), 왼쪽, 오른쪽을 만들고, **`CombatContext`가 기록한 조준 방향**에 맞춰 바꿔 끼운다.

- 방향은 유닛을 키로 기록한다. 슬롯을 키로 쓰면 전투 중 이동할 때 어긋난다. 공격 쿨다운과 같은 이유다(§1).
- **좌우를 뒤집기로 대신하지 않는다.** 장수는 절반으로 줄지만 총을 든 손이 바뀐다.
- 방향 판정은 `|dx| > |dy|`로 좌우와 상하를 가르는 4분할이면 충분하다.
- 전투 중이 아니면 정면을 보게 한다. 배치 단계에서 유닛들이 제각각 다른 곳을 보고 있으면 이유를 알 수 없다.

**총구 화염은 방향마다 "총구 목록"으로 적는다.** 한 곳에만 띄우면 §10.2의 구조 숫자가 연출에서 사라진다. 쌍권총인데 늘 같은 손만 번쩍이면 총이 하나로 보인다.

좌표를 하나씩 들고 있다가 **세 번 한계에 부딪혀** 목록으로 바꿨다. 그때마다 표현할 수 없는 배치가 나왔다.

| 담지 못한 것 | 드러난 곳 | 오차 |
|---|---|---|
| 방향마다 무기 위치가 다르다 | 마크스맨은 총을 어깨에 메서 뒷면 총구가 등 한가운데가 아니다. 스카우트도 뒷면 권총이 오른쪽으로 벗어나 있었다 | 21.6px / 23px |
| 무기가 둘이다 | 건슬링어·트윈레인저 | — |
| **총구가 다섯 곳에 흩어져 있다** | 배터리는 주포 3문이 머리 위, 보조포 2문이 허리에 있어 **좌우를 뒤집으면 두 점이 한 자리로 겹친다** | 51px |

- **옆면 / 정면 / 뒷면 목록 세 개를 둔다.** 좌우만은 대칭으로 묶는다. 실측 차이가 대개 1.7~3.6px이라 나눌 가치가 없다.
  **단, 묶을 때는 좌우 실측값의 가운데를 써야 한다.** 보머는 왼쪽을 향한 무기가 오른쪽보다 짧게 그려져 좌우 차이가 5.5px이었고, 한쪽 값을 그대로 쓰면 반대쪽만 4.9px 어긋났다. 차이가 이보다 더 큰 시트가 들어오면 좌우를 나눌지 다시 본다.
- **총구가 하나인 유닛은 목록에 하나만 넣는다.** 따로 특별 취급하지 않는다.

**한 발에 모든 총구를 터뜨릴지 하나만 터뜨릴지는 무기 수가 아니라 §10.2의 공격 방식이 정한다.**

| 유닛 | 방식 | 이유 |
|---|---|---|
| 건슬링어 | 번갈아 | 한 대상을 2연타한다. 번갈아 쏴야 쌍권총으로 보인다 |
| 트윈레인저 | **동시** | **적 둘에게 한 쌍씩** 쏜다. 번갈아 쏘면 Pair + Pair가 사라진다 |
| 배터리 | **무작위** | 총구가 다섯이라 순서대로 돌면 기계적으로 보인다. 흩어져야 연사로 보인다 |

- **패턴에서 추측하지 않고 데이터로 받는다.** 무기가 둘이라고 모두 동시에 쏘는 것은 아니고, 같은 Multi라도 배터리는 동시가 아니다. 코드에 규칙을 박아 두면 셋 중 하나에서는 반드시 깨진다.
- **어느 총구가 쏠 차례인지는 전투가 센 발사 횟수로 정한다.** 무작위도 그 횟수를 섞어서 만든다. 화면 쪽에서 프레임마다 새로 뽑으면 화염이 0.06초 동안 떨린다. 조준 방향, 공격 쿨다운과 같은 이유로 **유닛을 키로** 기록한다.

**화염은 반동과 함께 커져야 한다.** 아트는 발끝을 기준점으로 커지는데 화염 좌표를 고정해 두면, **화염이 보이는 0.06초가 정확히 반동이 가장 큰 순간이라** 늘 어긋난 상태로만 보이고 그 사이 간격까지 변한다. 총구가 높이 있을수록 더 크게 벌어진다(마크스맨 7.6px).

**움직임은 프레임 애니메이션이 아니라 코드로 만든다.** 슬롯이 124px이라 프레임이 바뀌는 게 눈에 띄지 않고, 공격속도가 초당 0.4~6.75회로 넓게 퍼져 있어(성급 배수 포함) 가장 빠른 유닛은 한 발에 148ms다. 발사 반동과 대기 중 숨쉬기는 **크기 변화**로 준다. 총구가 카메라를 향해 있어서 화면에서 "뒤로 밀리는" 방향이 정의되지 않고, 위아래로 흔들면 점프하는 것처럼 보이기 때문이다.

실루엣과 VFX는 M11 아트 단계에서 만든다. 그때 §10.2 표가 그대로 제작 기준이 된다.

### 10.5 적 종류

특수 능력은 넣지 않는다. **HP, 이동속도, 수량만 바꿔도 역할이 갈린다.**

| 적 | 특징 | 유리한 유닛 |
|---|---|---|
| Normal | 기준 | — |
| Runner | HP 낮음, 빠름 | Rapid, Multi |
| Tank | HP 높음, 느림 | Heavy |
| Swarm | HP 매우 낮음, 떼로 나옴 | Splash, Multi |
| Boss | HP 매우 높음, 소수 | 단일 고화력 |

**`EnemyDefinition`(HP, 이동속도, 타입)으로 모두 표현된다.** 코드가 `EnemyType`으로 분기하는 곳은 라이프 피해 상한의 보스 예외(§5.4) 하나뿐이고, 나머지는 표시용이다. 보호막, 방어력, 회복, 순간이동 같은 장치는 넣지 않는다.

**적의 남은 HP는 체력 바로 보여준다.** M10까지는 스프라이트 색에 남은 HP 비율만큼 밝기를 곱했는데, 그건 적이 단색 사각형이라 가능했던 방식이다. M11에서 컬러 스프라이트가 들어오면 죽어 갈수록 검게 뭉개져 **"죽어 간다"가 아니라 "안 보인다"** 가 된다. 그래서 색 변화를 없애고 체력 바를 붙였다.

**`EnemyType`에 값을 추가할 때는 반드시 맨 뒤에 붙인다.** 기존 에셋이 이 enum을 정수로 저장하고 있어서, 중간에 끼워 넣으면 모든 적의 타입이 소리 없이 어긋난다.

**적 타입은 §10.1의 패턴이 생기기 전에는 의미가 없었다.** 타겟팅이 "사거리 안에서 가장 앞선 적" 한 가지뿐일 때는 어떤 적이 나와도 결국 "총 DPS가 충분한가"로 끝났다. 패턴이 생긴 지금은 빠른 적이 느린 발사 주기를 불리하게 만들고(Runner ↔ Heavy), 많은 수의 적이 남는 피해를 불리하게 만든다(Swarm ↔ Heavy).

손패를 직접 맞추는 루프로 바꾸면서 가격, 잔액, 보관을 관리해야 하는 상점을 뺐다. ShopOffer, ShopScreen, 보관 트레이와 관련 경제 테스트도 지웠다. 5라운드가 끝나도 바로 다음 손패로 이어진다.

## 14. 지금 추구하는 경험과 판단 기준

핵심 재미는 **필요한 족보를 직접 만들고, 그 유닛으로 보드를 키우는 것**이다. 교체를 참아서 재화를 모으는 동기를 없애고 손패 선택에 집중하게 했다. 일반 교체 뒤의 선택 교체는 매 손패 쓸 수 있는 핵심 보조 수단이다. 고른 자리를 바꿨을 때 나올 수 있는 족보와 확률은 정확히 계산해서 보여준다(§19). 다만 어느 자리가 최선인지 추천하거나, 가장 높은 족보를 자동으로 맞춰 주지는 않는다.

정상 플레이에서 원했던 족보와 실제로 확정한 족보, 선택 교체를 쓴 이유, 첫 합치기까지 걸린 라운드, 희귀 유닛의 기여, 막힌 웨이브, 준비 시간을 관찰한다. 예전 경제 시뮬레이션의 승률이나 ★3 개수 목표를 지금의 합격 기준으로 다시 쓰지 않는다. 수치는 현재 규칙으로 기준을 잰 뒤 한 번에 하나씩 바꾼다.

## 15. 현재 UI/UX 원칙과 참고한 근거

운빨존많겜을 참고해 검토하면서 가져온 원칙은 다섯 가지다. 단계마다 주요 버튼을 같은 자리에 두기, 실행하기 전에 결과를 미리 보여주기, 카드 상태를 눈으로 구분하기, 보드에서 목적지 표시하기, 독립된 안내 창.

- 하단 버튼은 **일반 교체 / 선택 교체 / 손패 확정** 순서로 고정한다. 선택 교체 버튼에는 쓸 수 있는 조건과 이번 손패에서 이미 썼는지를 표시한다.
- 손패 아래 패널은 카드를 1~4장 골랐을 때만 나타나고, 그 카드를 바꿨을 때 나올 수 있는 족보와 확률을 모두 보여준다(§19). 아무것도 고르지 않았거나 5장을 고르면 숨는다. 고르기 전에 족보를 추천하지 않고, 어느 자리가 최선인지도 알려주지 않는다.
- 선택 교체는 일반 교체한 자리 하나를 골라 후보를 공개한다. 공개 전에는 취소할 수 있고, 공개한 뒤에는 반드시 한 장을 골라야 한다. 각 후보로 바꾸면 어떤 족보·유닛이 되는지, 합칠 수 있는지 미리 보여준다.
- 보드에서 이동, 합치기, 자리 교환은 목적지에 무슨 일이 생길지 구분해 보여준다. 기존 유닛을 없애는 교체·퇴장과 이번 소환 포기는 따로 확인 창을 거친다. 취소하면 원래 상태 그대로다.
- 첫 손패, 첫 배치, 첫 합치기 기회의 안내는 런마다 한 번씩 뜨는 독립 창이다. 상점 안내는 없다. 핵심 규칙은 메뉴의 도움말에서 다시 읽을 수 있다.
- 창을 띄울 때는 뒤를 어둡게 가리고, 입력을 막고, 게임을 멈추는 것을 항상 함께 한다. 메뉴를 겹쳐 열었다 닫아도 아래 창이 아직 열려 있으면 멈춤을 풀지 않는다.
- 전투 전 위협·사거리 표시, 직전 전투 되돌아보기, 1.8초 결과 화면, 다음 Act 예고는 유지한다. Act 진행 바는 다시 넣지 않는다.

## 16. 남은 발전 과제

우선순위와 완료 기준은 [POLISH.md](POLISH.md)에서 관리한다. 먼저 지금 손패 루프를 이해하는지, 보드 공급량과 초반 난이도는 어떤지, 실기기에서 입력이 잘 되는지 확인한다. 목표 안내가 결정에 도움이 되는지, 선택 교체가 의미 없이 반복하는 의식처럼 느껴지지 않는지도 본다.

저장·이어하기는 **아직 없다.** 만들기 전에 무엇을 복구할지 경계를 먼저 정해야 한다. 손패, 남은 덱과 난수 상태, 일반 교체 잠금, 선택 교체의 사용 여부·공개된 후보·대상, 보드와 대기 유닛, 웨이브·라이프·승급권, 정산 상태를 함께 다뤄야 한다. 껐다 켰을 때 후보를 다시 뽑거나 보상을 두 번 받게 해서는 안 된다. RunJournal은 분석 로그이지 복원용 파일이 아니다.

무료 카드 선택 보상, 보관 슬롯, 덱빌딩, 장비, 메타 성장, 특전 복원, 무한 모드는 채택하지 않았거나 보류한 후보다. 마음대로 추가하지 않는다.

## 17. 전체 루프 구현 상태

- Boot → Title → Game, 새 게임, 공통 음량 옵션, 도움말, 일시정지, 포기 확인, 결과 뒤 재도전·타이틀 복귀를 구현했다. 옵션은 기기에 저장되지만 게임 진행은 저장되지 않는다.
- `TrackPath.Arena`가 적 판정과 화면 표시에 같은 위치·방향·길이를 준다. 배경과 보스가 시각적으로 맞는지는 실기기 마무리 때 확인한다.
- `RoundController.AssistMode`의 기본값은 ChooseThree(후보 3장 중 선택)다. Disabled와 RandomOne은 개발 중 비교용이며, 정식 채택을 기다리는 후보가 아니다.
- RunJournal은 `Application.persistentDataPath/RunJournals`에 기록한다. 지금 규칙의 식별자는 `hand-loop-v1`이며, 예전 경제 규칙의 로그와 섞지 않는다.
- 최근 구현 검증은 §18과 [HANDOFF.md](HANDOFF.md)를 따른다. 예전 테스트 241개와 상점 프로토타입 검증은 과거 기록이다.

## 18. 손패 중심 루프 구조 개편 (2026-09-13)

이 절과 §1, §9가 현재 규칙이다. §14~§17도 현재 기준으로 고쳤고, 예전 경제·상점·이월 기회 기획은 LEGACY_LOOP_PLAN.md에 과거 기록으로 분리했다.

- `RoundContext`가 선택 교체 1회의 상태와 후보를 가진다. StageContext에 횟수를 쌓아 두거나 채우는 API는 두지 않는다. 새 손패가 곧 새 기회다.
- `StageContext`는 라이프, 웨이브, 승급권을 맡고, `PlacementController`는 손패 소환과 배치·교체를 맡는다. 상점으로 넘어가는 전환과 Chip 획득 이벤트는 없앴다.
- `HandGoals`는 포커 층의 순수 계산이다. 아직 나오지 않은 카드와 바꿀 수 있는 자리를 보고, 한 장을 바꿨을 때 가능한 족보를 나열한다. 2026-09-15부터 이 계산은 화면에 연결돼 있지 않다(§19). `RoundContext.FindGoals`와 `HandLoopTests`는 남아 있지만 표시하지 않는다.
- `BoardDecisionScreen`은 없어질 유닛을 확인하는 창이다. 실제 교체는 GridBoard와 PlacementController가 검사하고 실행한다. 취소하면 상태와 소환 기회가 그대로 남는다.
- 결과 통계와 RunJournal에서 Chip·상점 항목을 지우고, 기록에 규칙 식별자 `hand-loop-v1`을 넣었다. 예전 경제 로그와 섞어 비교하지 않는다.
- 개발용 자동 플레이에서도 상점과 랜덤 소환 호출을 지우고 후보 선택을 쓰게 고쳤다. 자동 플레이의 전략과 승률은 실제 사람을 대표하지 않는다.
- 검증: 새 교체, 목표, 가득 찬 보드의 교체와 기존 포커·전투·라이프 테스트 201개 통과. 삭제한 기능의 테스트는 지웠으므로 예전 241개와 개수를 직접 비교하지 않는다.
- 난이도는 아직 확정하지 않았다. 유닛 공급이 줄어든 영향과 선택 교체로 족보가 좋아진 영향을 나눠서 실측해야 한다. 기존 웨이브 데이터는 비교 기준으로 남겨 두며, 밸런스가 맞는다고 보지 않는다.

## 19. 확률 정보 도입 (2026-09-15)

§14·§15·§18은 "확률이나 최선의 행동을 단정해 보여주지 않는다"를 원칙으로 삼았다. 사용자 판단으로 이 원칙을 좁혔다. **확률 자체는 정확히 보여주되, 어느 자리가 최선인지는 여전히 추천하지 않는다.**

- **이유.** 이 게임에서 포커의 재미는 "이 카드를 바꾸면 어떤 족보가 나올 확률이 높은가"를 직접 따져 보는 데 있다고 판단했다. 이는 정답을 대신 골라 주는 것과 다르다. 나올 수 있는 카드(아웃츠)를 세어 보여주는 것은 플레이어의 판단을 대신하지 않고, 판단할 재료를 준다. 반면 "이 자리가 최선입니다" 같은 추천은 판단 자체를 대신하므로 하지 않는다.
- `HandOdds`는 고른 자리(최대 4개, 2026-09-21까지는 3개)를 남은 덱에서 뽑을 수 있는 모든 조합으로 채워 보고, 나올 수 있는 족보 전부와 정확한 확률·경우의 수를 계산한다. `HandGoals`처럼 자리마다 따로 보지 않고, 실제로 한꺼번에 바꿀 조합을 그대로 평가한다.
- **일반 교체:** 카드를 1~4장 골랐을 때만 패널이 떠서 그 선택의 확률 분포를 보여준다("원페어 47%(22/47)" 형식, 희귀한 족보부터). 아무것도 고르지 않았거나 5장을 고르면 숨는다. 고르기 전에 족보를 추천하던 `HandGoalText`는 삭제했다.
- **선택 교체:** 대상 자리를 고르면 후보를 공개하기 전에 그 자리의 확률 분포를 보여준다. 실제 후보는 남은 덱에서 3장만 무작위로 뽑히므로(§9.1), 이 확률은 "이번에 뜰 3장"이 아니라 "남은 덱 전체" 기준이다. 문구에서 이 차이를 흐리지 않는다.
- 5자리 이상을 한꺼번에 고르면 조합 수가 급격히 늘어서(예: 5자리를 바꾸면 남은 덱 기준 약 150만 가지) 정확히 세지 않는다. 근삿값도 보여주지 않고 계산을 아예 하지 않는다. (2026-09-21, 병렬 계산을 도입한 뒤 측정해서 3에서 4로 올림 — §20)
- 검증: `HandOddsTests` 6개로 경우의 수, 확률, 조합 상한, 정렬을 확인했고 EditMode 207/207이 통과했다. 처음 배포할 때 패널을 104px에서 170px로 키웠다가 손패 카드 줄과 겹쳐서(사용자 스크린샷으로 확인), 고르기 전 안내를 없애면서 원래 크기(104px)로 되돌렸다.

## 20. 교체 확률의 비동기·병렬 계산 (2026-09-20)

§19의 확률 의미는 그대로다. 표시 상한은 2026-09-21에 3에서 4로 올랐다(아래 "상한 4장 확장"). 계산하는 동안 "계산 중" 문구를 보여주고, 계산이 끝나기를 기다리지 않고도 카드 선택·교체·확정을 할 수 있다. 선택이 바뀌면 이전 확률을 지운다. 선택 교체 창과 일반 교체 화면은 워커 하나를 같이 쓴다.

메인 스레드에서 `RoundContext.CaptureOdds`로 손패, 남은 덱, 고른 자리를 복사하면 `HandOddsWorker`가 계산한다. `RoundController.Update`가 끝났는지 확인해서 지금 요청의 결과만 UI에 넘긴다. 실행 중인 작업은 최대 1개, 대기 요청은 가장 최근 것 1개만 둔다. 취소돼서 중간까지만 센 집계는 보여주지 않는다. 족보 종류만 판정하는 경로와 기존 손패 판정이 같은 결과를 내는지는 테스트로 보장한다. 병렬 기준은 3으로, 교체 상한 4와 따로 정한다. 1~2장은 워커에서 순차로, 3~4장은 최대 2스레드 병렬로 계산하며, 논리 CPU가 하나면 순차로 돈다.

구조, 수명, 다시 측정하는 방법은 [THREADING_PLAN.md](THREADING_PLAN.md), 측정 결과와 검증 한계는 [THREADING_RESULTS.md](THREADING_RESULTS.md)에 있다. 게임이 끝난 뒤의 결과 제출과 랭킹은 [NETWORK.md](NETWORK.md)에 있다.

### 교체 확률 UI (2026-09-20)

- 일반·선택 교체 확률은 두 줄 요약으로 보여주고, `자세히 >`를 누르면 상세 창이 열린다. "높은 족보"는 `HandRarity`의 희귀도 기준이며, 전투에서 더 강하다는 뜻은 아니다.
- 상세 창(`HandOddsScreen`)은 높은 족보부터 가능한 결과, 확률 막대, 경우의 수를 스크롤로 보여주고, 지금 손패의 족보를 강조한다. 0보다 크지만 0.1% 미만인 확률은 `<0.1%`로 표시한다.
- 선택 교체의 분포는 남은 덱에서 한 장을 뽑았을 때 기준이다. 후보 3장 중에서 원하는 카드를 고를 확률과는 다르다.
- 상세 창을 열면 게임을 멈추고 입력을 막으며, 닫으면 이전 입력 상태로 돌려놓는다. 상세 창 위에 메뉴를 열 수 있다.
- 씬 재설치는 `Tools/Poker Defense/Update Hand Odds UI`로 한다(Game 씬만 갱신). 위젯과 참조는 에디터 코드가 만들고 직렬화한다.

### 상한 4장 확장 (2026-09-21)

4장까지 순차·병렬 계산 시간을 다시 잰 뒤 `HandOdds.MaxSlots`를 3에서 4로 올렸다. 측정값과 한계는 [THREADING_RESULTS.md](THREADING_RESULTS.md) "상한 4장 확장"에 있다. §19의 "5자리 이상은 계산하지 않는다" 규칙은 그대로이며, 경계만 4에서 5로 옮겨졌다.
