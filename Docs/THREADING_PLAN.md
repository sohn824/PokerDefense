# 멀티스레드 도입 설계 (2026-09-20)

상태: **멀티스레드 계산·UI 연결 구현, EditMode 219/219 통과**. HandOdds.MaxSlots는 측정 후 3에서 **4**로 올렸다(2026-09-21, 아래 "상한과 측정" 및 THREADING_RESULTS §"상한 4장 확장" 참조). TCP는 다음 단계 설계이며 미구현이다. 현행 규칙은 DESIGN §19~20, 측정·검증 범위는 [THREADING_RESULTS.md](THREADING_RESULTS.md)를 따른다.

## 목적과 범위

실제 확정 손패 한 번의 판정은 기존 동기 호출로 유지한다. 많은 조합을 열거하는 **교체 확률 계산 HandOdds**를 메인 스레드에서 분리하고, 충분히 큰 계산만 병렬화한다. 응답성 개선과 계산 시간 단축은 서로 다른 지표다. TCP는 다음 단계이며, 이번 구현 범위는 확률 계산·UI 수명 관리·검증·측정이다.

변경 전 호출은 RoundScreen/AssistScreen → RoundController → RoundContext → HandOdds.Find였다. 현재 UI는 불변 스냅샷을 요청하고 RoundController가 소유한 단일 HandOddsWorker를 공유한다. 병렬 집계·임시 손패·조합은 분할별 소유다. 확률 계산은 배열/정렬 없는 HandEvaluator.CategoryOf를 사용하며, 실제 손패 확정과 승리 카드 표시는 기존 Evaluate를 유지한다. UnityEngine 미참조만으로 임의의 코드가 스레드 안전하다고 판정하지 않는다. 호출 그래프의 변경 가능한 static 상태도 점검한다.

## 구현 책임과 파일

기존 Poker → Game → UI 의존 방향과 asmdef 없는 구성을 유지한다. 별도 MonoBehaviour나 씬 참조를 추가하지 않고 기존 RoundController에 Unity 수명을 연결했다.

| 위치 | 책임 |
|---|---|
| Poker/HandOdds.cs | 순차 Find와 FindParallel이 같은 종류 전용 판정기를 사용한다. 기존 Evaluate와의 판정 일치를 별도로 테스트한다. UI/Unity/씬을 모름 |
| Game/Flow/HandOddsRequest.cs | 메인에서 검증 후 복사한 손패·남은 덱·선택 자리와 요청 인스턴스/상태 버전. 내부 배열을 외부에 변경 가능하게 노출하지 않음 |
| Game/Flow/HandOddsWorker.cs | 순수 C# 작업 수명. 활성 계산 하나 + 가장 최근 대기 요청 하나. 취소·오류·완료 상태 전달 |
| Game/Flow/RoundController.cs | Unity 수명과 연결. Update에서 완료 확인 후 메인 이벤트 발행, 비활성화 시 취소, 파괴 시 Dispose. 재활성화는 같은 워커를 사용해 이전 작업 종료 전 중첩 실행 방지 |
| UI/RoundScreen.cs, AssistScreen.cs | 요청과 표시만 담당. 계산 중/완료/실패 상태, 지난 선택의 수치 즉시 제거 |
| Tests/Editor/HandOddsTests.cs 및 전용 테스트 | 정답 대조·취소·오래된 결과·요청 제한·씬 수명 검증 |
| Editor/HandOddsBenchmark.cs | 고정 입력으로 순차/워커 순차/워커 병렬 비교, 결과를 Artifacts에 저장 |

서비스 인터페이스·전역 범용 디스패처를 미리 늘리지 않는다. 순차/병렬 계산이 같은 입력·출력 형태를 사용하고, 테스트가 작업 완료 순서를 제어할 최소한의 경계만 둔다.

## 요청과 결과의 흐름

1. 메인 스레드에서 교체 가능 조건을 검사하고 hand/unseen/indices를 **깊이 필요한 만큼 복사**한다. 실제 Deck이나 RoundContext를 워커에 넘기지 않는다. 덱 추첨/난수 상태를 바꾸지 않는다.
2. 같은 손패 버전·남은 덱·선택이면 UI 재갱신만으로 다시 계산하지 않는다. 손패/덱이 변하면 상태 버전을 증가시킨다. 선택이 바뀌면 새 요청 인스턴스로 교체하고 이전 표시를 지운다.
3. 활성 계산이 없으면 Task.Run으로 시작한다. 이미 실행 중이면 취소를 요청하고 대기 요청을 최신 하나로 교체한다. 이전 작업이 종료된 뒤 다음을 시작해 빠른 연타로 계산이 겹쳐 쌓이지 않게 한다.
4. 순차 또는 제한된 Parallel.For로 계산한다. Unity 객체/Debug.Log/Time/TMP에는 접근하지 않는다.
5. Update에서 완료된 Task의 결과·취소·예외를 모두 회수한다. 미완료 Task에 Wait/Result를 호출하지 않는다. 결과는 요청 인스턴스·손패 버전·현재 단계·표시 대상이 일치할 때만 적용한다.
6. 선택 해제, 손패 변경, 후보 공개, 확정, 새 라운드, 모달 닫기, 컴포넌트 비활성화/씬 종료 시 이전 결과를 무효화한다. 취소에 실패해 늦게 도착한 결과도 현재 요청과의 참조 비교로 폐기한다. 종료 후에도 예외는 순수 C# 완료 처리에서 관찰하고 Unity 콜백은 호출하지 않는다.

일반 교체와 선택 교체 확률은 동시에 표시하지 않으므로 활성 표시 대상 하나로 관리한다. 선택 교체의 현재 확률 의미는 남은 덱에서 **한 장을 뽑을 때**의 분포다. 세 후보 중 원하는 족보를 선택할 확률과 혼동하지 않으며 이번 작업에서 의미를 바꾸지 않는다.

## 계산 분할

- 조합의 첫 카드 인덱스별로 분할한다. 각 분할에서 다음 인덱스 이상만 재귀 열거해 중복·누락을 막는다.
- 첫 인덱스별 작업량이 다르므로 고정 등분 대신 작은 분할을 동적으로 배분한다. 조합 하나당 Task를 만들지 않는다.
- 작업별 손패/조합 버퍼와 카테고리 카운터를 사용한다. 각 분할 결과는 자기 슬롯에 기록하고 모든 작업 완료 후 한 번 합산한다. 내부 루프에 공유 Dictionary 갱신이나 매 조합 lock을 넣지 않는다.
- 취소는 분할 시작 및 재귀/일정 조합 단위에서 확인한다. 부분 집계는 정상 결과로 반환하지 않는다.
- 작은 계산은 워커에서 순차 실행한다. 병렬 임계값과 최대 동시 계산 수는 타깃 측정으로 결정한다. 측정은 병렬도 1/2/4를 비교했다. 런타임은 1~2장 워커 순차, 3~4장은 병렬도 최대 2(논리 CPU 하나면 순차)다. 모바일의 모든 코어를 점유하지 않는다.
- CPU 작업은 Task.Run으로 실행하고, 그 안의 Parallel 계산에는 명시적 병렬도 제한을 둔다. 메인에서 Parallel.For를 호출하면 완료까지 막히므로 금지한다.

## 상한과 측정

**우선 상한 3 유지 → 비동기/병렬 구현 검증 → 측정 후 4장 UI 노출 결정** 순서였다. 2026-09-21, k=4까지 재측정한 뒤 이 순서대로 상한을 4로 올렸다(THREADING_RESULTS §"상한 4장 확장"). 포트폴리오 자료(덱·경력기술서·QnA)의 "3자리 상한" 서술은 아직 갱신하지 않았다 — 아래 안내대로 별도로 갱신해야 한다.

47장 기준 C(47,3)=16,215, C(47,4)=178,365, C(47,5)=1,533,939다. 실제 남은 카드 수를 입력으로 삼는다. 입력 카드와 선택 자리 수에 따라 평가 비용도 달라질 수 있다.

- 동일 입력·동일 평가기를 사용해 순차 메인 기준/워커 순차/워커 병렬을 비교한다. 메뉴 벤치마크의 reference-sequential은 기존 Evaluate를 이용한 조합 열거 기준이며 종류 전용 순차/병렬 경로와 함께 측정한다. 속도 개선 전체를 병렬화 성과로 표현하지 않는다.
- 워밍업 후 반복 횟수·기기·CPU·Unity 버전·빌드 백엔드/설정을 기록한다. 중앙값/p95 계산 시간, 요청→표시 지연, 프레임 시간, GC/할당과 취소 반응 시간을 구분한다.
- Editor 수치와 실제 Player/모바일 수치를 분리한다. 모바일에서는 반복 실행 중 발열에 따른 성능 저하도 확인한다.
- 순차보다 느린 영역은 순차 경로를 채택한다. 워커 이관은 메인 정지를 줄일 수 있지만 CPU 경합·GC 때문에 프레임 영향 0을 보장하지 않는다.
- 4장 노출은 정확성·응답성·프레임/메모리 예산 통과 후 별도 결정한다. 채택 시 DESIGN §19, HANDOFF, POLISH와 실제 존재하는 포트폴리오 자료의 상한 설명을 함께 갱신한다.

## 검증과 완료 기준

- 기존 정답 테스트 유지. 여러 손패/남은 덱/자리 입력에서 순차·병렬의 카테고리별 Count/Total/정렬이 완전히 같다. 합계는 nCk와 같다.
- 병렬도 1/2/4, 반복 실행, 입력 불변성, 빈 선택/중복·범위 밖 자리/덱 부족 입력의 기존 또는 명시한 계약 확인.
- 취소 전/도중/완료 직후, 빠른 선택 변경, 예외, 씬 종료에서 오래된 수치·미관찰 예외·지속 작업 누적 없음. 타이밍 의존 Sleep 대신 제어 가능한 완료 신호로 테스트한다.
- 실제 UI에서 계산 중에도 선택/교체/확정 가능하고 오래된 확률은 보이지 않는다. 실제 선택 후보 공개 이후 이전 확률 표시가 돌아오지 않는다.
- 개발 PC 수치만으로 모바일 완료를 선언하지 않는다. 측정 결과가 나오기 전에는 속도 향상 배수나 1ms 처리 시간을 기재하지 않는다.

## 다음 단계: 선택적 TCP 결과 제출

RunJournal은 기존 분석 로그이며 현재 runId/프로토콜 DTO/서버 제출 계약이 없다. 그대로 서버 검증 가능한 데이터라고 가정하지 않는다. 런 종료 시 불변 RunResult DTO를 만들고 로컬 저장 후 전송한다. OnDestroy는 보조 저장 경로일 뿐 강제 종료 시 실행을 보장하지 않는다.

제안 경계: 게임 종료 이벤트 → RunResult → 로컬 durable outbox → 전송 서비스 → C++ TCP 서버. Stand-Alone이 기본이며 네트워크 비활성 시 DNS/연결/재시도를 하지 않는다. 온라인 실패는 게임 결과를 되돌리지 않는다. 서버 ACK 후 outbox를 제거하고, ACK 유실 시 같은 runId 재시도로 멱등 처리한다. 부분 파일 방지, 큐 용량/보존 기간/최대 시도/백오프와 영구 거부 상태를 명시한다.

프로토콜은 버전·메시지 종류·requestId/runId·ruleset을 가진 본문과 네트워크 바이트 순서의 길이 프리픽스다. 송수신 모두 부분 처리를 다루고 프레임 최대 크기·잘못된 길이·타임아웃·재연결을 검증한다. 메모리 중복 맵만으로 끝내지 않고 서버 재시작 후에도 중복 확인과 랭킹 갱신이 일관되게 복구되도록 저장한다.

TCP는 Socket async I/O를 기본 후보로 한다. 네트워크 대기를 위해 항상 전용 스레드가 필요한 것은 아니다. 전용 워커를 택하면 블로킹 I/O를 격리하는 목적과 종료 방법을 문서화한다. 확률 계산 워커와 소켓 수명은 분리하고 메인 전달 원칙만 공유한다.

C++ 서버는 형식·범위·규칙 버전·중복 요청을 검사하고 랭킹을 제공할 수 있다. 그러나 현재 RunJournal은 보드 위치·전 행동·전투 재현 상태를 충분히 기록하지 않으므로 점수의 정당성을 재시뮬레이션해 증명할 수 없다. 초기 버전은 **클라이언트 제출 기록 기반 데모 랭킹**으로 명시한다. 서버 권한 검증은 별도 재현/권위 모델이 필요하다. 계정 없는 환경의 runId 중복 방지는 이용자 신원이나 치팅 방지가 아니다.

실시간 멀티플레이·계정·DB·대규모 동접은 첫 범위에서 제외한다. TCP 및 C++ 서버 구현 착수는 확률 계산 검증 이후 별도 작업으로 진행한다.
