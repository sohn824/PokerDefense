# 멀티스레드 도입 설계 (2026-09-20)

**상태:** 확률 계산의 멀티스레드 처리와 UI 연결을 구현했고, EditMode 225/225가 통과했다. 교체 상한(`HandOdds.MaxSlots`)은 측정을 거쳐 3에서 **4**로 올렸다(2026-09-21, 아래 "상한과 측정" 참조). TCP 결과 제출은 2026-09-27에 구현했다([NETWORK.md](NETWORK.md)). 현재 게임 규칙은 DESIGN §19~20, 측정·검증 기록은 [THREADING_RESULTS.md](THREADING_RESULTS.md)를 따른다.

## 목적과 범위

교체 확률 계산(`HandOdds`)은 조합을 수만~수십만 개 열거하므로 메인 스레드에서 떼어내고, 충분히 큰 계산만 병렬로 돌린다. 손패를 실제로 확정할 때 하는 판정은 한 번뿐이라 기존처럼 동기로 호출한다.

화면이 멈추지 않게 하는 것(응답성)과 계산 자체를 빠르게 하는 것(계산 시간)은 다른 목표이며, 따로 측정한다. 이번 범위는 확률 계산, UI와의 수명 관리, 검증, 측정이다. TCP는 다음 단계다.

**바뀐 호출 흐름.** 이전에는 RoundScreen/AssistScreen → RoundController → RoundContext → `HandOdds.Find`를 그대로 호출했다. 지금은 UI가 복사본으로 만든 요청을 보내고, RoundController가 가진 `HandOddsWorker` 하나가 모든 요청을 처리한다.

**판정 함수를 둘로 나눴다.** 확률 계산은 배열 생성과 정렬이 없는 `HandEvaluator.CategoryOf`(족보 종류만 판정)를 쓴다. 실제 손패 확정과 승리 카드 표시는 기존 `Evaluate`를 그대로 쓴다.

**스레드 안전성은 따로 확인한다.** UnityEngine을 참조하지 않는다고 해서 스레드에서 안전한 것은 아니다. 호출 경로에 값이 바뀌는 static 상태가 있는지도 점검한다.

## 파일별 책임

기존 Poker → Game → UI 의존 방향과 asmdef 없는 구성은 그대로 둔다. 새 MonoBehaviour나 씬 참조는 추가하지 않고, 기존 RoundController에 Unity 수명을 연결했다.

| 위치 | 책임 |
|---|---|
| Poker/HandOdds.cs | 순차 `Find`와 병렬 `FindParallel`. 둘 다 같은 종류 전용 판정을 쓰고, 기존 `Evaluate`와 결과가 같은지는 별도로 테스트한다. UI·Unity·씬을 모른다 |
| Game/Flow/HandOddsRequest.cs | 메인 스레드에서 검증하고 복사한 손패·남은 덱·선택 자리, 그리고 요청을 구분하는 버전. 내부 배열은 밖에서 바꿀 수 없게 공개한다 |
| Game/Flow/HandOddsWorker.cs | 계산 작업의 수명을 관리하는 순수 C# 클래스. 실행 중인 계산 하나와 가장 최근 대기 요청 하나만 둔다. 취소·오류·완료 상태를 전달한다 |
| Game/Flow/RoundController.cs | Unity 수명과 연결한다. `Update`에서 완료를 확인해 메인 스레드에서 이벤트를 보내고, 비활성화되면 취소, 파괴되면 `Dispose`한다. 다시 활성화돼도 같은 워커를 써서 이전 작업과 겹쳐 돌지 않게 한다 |
| UI/RoundScreen.cs, AssistScreen.cs | 요청과 표시만 맡는다. 계산 중·완료·실패 상태를 보여주고, 선택이 바뀌면 이전 수치를 바로 지운다 |
| Tests/Editor/HandOddsTests.cs 외 전용 테스트 | 정답 대조, 취소, 오래된 결과 폐기, 요청 제한, 씬 수명 |
| Editor/HandOddsBenchmark.cs | 같은 입력으로 순차·워커 순차·워커 병렬을 비교하고 결과를 Artifacts에 저장한다 |

서비스 인터페이스나 범용 디스패처는 미리 만들지 않는다. 순차와 병렬 계산이 같은 입력·출력 형태를 쓰게 하고, 테스트가 작업 완료 순서를 조절할 수 있는 최소한의 경계만 둔다.

## 요청에서 결과까지

1. **복사.** 메인 스레드에서 교체할 수 있는 상태인지 확인한 뒤, 손패·남은 덱·선택 자리를 필요한 만큼 복사한다. 실제 `Deck`이나 `RoundContext`는 워커에 넘기지 않고, 덱의 난수 상태도 건드리지 않는다.
2. **중복 요청 무시.** 손패 버전·남은 덱·선택이 모두 같으면 UI가 다시 그려져도 새로 계산하지 않는다. 손패나 덱이 바뀌면 버전을 올린다. 선택이 바뀌면 새 요청으로 교체하고 이전 표시를 지운다.
3. **실행.** 돌고 있는 계산이 없으면 `Task.Run`으로 시작한다. 이미 돌고 있으면 취소를 요청하고, 대기 요청을 가장 최근 것 하나로 바꾼다. 이전 작업이 끝난 뒤에 다음 작업을 시작하므로 빠르게 연타해도 계산이 쌓이지 않는다.
4. **계산.** 순차로 돌리거나, 병렬 수를 제한한 `Parallel.For`로 돌린다. 계산 중에는 Unity 객체, `Debug.Log`, `Time`, TMP에 접근하지 않는다.
5. **회수.** `Update`에서 끝난 작업의 결과·취소·예외를 모두 거둔다. 끝나지 않은 작업에 `Wait`나 `Result`를 부르지 않는다. 결과는 요청 인스턴스·손패 버전·현재 단계·표시 대상이 모두 맞을 때만 화면에 반영한다.
6. **무효화.** 선택 해제, 손패 변경, 후보 공개, 확정, 새 라운드, 창 닫기, 컴포넌트 비활성화, 씬 종료 때 이전 결과를 무효로 만든다. 취소가 늦어 결과가 뒤늦게 도착해도 현재 요청과 참조를 비교해 버린다. 종료 뒤에 난 예외도 순수 C# 쪽에서 거두고, Unity 콜백은 부르지 않는다.

일반 교체와 선택 교체의 확률은 동시에 보여주지 않으므로 표시 대상은 하나만 둔다. 선택 교체의 확률은 남은 덱에서 **한 장을 뽑았을 때**의 분포다. 후보 3장 중 원하는 족보를 고를 확률과는 다르며, 이번 작업에서 이 의미는 바꾸지 않는다.

## 계산을 나누는 방법

- **첫 카드별로 나눈다.** 조합의 첫 카드 인덱스마다 묶음을 만들고, 각 묶음에서는 그 뒤 인덱스만 재귀로 열거한다. 그래서 빠지거나 겹치는 조합이 없다.
- **작게 나눠 동적으로 배분한다.** 첫 카드에 따라 묶음 크기가 다르므로 똑같이 등분하지 않는다. 조합 하나마다 Task를 만들지도 않는다.
- **공유 상태 없이 합친다.** 묶음마다 작업용 손패·조합 배열과 족보별 집계 표를 따로 쓴다. 결과는 각자 자기 칸에 기록하고, 모든 작업이 끝난 뒤 한 번만 합산한다. 안쪽 루프에서 공유 Dictionary를 고치거나 조합마다 lock을 걸지 않는다.
- **중간에 취소를 확인한다.** 묶음 시작과 재귀 중에 취소를 확인한다. 중간까지만 센 집계는 정상 결과로 돌려주지 않는다.
- **작은 계산은 순차로 돌린다.** 병렬을 시작할 기준과 최대 스레드 수는 측정으로 정했다. 병렬 1·2·4를 비교한 결과, 현재는 1~2장은 워커에서 순차, 3~4장은 최대 2스레드 병렬이다(논리 CPU가 하나면 순차). 모바일에서 모든 코어를 차지하지 않기 위해서다.
- **메인 스레드에서 `Parallel.For`를 부르지 않는다.** 끝날 때까지 메인이 멈추기 때문이다. CPU 작업은 `Task.Run` 안에서 돌리고, 그 안의 병렬 계산에는 스레드 수 제한을 둔다.

## 상한과 측정

처음 정한 순서는 **상한 3 유지 → 비동기·병렬 구현 검증 → 측정 후 4장 노출 결정**이었다. 2026-09-21 4장까지 다시 측정한 뒤 이 순서대로 상한을 4로 올렸고(THREADING_RESULTS "상한 4장 확장"), 포트폴리오 자료의 상한 설명도 함께 고쳤다.

47장 기준 조합 수는 C(47,3)=16,215, C(47,4)=178,365, C(47,5)=1,533,939다. 실제로는 그때 남은 카드 수로 계산하며, 어떤 카드와 몇 자리를 골랐는지에 따라 판정 비용도 달라질 수 있다.

- 같은 입력과 같은 판정 함수로 메인 순차·워커 순차·워커 병렬을 비교한다. 벤치마크의 `reference-sequential`은 기존 `Evaluate`로 조합을 열거한 기준값이며, 종류 전용 순차·병렬과 함께 잰다. 전체 속도 개선을 병렬화 효과로만 설명하지 않는다.
- 워밍업 뒤 반복 횟수, 기기, CPU, Unity 버전, 빌드 백엔드와 설정을 기록한다. 계산 시간의 중앙값과 p95, 요청에서 표시까지의 지연, 프레임 시간, GC·할당, 취소 반응 시간을 구분한다.
- 에디터 수치와 실제 Player·모바일 수치를 섞지 않는다. 모바일에서는 오래 돌렸을 때 발열로 느려지는지도 본다.
- 순차보다 느린 구간은 순차를 쓴다. 워커로 옮기면 메인이 멈추는 시간은 줄지만, CPU 경합과 GC 때문에 프레임 영향이 0이 되는 것은 아니다.
- 4장 노출은 정확성·응답성·프레임·메모리 기준을 통과한 뒤 결정한다. 채택하면 DESIGN §19, HANDOFF, POLISH, 포트폴리오 자료의 상한 설명을 함께 고친다.

## 검증과 완료 기준

- 기존 정답 테스트를 유지한다. 여러 손패·덱·자리 입력에서 순차와 병렬의 족보별 개수·전체 수·정렬이 완전히 같아야 한다. 개수 합은 nCk와 같아야 한다.
- 병렬 1·2·4, 반복 실행, 입력이 바뀌지 않는지, 빈 선택·중복·범위 밖 자리·덱 부족 같은 잘못된 입력의 처리를 확인한다.
- 취소 전·도중·완료 직후, 빠른 선택 변경, 예외, 씬 종료에서 오래된 수치가 남거나, 거두지 않은 예외가 있거나, 작업이 계속 쌓이면 안 된다. 타이밍에 기대는 `Sleep` 대신 테스트가 조절할 수 있는 완료 신호를 쓴다.
- 실제 UI에서 계산 중에도 선택·교체·확정을 할 수 있어야 하고, 오래된 확률이 보이면 안 된다. 후보를 공개한 뒤 이전 확률이 다시 나타나서도 안 된다.
- 개발 PC 수치만으로 모바일에서도 괜찮다고 선언하지 않는다. 측정 전에는 속도 향상 배수나 처리 시간을 적지 않는다.

## 다음 단계: TCP 결과 제출 (선택 기능)

> 2026-09-27 구현. 실제 구현과 결정, 검증은 [NETWORK.md](NETWORK.md)가 기준이다. 아래는 구현 전에 정한 설계 방향이다.

**데이터.** 지금 있는 RunJournal은 분석용 로그일 뿐이라 runId, 프로토콜 형식, 서버 제출 규약이 없다. 그대로 서버에서 검증할 수 있는 데이터로 보지 않는다. 런이 끝나면 바뀌지 않는 `RunResult` DTO를 만들어 먼저 로컬에 저장하고 그다음 보낸다. `OnDestroy`는 보조 저장 경로일 뿐이며, 강제 종료 때 실행된다는 보장이 없다.

**흐름.** 게임 종료 이벤트 → `RunResult` → 로컬 outbox(영구 저장 대기열) → 전송 서비스 → C++ TCP 서버.
- 기본은 오프라인 게임이다. 네트워크가 꺼져 있으면 DNS 조회, 연결, 재시도를 하지 않는다. 전송에 실패해도 게임 결과는 그대로다.
- 서버가 ACK를 보내면 outbox에서 지운다. ACK가 유실되면 같은 runId로 다시 보내고, 서버는 같은 runId를 한 번만 처리한다.
- 파일이 쓰다 만 상태로 남지 않게 하고, 대기열 용량, 보존 기간, 최대 재시도 횟수, 재시도 간격, 영구 거부 상태를 정해 둔다.

**프로토콜.** 본문에는 버전, 메시지 종류, requestId/runId, ruleset을 넣고, 앞에 네트워크 바이트 순서의 길이를 붙인다. 보내고 받을 때 모두 데이터가 나눠 도착하는 경우를 처리하고, 최대 크기, 잘못된 길이, 타임아웃, 재연결을 검증한다. 중복 확인을 메모리에만 두지 않고 저장해서, 서버를 다시 켜도 중복 확인과 랭킹이 일관되게 복구되게 한다.

**소켓.** `Socket`의 비동기 I/O를 기본 후보로 둔다. 네트워크를 기다리는 데 항상 전용 스레드가 필요한 것은 아니다. 전용 스레드를 쓴다면 블로킹 I/O를 격리하려는 이유와 종료 방법을 문서에 남긴다. 확률 계산 워커와 소켓의 수명은 따로 관리하고, "결과는 메인 스레드로 넘긴다"는 원칙만 같이 쓴다.

**서버가 보장하지 못하는 것.** C++ 서버는 형식, 값 범위, 규칙 버전, 중복 요청을 검사하고 랭킹을 제공할 수 있다. 하지만 지금 RunJournal은 보드 위치, 모든 행동, 전투를 재현할 상태를 충분히 기록하지 않으므로, 서버가 다시 시뮬레이션해서 점수가 정당한지 증명할 수는 없다. 그래서 첫 버전은 **클라이언트가 제출한 기록을 그대로 믿는 데모 랭킹**이라고 명시한다. 서버가 결과를 판정하려면 별도의 재현 모델이 필요하다. 계정 없이 runId로 중복을 막는 것은 사용자 확인이나 치팅 방지가 아니다.

실시간 멀티플레이, 계정, DB, 대규모 동시 접속은 첫 범위에서 제외한다. TCP와 C++ 서버 구현은 확률 계산 검증을 마친 뒤 별도 작업으로 시작한다.
