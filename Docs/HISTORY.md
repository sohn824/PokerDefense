## 이 문서의 관리 규칙

- **최신 항목이 위로.** 각 항목은 `날짜 — 제목` / 결정과 이유 / 검증 결과 순으로 적는다.
- **레거시 정리:** 이후 작업으로 완전히 대체되어 현재 코드·설계와 무관해진 항목은 **삭제한다.** 그 결정이 왜 뒤집혔는지가 지금도 의미 있으면 최신 항목에 한 줄로 흡수시키고, 아니면 흔적을 남기지 않는다.
- **현재 상태 요약**과 **반복 함정**은 항상 최신이어야 한다. 이력을 읽지 않아도 이 둘만으로 상태를 파악할 수 있어야 한다.
- 설계 내용 자체는 여기에 쓰지 않는다. [DESIGN.md](DESIGN.md)가 유일한 설계 출처다.

## 반복 함정

같은 곳에 두 번 이상 걸렸거나, 걸리면 원인을 찾기 어려운 것들.

| 함정 | 대응 |
|---|---|
| **폰트에 없는 글자** — `♦`(U+2666), `—`(U+2014), `–`(U+2013)이 Maplestory에 없어 두부(□)가 난다 | `◆`, `-`로 대체함. **새 기호를 쓰기 전에 `HasCharacter(c, false, true)`로 확인할 것.** Dynamic 폰트는 문자 테이블이 비어 있어 인자 없는 `HasCharacter`로는 판정이 안 된다 |
| 화면 표기에 `ToString()`을 쓰면 어긋난다 | `Card.ToString()`("4h")·`UnitInstance.ToString()`(★)은 로그·테스트용이다. 화면은 `CardText`·`BoardScreen.Describe()`가 만든다 |
| **에디터가 포커스를 잃으면 플레이어 루프가 거의 멈춘다** | `PlayerSettings.runInBackground = true`로 해결함. MCP로 실시간 동작을 볼 때 필수 |
| `manage_build`로 씬 목록을 바꿔도 디스크에 안 써진다 | `File/Save Project`를 실행해야 `EditorBuildSettings.asset`에 반영된다 |
| TMP 폰트 에셋의 아틀라스·머티리얼이 리로드 때 사라진다 | `CreateFontAsset` 후 **서브에셋으로 추가**해야 한다. TMP 기본 폰트만 바꾸면 기존 컴포넌트는 옛 폰트를 계속 문다 — 씬 전체를 갈아끼워야 함 |
| Input System 전용(`activeInputHandler: 1`)이라 기본 입력 모듈이 터진다 | `EventSystem`에 `InputSystemUIInputModule`을 붙인다 |
| 에디터를 켠 채로 패키지를 제거하면 `Library/ScriptAssemblies`에 고아 DLL이 남아 로드 실패가 쏟아진다 | 수동 삭제 후 리프레시 |
| 컨트롤러를 거치지 않고 `GridBoard`를 직접 바꾸면 화면이 굳는다 | `PlacementController`의 이벤트가 안 나가서다. 검증 스크립트를 짤 때 자주 걸린다 |
| **슬롯 인덱스로 들고 있는 전투 상태는 유닛이 움직이면 어긋난다** | 공격 쿨다운이 그랬다 — 빈 칸으로 옮기면 그 칸의 0을 물려받아 연사가 됐다(10배). 전투 중 배치가 바뀔 수 있으므로 **유닛을 키로** 들어야 한다 |
| **기존 에셋에 `[SerializeField]` 필드를 새로 넣으면 C# 초기값이 아니라 0이 들어간다** | YAML에 그 키가 없으면 Unity는 `default(T)`로 읽는다. 필드를 추가했으면 **기존 에셋에 값을 명시적으로 써 넣어야 한다** (`maxLifeDamagePerWave`가 0이 될 뻔했다). M8에서 유닛 13종에 패턴 필드를 넣으며 **비어 있지 않은지 검사하는 에셋 가드 테스트**를 붙였다. M9의 `perkReward`도 같은 방식으로 웨이브 15개 전부에 써 넣고 5·10만 켜졌는지 검사한다 |
| **`Awake`에서 만든 것을 다른 컴포넌트의 `Awake`가 읽으면 순서에 걸린다** | `StageController.Awake`가 `StageContext`를 만들었는데 `BoardScreen.Awake`가 먼저 돌아 null이었다. 실행 순서는 씬 설정에 달려 있어 코드만 봐서는 안 보인다. **처음 묻는 쪽이 만들게** 바꿨다(지연 생성). 컨트롤러가 들고 있는 상태를 UI가 `Awake`에서 읽는 구조라 또 걸릴 수 있다 |
| **enum 값을 중간에 끼우면 기존 에셋이 조용히 어긋난다** | 에셋은 enum을 정수로 들고 있다. `EnemyType`에 Runner·Tank를 더할 때 뒤에 붙였고(Normal 0 / Swarm 1 / Boss 2 / Runner 3 / Tank 4) 정수 값을 고정하는 테스트를 뒀다 |
| 테스트에서 `Tick(0.05f)`를 N번 돌려도 정확히 N×0.05초가 안 된다 | 부동소수 누적이라 아주 살짝 못 미쳐 **제한시간 판정을 안 지난다.** `TimedOut`을 기대하는 테스트가 `InProgress`로 떨어진다. 한 스텝 더 돌린다 |
| 스크립트로 씬의 `RectTransform`을 옮길 때 `localPosition`을 쓰면 저장이 안 된다 | 직렬화되는 것은 `m_AnchoredPosition`이다. **`anchoredPosition`에 쓰고 `RectTransform`도 `SetDirty`** 해야 한다. `sizeDelta`만 반영되고 위치는 옛 값으로 남는다 |
| **플레이 모드에서 만든 오브젝트는 나가는 순간 사라진다** | 씬을 고칠 때는 `Application.isPlaying`을 먼저 확인할 것. `PerkLabel`을 플레이 중에 만들었다가 통째로 날렸다. `SerializedObject`로 씬을 저장하려 하면 `This cannot be used during play mode`가 난다 |
| **라벨이 넘치는지 rect 폭으로 판단하면 틀린다** | TMP는 기본이 자동 개행이라 넘치면 **밖으로 나가는 게 아니라 두 줄이 되어 아래를 침범한다.** `textBounds`는 개행된 뒤 값이라 항상 rect 안으로 보인다. **`GetPreferredValues`로 재고 `textInfo.lineCount`가 1인지 확인할 것** |
| 에디트 모드에서 뷰 컴포넌트의 `Show()`를 불러 미리보기하면 그대로 씬에 저장된다 | TMP 문자열·색이 직렬화된다. 찍어 본 뒤 **`Show(null)`로 되돌리고 저장**할 것 |
| **성급 배수는 공격력과 공격속도에 동시에 곱해져 DPS가 제곱으로 커진다** | `{1, 2, 4}`를 "★3은 4배"로 읽으면 틀린다. **실제 DPS는 16배다.** M3 검증이 `ATK 28(정확히 2배)`만 확인해 M9까지 안 보였고, 그동안 하이카드 ★3이 로열 스트레이트 플러시 ★1보다 강했다. **배수를 만질 때는 항상 제곱해서 볼 것** |
| **오버킬은 명목 DPS가 아니라 ATK의 절대 크기에 달렸다** | 패턴을 비교하려고 명목 DPS를 낮게(5) 맞추면 ATK가 적 HP보다 훨씬 작아져 **오버킬이 아예 일어나지 않는다.** Rapid↔Heavy 차이가 1.5% 아래로 사라져 "Rapid는 어떤 페널티에서도 가망 없음"이라는 **반대 결론**이 나왔다. 현실 규모(ATK 40 vs 300)로 올리자 잔챙이 웨이브에서 3.9배로 갈렸다. **패턴을 비교할 때는 실제 유닛의 ATK 대역(5~310)에서 잴 것** |
| **전투 성능을 클리어 시간으로 재면 스폰 바닥에 걸린다** | 마지막 스폰 시각보다 빨리 끝날 수 없어(2026-08-09 항목) 강한 보드끼리는 전부 같은 값이 나온다. 제한시간 천장도 있어 약한 쪽은 전부 시간 초과로 뭉갠다. **제한시간 동안의 유효 피해량(스폰된 HP - 잔여 HP, 오버킬 제외)** 으로 재면 바닥과 천장을 둘 다 피한다 |
| 재현 실행이 필요한 검증은 손으로 하면 오래 걸린다 | `Time.timeScale`을 올리고 `EditorApplication.update`에 자동 진행 콜백을 걸면 20웨이브 완주를 손 안 대고 확인할 수 있다. 콜백은 끝날 때 스스로 해제하게 짠다 |

## 이력

### 2026-08-12 — M11 착수: 아트 스펙 확정 + 적 체력 바

`ART_REQUEST.md`의 공통 스펙이 "제안값"으로 남아 있어 먼저 확정했다. 이미지는 아직 한 장도 없다.

- **검증 조건의 "세 곳"이 모호했다.** `PlaceholderColor`를 쓰는 코드는 3곳인데 **그중 둘이 같은 대상(적)** 이고, 카드는 그 필드를 아예 안 쓰는 TMP 텍스트다. **유닛·적·카드 세 대상**으로 확정해 DESIGN §8에 명시했다. 카드를 빼면 화면 아래 절반이 텍스트로 남는다.
- **PPU 256을 못 박았다.** 스펙에 PPU가 없어서 13종을 씬에서 손으로 스케일 맞추게 될 뻔했다. 유닛 1칸 = 1 월드유닛이다.
- **캔버스와 판별 크기를 분리했다.** 실측하니 **유닛은 134px, 적은 73px**로 그려진다(1 월드유닛 = 145.5px). 캔버스 256은 축소 여유일 뿐이고 진짜 조건은 그 크기에서 서로 구분되는가다. 검증 조건이 이름 라벨 제거를 포함하므로 실루엣이 실패하면 13종을 색으로만 구분하게 된다 — **M11 최대 리스크다.**
- **지침에서 두 가지를 걷어냈다.** *좌우 플립*(적이 닫힌 루프를 360도로 도는데 플립으로는 대응이 안 되고 유닛에 회전 코드가 없다)과 *투사체 3종*(§5.5가 즉시 히트로 못 박아 붙일 곳이 없다).
- **성급 오라 오버레이를 만들지 않기로 했다.** 슬롯의 `★` 라벨이 이미 성급을 담당해 §10.4의 *구조는 실루엣, 성급은 별* 두 축이 유지된다. 39장도 오라 1장도 필요 없다.
- **적은 7장 개별로 만든다.** 타입은 5종이지만 에셋이 7개다. 배경·트랙도 범위에 넣었다 — 지금은 **트랙이 아예 안 그려지고** 카메라가 단색으로만 지운다. 총 31장이다.
- **HP 표시를 밝기에서 체력 바로 바꿨다.** `Color.Lerp(full * 0.25f, full, ratio)`는 적이 단색 사각형이라 성립하던 방식이라, 컬러 스프라이트가 들어오면 죽어갈수록 검게 뭉개져 **"죽어간다"가 아니라 "안 보인다"** 가 된다. 적 뷰가 렌더러 하나에서 계층(루트 + 몸통 + 바 2장)으로 바뀌었다. **루트는 스케일 1로 두고 몸통만 0.5로 줄였다** — 그래야 바 수치를 월드 단위 그대로 쓴다. 바도 같은 사각 스프라이트를 늘려 쓰므로 새 에셋이 없다.
- **성한 적은 바를 숨긴다.** 한 웨이브에 최대 68기라 전부 띄우면 화면이 뒤덮인다.
- **검증:** EditMode **205/205**, 콘솔 0건. 실플레이로 바 길이가 HP 비율과 일치하는 것을 확인했다 — 비율 0.667에서 `scaleX 0.333`·`posX -0.083`, 0.833에서 `0.417`·`-0.042`로 계산과 정확히 맞고 왼쪽 끝이 고정된다. 유닛을 전부 팔아 아무도 안 다치게 만든 판에서 **성한 적 9기 → 바 9개 전부 숨김**을 확인했다. 렌더링 캡처로 73px 적 위에서 바가 읽히는 것도 확인했다.

### 2026-08-12 — §7-2 재측정: Rapid는 어디서도 최적이 아니다 (계수 조정은 보류)

DESIGN §7-2가 "성급 배수가 바뀌었으므로 재측정이 먼저다"라고 남겨둔 항목을 쟀다. **코드·데이터는 바뀌지 않았다.**

- **측정 방법을 두 번 갈아엎었다.** 처음엔 M8처럼 클리어 시간으로 쟀는데 **마지막 스폰 시각이 바닥**이라 강한 패턴끼리 전부 같은 값(13.5초)이 나왔다. 제한시간 천장까지 있어 약한 쪽은 시간 초과로 뭉갠다. **제한시간 동안의 유효 피해량(스폰된 HP - 잔여 HP, 오버킬 제외)** 으로 바꿔 닫았다. 둘 다 반복 함정에 적었다.
- **명목 DPS를 낮게 정규화했다가 반대 결론을 낼 뻔했다.** 패턴만 비교하려고 D=5로 맞췄더니 ATK가 적 HP(50~1300)보다 훨씬 작아져 **오버킬이 아예 일어나지 않았고**, Rapid↔Heavy 차이가 1.5% 아래로 사라졌다. 그 상태로는 페널티를 0.25까지 내려도 Rapid가 1위를 못 잡아 "계수로는 못 고친다"가 결론이었다. 현실 규모(D=120, ATK 40 vs 300)로 올리자 **잔챙이 웨이브에서 Rapid가 Heavy를 3.9배로 이겼다.** 성급 배수 함정과 같은 종류다 — 배분만 보고 절대 크기를 안 봤다.
- **증상은 확인됐다.** 실제 웨이브 기준 페널티 0.6에서 Rapid는 10패턴 중 W14 8위 / W17 7위 / W19 9위 / W20 3위다. W5·W10·W11은 단일 유닛이 웨이브를 전멸시켜 포화라 제외했다. 페널티를 0.4까지 내려야 1위가 하나(W20) 생긴다.
- **그런데 계수를 지금 만지지 않기로 했다.** 다중 타격 이득은 **적 밀도에 비례해 커지는데 페널티는 평평하다** — 반경 2.2는 0.3까지 내려도 1위였다. 밀도를 정하는 것은 웨이브 데이터이고 §7-1이 그것을 전면 재작성하기로 했으니 **계수는 웨이브를 확정한 뒤 맞추는 것이 순서다.** 지금 넣으면 Multi·Splash 7종의 실효 화력이 33% 깎여 방금 통과한 M10 검증 밴드가 깨지는데, 얻는 것은 20웨이브 중 하나에서의 1위다.
- **갈린 축이 하나뿐이라는 것도 알아냈다.** Rapid↔Heavy는 건강하다(오버킬 낭비가 §10.1대로 작동한다). 문제는 단일 대상 ↔ 다중 타격 축이고, 진짜 레버는 페널티 계수가 아니라 **스플래시 반경**일 수 있다.
- **검증:** 측정 전용이라 프로덕션 코드는 건드리지 않았다. 합성 `UnitDefinition`·`WaveDefinition`을 리플렉션으로 만들어 `CombatContext`에 직접 물렸다. 슬롯 기하도 재서 기록해 둔다 — **15칸 중 12칸이 트랙까지 1.4이고 가운데 3칸(6·7·8)만 2.4다.**

### 2026-08-12 — M10: 20웨이브 재편 + 밸런싱 1차

M10을 **밸런싱(M10)과 아트(M11)로 나눴다.** 둘은 서로를 막지 않고, §10.4가 구조 숫자를 고정해 밸런싱 결과가 아트 사양을 바꾸지 않는다. 아트가 먼저 들어가면 실행 한 번마다 렌더링 검증이 따라붙는다.

- **웨이브를 15개에서 20개로 늘렸다.** 한 라운드는 짧게 끝나는 편이 좋고 길이는 라운드 수로 만든다는 판단이다. 웨이브 수가 코드에 박힌 곳이 없어(`StageDefinition`의 리스트) 에셋 5개 신설 + `Wave_15`를 최종 보스에서 **세 번째 보스**로 돌리는 것으로 끝났다. **보스 주기를 5로 두면 특전 선택이 3회가 되는데, 특전 6종은 정확히 3회까지만 성립한다** — 4회차에는 남은 3종이 전부 제시돼 고르는 행위가 사라진다. 더 늘리려면 특전이 먼저다.
- **성급 배수가 DPS를 16배로 만들고 있었다.** `{1, 2, 4}`가 공격력과 공격속도에 **동시에** 곱해진다. M3에서 `ATK 28(정확히 2배)`만 확인해 M9까지 안 보였고, 그동안 `하이카드 스카우트 ★3`(DPS 320)이 `로열 스트레이트 플러시 소버린 ★1`(162)보다 강했다 — §10.2가 통째로 뒤집혀 있었다. `{1, 1.6, 2.25}`로 내렸다(DPS ×1 / ×2.56 / ×5.06). 4기를 합쳐 5배면 머지는 여전히 이득이고 칸도 아낀다.
- **§7의 유지 보너스 걱정은 방향이 반대였다.** "좋은 패가 Chip까지 받는다"가 아니라 **교체하면 Chip이 0이 되어 지원 소환이 20회에서 1회로 무너진다**였다. Chip 획득처가 유지 보너스 하나뿐이라 교체가 곧 경제를 끊는 행동이다. 상한 4 → 3, 지원 소환 라운드당 2 → 1회로 파이프라인을 좁혔다.
- **★3 목표를 1~3기에서 4~9기로 고쳤다.** 개수를 정하는 것은 배수도 경제도 아니라 **유입 유닛 수**다 — 20라운드가 포커만으로 20기를 공급하고 손패의 92%가 2종에 몰리니 ★3 하나에 4기인 이상 산술적으로 그만큼 나온다. 지원 소환을 절반으로 줄여도 10 → 9로만 움직였고 소환이 0인 판도 4기였다. 라운드를 20으로 늘리기로 정한 이상 ★3이 느는 것은 결과가 아니라 전제다.
- **웨이브 5 보스는 전용 적을 따로 만들어야 했다.** 그 라운드의 보드는 3기뿐이라 W10·W15와 같은 HP를 쓰면 무조건 실패한다 — 성급 배수를 내린 뒤 더 두드러졌다. `Enemy_MiniBoss`(HP 550)를 신설해 W5에 쓰고 `Enemy_Boss`(1300)는 W10·W15·W20 전용으로 뒀다. 이걸 고치자 특전 3회를 전부 받게 됐다.
- **사거리 2 유닛의 중앙 3칸**을 스카우트·건슬링어 2 → 2.5로 닫았다. 보드 중앙에서 트랙까지가 2.4다.
- **마지막에 막힌 것은 시작 라이프였다.** 15로는 자동 진행이 11을 남기고 끝나 "지지 않는 판"이었는데, **적 HP +40% / 스폰 수 +70% / 제한시간 −25%를 각각 넣어도 11에서 안 움직였다.** 유닛 전력은 머지로 배수 성장하고(4기 → DPS 5배, 20라운드 중첩) 웨이브는 데이터에 덧셈으로 적혀 있어서다 — 웨이브 20에서 보드가 총 HP를 소화하는 데 제한시간의 20%밖에 안 쓴다. 숫자를 더 곱하는 것은 근거 없는 추측이 되므로 **시작 라이프를 12로 내려 닫았다.** Act 3·4 전면 재작성이 제대로 된 해법이지만 아트를 막을 만큼 커서 DESIGN §7에 남겼다.
- **검증:** EditMode **205/205**, 콘솔 0건. 자동 진행 **11회** 실측(교체 0장 / 전부 교체 두 정책). 최종 2회 연속으로 M10 검증 조건 4개를 전부 통과 — 라이프 **9·8**(목표 3~10), ★3 **9·7기**(목표 4~9), ★1·★2 잔존 **4·6칸**(목표 3 이상), 특전 **3회 전부 수령**. 게임 시간 530·462초, 지원 소환 15·10회.
- **자동 진행은 판마다 ±2 흔들린다.** 덱과 특전 선택지가 매 판 새 시드라 한 번만 재고 판단하면 안 된다. 초반 웨이브에서 어떤 유닛이 뜨는지가 그대로 잔여 라이프로 이어진다.

### 2026-08-10 — M9: 딜러 특전 (Dealer Perk)

- **`if`가 흩어질 자리를 먼저 세었다.** 특전 6종이 건드리는 곳은 유지 보너스·확정 보상·지원 소환 비용·웨이브 수입·공격력 다섯이었다. 이 다섯을 **`PerkSet`의 메서드 다섯 개**로 고정하고, 조건은 전부 그 안에만 뒀다. 호출부는 "지금 값이 얼마인가"만 묻고 어떤 특전이 걸렸는지 모른다 — 확장 후보 9종을 붙여도 손댈 곳은 `PerkTable`(수치)과 `PerkSet`(조건) 둘뿐이다.
- **`PerkSet`은 `StageContext`가 소유한다.** 수명이 스테이지와 정확히 같다. `RunStats`를 분리했던 기준(규칙에 관여하지 않는가)을 그대로 적용하면 특전은 **규칙을 바꾸므로** 붙이는 쪽이 맞다.
- **공격력 배수를 `UnitInstance`에 넣지 않았다.** 유닛은 스테이지를 모르는 불변 객체다. 대신 `PerkSet.AttackPowerOf(unit)` 하나를 `CombatContext`와 `BoardScreen`이 함께 부른다 — **전투가 넣는 피해와 상세 블록의 숫자가 어긋나면 §10.3의 "비교하는 곳"이 거짓말이 된다.**
- **특전마다 SO를 만들지 않았다.** 6종이 전부 값 몇 개짜리 행이라 `HandUnitTable`처럼 전역 에셋 1개(`PerkTable`)에 담았다. 수치는 여전히 데이터에 있어 §4를 지키고, 파일은 7개가 아니라 1개다.
- **`amount`/`limit` 두 칸의 뜻이 특전마다 다르다.** `Insurance`의 `limit`은 발동에 필요한 교체 장수고 `Interest`의 `limit`은 이자 상한이다. 효과별로 필드를 나누면 대부분 빈 칸이 되므로 뜻은 `PerkTable` 주석의 표에 적었다.
- **화면 이름은 한글 하나뿐이다.** 뚝심·위로금·흥정·이자·신병 훈련·고참. 직역(인내·보험)보다 그 특전이 시키는 **행동**에 붙였고, 신병 훈련과 고참은 ★1과 ★2 이상을 가르는 짝이라 짝으로 지었다. `PerkId`는 영문 그대로 둔다 — 코드 식별자와 화면 이름을 같게 만들 이유가 없고, **이름이 둘이면 플레이어가 외울 것만 늘어난다**는 §10.3의 기준은 화면 안에서만 적용된다.
- **특전 보상을 `jokerReward`에 얹지 않고 `perkReward` 필드로 나눴다.** 지금은 둘 다 5·10에만 켜져 있어 구분이 없지만, 한쪽만 주는 웨이브가 생겨도 데이터로 끝난다. 최종 보스(15)는 받아도 쓸 라운드가 없어 끄는 편이 맞다.
- **고르기 전에는 다음 라운드를 열지 않는다.** `GameFlowController`가 멈춰 서고 3칸을 내놓는다. 라운드가 먼저 열리면 손패를 보고 특전을 고르게 되거나, 반대로 특전이 그 라운드에 안 붙는다. **루프에 플레이어 입력 지점이 셋째로 늘었다** — 한 판에 두 번뿐이다.
- **선택 화면은 전면 패널이다.** 유닛 상세는 보드를 가리면 안 돼서 문구 자리를 썼지만(2026-08-09), 특전은 웨이브 사이라 보드에 볼 것이 없다. 화면을 덮는 판이 보드 클릭까지 함께 막아 준다 — `BoardScreen`이 UI 위 클릭을 이미 거른다.
- **`Awake` 순서에 걸렸고 지연 생성으로 고쳤다.** `BoardScreen.Awake`가 `StageController.Awake`보다 먼저 돌아 `Stage`가 null이었다. 지원 소환 비용이 특전을 거치면서 드러났다.
- **검증:** EditMode **205/205**(신규 28). 15웨이브를 자동 진행으로 완주 — 웨이브 10 클리어에서 패널이 뜨고, 고른 즉시 지원 소환 표기가 6에서 5로 바뀌고 라운드 11이 열리는 것을 확인. 콘솔 0건. 최악값 확인: 제목 679px, 카드 텍스트 618×80(rect 840×230).
- **고른 특전을 상단 줄에 남긴다.** 라이프·Chip과 같은 "판이 끝날 때까지 유지되는 상태"라 같은 줄이 맞다. **빈 자리는 rect가 아니라 실제로 그려지는 폭으로 재야 했다** — 좌우 라벨 rect는 380px씩이지만 라운드 표기가 150px밖에 안 써서 가운데가 400px 넘게 비어 있었다. 특전은 한 판에 최대 2개라 최악값이 263px이다.
- **자리를 재다가 기존 버그를 찾아 고쳤다.** 조커를 들고 있으면 `라이프 15 Chip 120 조커 2`가 380px rect를 넘겨 **두 줄로 개행되고 둘째 줄이 안내 문구 자리를 침범**했다. M9 이전부터 있었지만 같은 줄에 특전을 넣는 이상 두고 갈 수 없었다. 좌측 끝(x=-520)은 그대로 두고 폭만 500으로 넓혔다.

### 2026-08-09 — 슬롯을 비우고 유닛 상세를 만들다 (+ 이름 통합)

M8이 슬롯에 수치를 밀어 넣으면서 생긴 문제를 정리했다. 이름·성급·공격력·공격속도 네 가지가 145px 칸을 꽉 채워 **M10에 유닛 아트가 들어갈 자리가 없었다.**

- **정보를 두 층으로 갈랐다.** 슬롯은 *알아보는 곳*(아트 + 성급), 상세는 *비교하는 곳*(이름·패턴·공격력·공격속도·DPS·사거리). 슬롯에서 수치를 전부 뺐다.
- **상세는 모달 창이 아니다.** 전투 중에도 배치를 고치므로(§1) 보드를 덮으면 적이 안 보이고 이동·머지 대상 칸도 못 누른다. §9.4의 "보드 탭은 모드를 늘리지 않는다"도 그대로 지켜야 한다.
- **띄울 빈 자리가 없어서 기존 안내 문구를 두 줄 블록으로 승격했다.** 화면을 재보니 보드 아래 띠는 `CombatLabel`(1055~1125)과 `CategoryLabel`(965~1075)이 쓰고, 그 위 1105~1236은 적이 지나가는 트랙 안쪽이다. **새 창을 띄우려면 무언가를 가려야 한다.** 문구 자리를 쓰면 새로 가리는 것이 없다.
- **공격력·공격속도·DPS를 셋 다 띄운다.** 하나로 못 뭉친다 — 패턴마다 배분이 크게 달라(§10.1) DPS만 보면 오버킬 낭비가, 공격력만 보면 발사 주기가 사라진다. M8에서 DPS 하나로 바꿨다가 되돌린 이유다.
- **이름을 정식명 하나로 통합했다.** 슬롯이 이름을 담지 않게 되자 짧은 이름이 필요한 자리가 사라졌다. 유닛 하나에 이름이 둘이면 외울 것만 늘어난다(§0). 6자 제한도 없앴다. `displayName` 필드가 정식명을 들고 있어 **새 필드는 늘지 않았다.**

### 2026-08-09 — 전투 중 배치 변경을 정식 규칙으로

- **검증 중에 크래시를 하나 더 잡았다.** 고른 칸의 유닛이 UI를 거치지 않고 사라지면 `Describe(null)`로 `NullReferenceException`이 쏟아진다. `Refresh`에서 빈 칸을 가리키는 선택을 버리게 했다. 선택은 UI 상태고 보드는 슬롯 탭 말고도 바뀐다.
