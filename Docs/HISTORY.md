# 작업 히스토리

## 이 문서의 관리 규칙

- **최신 항목이 위로.** 각 항목은 `날짜 — 제목` / 결정과 이유 / 검증 결과 순으로 적는다.
- **레거시 정리:** 이후 작업으로 완전히 대체되어 현재 코드·설계와 무관해진 항목은 **삭제한다.** 그 결정이 왜 뒤집혔는지가 지금도 의미 있으면 최신 항목에 한 줄로 흡수시키고, 아니면 흔적을 남기지 않는다.
- **현재 상태 요약**과 **반복 함정**은 항상 최신이어야 한다. 이력을 읽지 않아도 이 둘만으로 상태를 파악할 수 있어야 한다.
- 설계 내용 자체는 여기에 쓰지 않는다. [DESIGN.md](DESIGN.md)가 유일한 설계 출처다.

## 현재 상태 요약

- **진행 단계:** M0~M10 완료. **M11(아트 교체) 진행 중** — **유닛 13종 중 6종 완료**(스카우트·건슬링어·트윈레인저·마크스맨·쿼드캐논·배터리). **구조 숫자가 있는 여섯이 전부 끝났고**, 남은 7종은 구조가 없는 유닛이다. 적·카드·배경은 아직 0장. 검증 조건은 DESIGN §8, 절차와 프롬프트는 [ART_REQUEST.md](ART_REQUEST.md)
- **코드:** `Scripts/Poker/`, `Scripts/Game/`(Flow·Board·Units·Enemies·Data), `Scripts/UI/`, `Scripts/Tests/Editor/`
- **데이터:** 유닛 13종(정식명 `원페어 건슬링어`, **공격 패턴 5종을 나눠 씀**) + `HandUnitTable`, 적 7종(Grunt·Runner·Swarm·Brute·MiniBoss·Boss·FinalBoss = **5타입 전부 사용**. MiniBoss는 W5 전용, Boss는 W10·W15·W20) + **웨이브 20개** + `Stage_1` + `Economy` + `PerkTable`(특전 6종). **수치는 M10에서 조정을 마쳤다**
- **씬:** `Boot.unity`(빌드 0, 카메라만), `Game.unity`(빌드 1). **보드·적은 월드 스페이스, 카드 UI와 HUD만 uGUI**
- **렌더링:** URP 2D. Game 뷰 Portrait 1080x1920, 카메라 직교 크기 6.6, 보드 중심 월드 y=3.4
- **어셈블리:** asmdef 없음. 게임 코드 `Assembly-CSharp`, 테스트 `Assembly-CSharp-Editor`
- **테스트:** EditMode **210/210 통과** (2026-08-14 확인)
- **개발 도구:** Unity 메뉴 `DevMode > 족보 소환` — 플레이 중 교체 단계에서 원하는 족보를 손패에 쥐여 준다. 족보 13종과 유닛 13종이 1:1이라 **원하는 유닛을 즉시 부르는 수단**이다. 게임 코드에는 `#if UNITY_EDITOR`로 감싼 진입점만 있고 카드표·창은 `Assembly-CSharp-Editor`에 있다
- **전투:** 겨냥 대상은 언제나 사거리 내 가장 앞선 적 1기. 패턴은 그 한 발이 **몇 기를 함께 때리는가**만 정한다 — DESIGN §10.1
- **루프:** 20라운드가 자동으로 이어지고 끝나면 결과 화면 → 씬 리로드로 재시작. 플레이어 입력이 필요한 지점은 **확정**, **전투 시작**, 그리고 보스를 잡았을 때의 **특전 선택** 셋
- **특전:** 5·10·15 보스를 클리어하면 3중 택1. 특전이 바꾸는 값은 전부 `PerkSet` 하나에 묻는다 — DESIGN §11.1
- **보드 조작(이동·머지·판매·조커)은 전투 중에도 열려 있다.** 지원 소환만 `Place` 페이즈 전용 — DESIGN §1
- **Chip 경제:** 유지 보너스(교체를 덜 쓸수록 +Chip) / 판매 / 지원 소환 6 Chip(라운드당 1회). 유지 보너스 상한 3
- **스테이지:** 20웨이브, 시작 라이프 12, **웨이브당 라이프 피해 상한 5(보스가 남으면 무조건 상한)**, 보스(5·10·15) 클리어 시 Joker 1개 + 특전 선택, 20은 최종 보스
- **UI는 한글.** 폰트 Maplestory(Light 기본 / Bold 굵기 연결), TMP **Dynamic 아틀라스**
- **슬롯에는 유닛 아트와 성급(★)만.** 아트가 없는 유닛은 플레이스홀더 색 + 이름 라벨로 떨어진다. 수치는 유닛을 고르면 뜨는 상세 블록에서만 나온다 — DESIGN §10.3
- **유닛 아트는 방향별 4장이고 모션은 코드가 낸다** (발사 반동 + 대기 호흡). 조준 방향은 `CombatContext`가 유닛을 키로 기록한다 — DESIGN §10.4
- **무기를 둘 든 유닛은 총구도 둘이다.** `UnitDefinition.muzzleOffsetSecond`가 비어 있으면(0,0) 단발로 떨어진다. **동시에 터질지 번갈아 터질지는 `muzzlesFireTogether`로 받는다** — 무기 수가 아니라 §10.2의 공격 방식이 정하기 때문이다(트윈레인저만 동시). 교대의 홀짝은 `CombatContext.ShotCountOf`가 센다 — DESIGN §10.4
- **총구는 방향별 목록이다 — `muzzlesSide / muzzlesFacing / muzzlesBack`.** 유닛마다 총구 수가 달라(1~5개) 낱개 좌표로는 못 담는다. 좌우만 대칭으로 묶는다. **한 발에 전부 터뜨릴지(`muzzlesFireTogether`), 하나만 순서대로/무작위로 터뜨릴지(`muzzleRandomOrder`)는 데이터로 받는다.** 화염은 반동 배율을 따라간다 — DESIGN §10.4
- **지켜야 할 관례:** 레이어 역방향 `using` 금지, `Poker`에서 `UnityEngine.Random` 금지(재현성), ScriptableObject·MonoBehaviour 금지 — DESIGN §2
- **대기 중인 결정:** DESIGN §7의 4건 — 중반 웨이브 6~17이 위협이 안 됨(Act 3·4 전면 재작성이라 M11 이후) / Rapid가 어디서도 최적이 아님(재측정 완료, 계수 조정은 웨이브 재작성 이후) / 라운드 전환 간격 없음(§1 전이 표를 건드린다) / 상세 블록 둘째 줄이 15px 넘침(M11이 슬롯 레이아웃을 갈아엎으므로 그때 같이). **M11 착수를 막는 것은 없다**

## 반복 함정

같은 곳에 두 번 이상 걸렸거나, 걸리면 원인을 찾기 어려운 것들.

| 함정 | 대응 |
|---|---|
| **폰트에 없는 글자** — `♦`(U+2666), `—`(U+2014), `–`(U+2013)이 Maplestory에 없어 두부(□)가 난다 | `◆`, `-`로 대체함. **새 기호를 쓰기 전에 `HasCharacter(c, false, true)`로 확인할 것.** Dynamic 폰트는 문자 테이블이 비어 있어 인자 없는 `HasCharacter`로는 판정이 안 된다 |
| 화면 표기에 `ToString()`을 쓰면 어긋난다 | `Card.ToString()`("4h")·`UnitInstance.ToString()`(★)은 로그·테스트용이다. 화면은 `CardText`·`BoardScreen.Describe()`가 만든다 |
| **에디터가 포커스를 잃으면 플레이어 루프가 거의 멈춘다** | `PlayerSettings.runInBackground = true`로 해결함. MCP로 실시간 동작을 볼 때 필수 |
| `manage_build`로 씬 목록을 바꿔도 디스크에 안 써진다 | `File/Save Project`를 실행해야 `EditorBuildSettings.asset`에 반영된다 |
| TMP 폰트 에셋의 아틀라스·머티리얼이 리로드 때 사라진다 | `CreateFontAsset` 후 **서브에셋으로 추가**해야 한다. TMP 기본 폰트만 바꾸면 기존 컴포넌트는 옛 폰트를 계속 문다 — 씬 전체를 갈아끼워야 함 |
| Input System 전용(`activeInputHandler: 1`)이라 기본 입력 모듈이 터진다 | `EventSystem`에 `InputSystemUIInputModule`을 붙인다 |
| 에디터를 켠 채로 패키지를 제거하면 `Library/ScriptAssemblies`에 고아 DLL이 남아 로드 실패가 쏟아진다 | 수동 삭제 후 리프레시 |
| 컨트롤러를 거치지 않고 `GridBoard`를 직접 바꾸면 화면이 굳는다 | `PlacementController`의 이벤트가 안 나가서다. 검증 스크립트를 짤 때 자주 걸린다 |
| **슬롯 인덱스로 들고 있는 전투 상태는 유닛이 움직이면 어긋난다** | 공격 쿨다운이 그랬다 — 빈 칸으로 옮기면 그 칸의 0을 물려받아 연사가 됐다(10배). 전투 중 배치가 바뀔 수 있으므로 **유닛을 키로** 들어야 한다 |
| **기존 에셋에 `[SerializeField]` 필드를 새로 넣으면 C# 초기값이 아니라 0이 들어간다** | YAML에 그 키가 없으면 Unity는 `default(T)`로 읽는다. 필드를 추가했으면 **기존 에셋에 값을 명시적으로 써 넣어야 한다** (`maxLifeDamagePerWave`가 0이 될 뻔했다). M8에서 유닛 13종에 패턴 필드를 넣으며 **비어 있지 않은지 검사하는 에셋 가드 테스트**를 붙였다. M9의 `perkReward`도 같은 방식으로 웨이브 15개 전부에 써 넣고 5·10만 켜졌는지 검사한다 |
| **`Awake`에서 만든 것을 다른 컴포넌트의 `Awake`가 읽으면 순서에 걸린다** | `StageController.Awake`가 `StageContext`를 만들었는데 `BoardScreen.Awake`가 먼저 돌아 null이었다. 실행 순서는 씬 설정에 달려 있어 코드만 봐서는 안 보인다. **처음 묻는 쪽이 만들게** 바꿨다(지연 생성). 컨트롤러가 들고 있는 상태를 UI가 `Awake`에서 읽는 구조라 또 걸릴 수 있다 |
| **enum 값을 중간에 끼우면 기존 에셋이 조용히 어긋난다** | 에셋은 enum을 정수로 들고 있다. `EnemyType`에 Runner·Tank를 더할 때 뒤에 붙였고(Normal 0 / Swarm 1 / Boss 2 / Runner 3 / Tank 4) 정수 값을 고정하는 테스트를 뒀다 |
| 테스트에서 `Tick(0.05f)`를 N번 돌려도 정확히 N×0.05초가 안 된다 | 부동소수 누적이라 아주 살짝 못 미쳐 **제한시간 판정을 안 지난다.** `TimedOut`을 기대하는 테스트가 `InProgress`로 떨어진다. 한 스텝 더 돌린다 |
| 스크립트로 씬의 `RectTransform`을 옮길 때 `localPosition`을 쓰면 저장이 안 된다 | 직렬화되는 것은 `m_AnchoredPosition`이다. **`anchoredPosition`에 쓰고 `RectTransform`도 `SetDirty`** 해야 한다. `sizeDelta`만 반영되고 위치는 옛 값으로 남는다 |
| **"콘솔에 오류가 없다"가 "컴파일이 됐다"는 뜻이 아니다** | `refresh_unity`가 파일 변경을 감지 못 하면 **컴파일 자체가 안 돈다**(`refresh_triggered: false`). 그러면 콘솔은 계속 깨끗하고, MCP `execute_code`는 **옛 어셈블리**를 보며, 테스트도 옛 코드로 210/210을 낸다 — 30분을 도메인 리로드 문제로 오진했다. **`Library/ScriptAssemblies/Assembly-CSharp.dll`의 수정 시각을 소스와 비교할 것.** 안 돌았으면 `AssetDatabase.ImportAsset(path, ForceUpdate)` + `CompilationPipeline.RequestScriptCompilation()`으로 강제한다 |
| **플레이 모드에서는 에셋 갱신·저장이 막힌다** | `refresh_unity`가 30초 타임아웃으로 죽는다. **에디터 상태의 `is_playing`을 먼저 볼 것** — 그대로 밀어붙이면 아래 함정으로 이어진다. 플레이 중에는 Unity를 안 건드리는 작업(분할·측정·검산)을 먼저 하고 기다리면 된다 |
| **플레이 모드에서 만든 오브젝트는 나가는 순간 사라진다** | 씬을 고칠 때는 `Application.isPlaying`을 먼저 확인할 것. `PerkLabel`을 플레이 중에 만들었다가 통째로 날렸다. `SerializedObject`로 씬을 저장하려 하면 `This cannot be used during play mode`가 난다 |
| **라벨이 넘치는지 rect 폭으로 판단하면 틀린다** | TMP는 기본이 자동 개행이라 넘치면 **밖으로 나가는 게 아니라 두 줄이 되어 아래를 침범한다.** `textBounds`는 개행된 뒤 값이라 항상 rect 안으로 보인다. **`GetPreferredValues`로 재고 `textInfo.lineCount`가 1인지 확인할 것** |
| 에디트 모드에서 뷰 컴포넌트의 `Show()`를 불러 미리보기하면 그대로 씬에 저장된다 | TMP 문자열·색이 직렬화된다. 찍어 본 뒤 **`Show(null)`로 되돌리고 저장**할 것 |
| **성급 배수는 공격력과 공격속도에 동시에 곱해져 DPS가 제곱으로 커진다** | `{1, 2, 4}`를 "★3은 4배"로 읽으면 틀린다. **실제 DPS는 16배다.** M3 검증이 `ATK 28(정확히 2배)`만 확인해 M9까지 안 보였고, 그동안 하이카드 ★3이 로열 스트레이트 플러시 ★1보다 강했다. **배수를 만질 때는 항상 제곱해서 볼 것** |
| **스프라이트로 전환하기 전에 텍스처 높이를 읽으면 NPOT 값이 나온다** | 407×749 PNG인데 `tex.height`가 **512**를 준다 — 기본 `npotScale`이 가장 가까운 2의 거듭제곱으로 눌러 놓기 때문이다. 그 값으로 PPU를 잡으면 스프라이트 크기가 통째로 어긋난다. **`textureType = Sprite`와 `npotScale = None`을 먼저 걸고 리임포트한 뒤 다시 읽을 것** |
| **4방향 시트를 캔버스 정중앙으로 자르면 안 된다** | 건슬링어 시트는 위 칸 부츠가 622행에서 끝나고 아래 칸 머리가 623행에서 시작해 **간격이 0이었다.** 정중앙(627)에서 자르면 아래 칸 머리끝 4행이 위 칸에 딸려 들어가고, 트림 bbox가 그 얼룩까지 잡아 **바닥 정렬이 발끝이 아니라 얼룩 기준으로 잡힌다.** 생성기가 세로로 빡빡하게 채우므로 **자르기 전에 실제 분리 행을 찾을 것.** 세로 중앙선만 세면 못 잡는다 — **가로 중앙선 통과 픽셀도 함께 셀 것** |
| **4방향 시트는 좌우가 뒤바뀌어 나올 수 있다** | 프롬프트에 `BOTTOM-LEFT = LEFT`라고 박아도 마크스맨은 반대로 나왔다. 그대로 넣으면 **오른쪽 적을 쏠 때 왼쪽을 겨눈 그림**이 나오는데, 화면으로는 "좀 이상한데" 정도로만 보여 못 찾는다. **자르기 전에 무기 띠의 x 중심과 다리의 x 중심을 비교해 판정할 것.** 뒤바뀌었으면 다시 뽑지 말고 엇갈려 배정하면 된다 |
| **화면에 고정된 좌표는 반동을 안 따라간다** | 아트는 발끝을 피벗으로 커지는데 총구 화염 좌표는 슬롯 로컬 고정이라 어긋난다. 하필 **화염이 보이는 0.06초가 반동이 가장 큰 구간**이라 늘 어긋난 상태로만 보이고, 그 사이 간격까지 변해 "위치가 안 맞는다"로 보인다(마크스맨 7.6px). **아트에 스케일을 걸면 거기 붙는 것들도 같은 배율을 받아야 한다** |
| **총구가 몸 중앙에 있다고 가정하면 안 된다** | 정면·후면을 `x=0`으로 두면 **어깨에 멘 총**에서 크게 어긋난다 — 마크스맨 21.6px(뒤통수에 화염), 스카우트 23px. 스카우트는 **세 시트를 넘기는 동안 아무도 못 봤다.** 방향마다 실제로 재서 넣을 것 |
| **`spriteAlignment`는 `TextureImporter`에 없다** | `TextureImporterSettings`에 있다. MCP `manage_asset`으로 넘기면 **성공을 반환하고 조용히 무시**되어 피벗이 Center로 남는다(유닛이 슬롯에서 위로 뜬다). `ReadTextureSettings` → 수정 → `SetTextureSettings` → `SaveAndReimport`로 걸고, **메타를 되읽어 `alignment: 7`을 확인할 것** |
| **오버킬은 명목 DPS가 아니라 ATK의 절대 크기에 달렸다** | 패턴을 비교하려고 명목 DPS를 낮게(5) 맞추면 ATK가 적 HP보다 훨씬 작아져 **오버킬이 아예 일어나지 않는다.** Rapid↔Heavy 차이가 1.5% 아래로 사라져 "Rapid는 어떤 페널티에서도 가망 없음"이라는 **반대 결론**이 나왔다. 현실 규모(ATK 40 vs 300)로 올리자 잔챙이 웨이브에서 3.9배로 갈렸다. **패턴을 비교할 때는 실제 유닛의 ATK 대역(5~310)에서 잴 것** |
| **전투 성능을 클리어 시간으로 재면 스폰 바닥에 걸린다** | 마지막 스폰 시각보다 빨리 끝날 수 없어(2026-08-09 항목) 강한 보드끼리는 전부 같은 값이 나온다. 제한시간 천장도 있어 약한 쪽은 전부 시간 초과로 뭉갠다. **제한시간 동안의 유효 피해량(스폰된 HP - 잔여 HP, 오버킬 제외)** 으로 재면 바닥과 천장을 둘 다 피한다 |
| 재현 실행이 필요한 검증은 손으로 하면 오래 걸린다 | `Time.timeScale`을 올리고 `EditorApplication.update`에 자동 진행 콜백을 걸면 20웨이브 완주를 손 안 대고 확인할 수 있다. 콜백은 끝날 때 스스로 해제하게 짠다 |

## 이력

### 2026-08-16 — M11: 배터리(6종째) + 총구를 방향별 목록으로

`3+2`는 제약이 가장 많았다 — 마크스맨의 `3`(삼각), 쿼드캐논의 `4`(사각), 트윈레인저의 `2+2`(같은 크기 두 덩어리)를 전부 피해야 했다.

- **`3+2`를 `2+2`와 가르는 것은 개수가 아니라 비대칭이다.** 두 덩어리가 같은 크기면 세지 않는 한 `2+2`로 읽힌다. 주포를 굵고 길게, 보조포를 가늘고 짧게 잡고 몸통으로 갈랐다. 위쪽은 **가로 일렬**이라 삼각·사각과도 안 겹친다.
- **한 번 폐기하고 다시 뽑았다.** 첫 시트는 위쪽 3문 중 **가운데가 머리에 완전히 가려** 정면에서 `2+2`로 보였다. 개수는 맞았으므로 개수를 더 강조해도 소용없고 **가림 자체를 금지해야** 했다 — `sits ENTIRELY ABOVE HIS HEAD`를 넣고 같은 내용을 세 곳에 반복했다.
- **하의 색을 안 적으면 군단 기본값인 흰 바지가 나온다.** 첫 시트가 **스카우트와 하체 색 블록이 똑같아** "개성이 없다"는 지적을 받았다. 원인은 프롬프트에서 바지 색을 빠뜨린 것이었고, `===` 블록으로 승격 + `does NOT wear white trousers` 명시로 닫혔다. **한 줄로는 무시되고 문단으로 빼야 먹힌다**는 것이 세 번째 확인이다.
- **총구 좌표를 목록으로 바꿨다.** 배터리는 주포 3문이 머리 위, 보조포 2문이 허리라 **정면·후면에서 x가 둘 다 0**이다. 좌우 반전으로 두 번째를 만들던 규칙에서는 **두 점이 한 자리로 붕괴한다**(51px 어긋남). 낱개 좌표로 버티다 세 번째 한계였고, `muzzlesSide / muzzlesFacing / muzzlesBack` 배열로 정리했다 — 1개든 5개든 그대로 담긴다.
- **발사 방식도 데이터로 받는다.** 동시(`muzzlesFireTogether`) / 순서대로 / 무작위(`muzzleRandomOrder`). 배터리는 총구가 다섯이라 순서대로 돌면 규칙적으로 보여 **무작위**로 했다. 무작위값은 **`CombatContext`가 센 발사 횟수를 해시로 흩어** 만든다 — 뷰가 프레임마다 뽑으면 화염이 0.06초 동안 떨린다.
- **렌더러를 개수 가변 풀로 바꿨다.** 단일 복제로는 동시 발사 총구 수를 못 따라간다. 여전히 **처음 쓸 때** 만들어 `Awake` 순서 함정을 피한다.
- **기관총 연사로 바꿨다.** ATK 68.0 → 22.0, APS 0.80 → 2.50(1250ms → 400ms), **DPS 54.4 → 55.0으로 유지**. 천장은 3.00 — 백스트레이트 에이스의 `초고속 연사` 자리다.
- **"총구 간격이 화염보다 작으니 정확한 5좌표는 값어치가 없다"는 내 판단이 틀렸다.** 화염끼리 겹치는 것과 **위치가 이동하는 것이 보이는 것**은 다른 문제다. 위쪽 3문은 46px에 걸쳐 있어 124px 유닛에서 3분의 1 넘게 움직인다 — 명백히 보인다.
- **검증:** EditMode **210/210**, 콘솔 0건. 두 중앙선 통과 0 / 클리핑 0. 네 방향 5개 총구 위치를 각각 격자로 재서 넣고, 화염이 전부 제 포신에 붙는 것을 그림으로 검산했다. 높이 편차 4.3%는 **포대가 정면에서만 머리 위로 올라가기 때문**이고, 발끝 정렬 격자로 몸 크기가 네 방향 같은 것을 확인했다.

### 2026-08-16 — M11: 쿼드캐논(5종째)

`4`는 **가를 상대가 둘**이었다 — 마크스맨(`3`)과는 둘 다 한 덩어리라 형태로, 트윈레인저(`2+2`)와는 총열 수가 같아 간격으로 갈라야 했다.

- **삼각 ↔ 사각, 그리고 "붙어 있음 ↔ 갈라짐".** 총구를 2×2 정사각으로 **네 개가 맞닿게** 하고 윗변을 평평하게 잡았다. 트윈레인저 프롬프트의 `wide empty gap`을 정확히 뒤집어 `NO gap, NO division running through the middle`로 못 박은 것이 갈림선이었다.
- **자세로도 갈랐다.** 마크스맨은 어깨 견착(무기가 높다), 쿼드캐논은 **허리 받침(낮다)**. 측면에서 무기 높이가 달라 실루엣이 겹치지 않는다.
- **몸통이 어두운 첫 유닛이다.** 붉은 군복 *위에* 검은 판금을 덮었다. 스카우트와 머리색(검정)이 겹쳐 걱정했는데, **명암 분포가 정반대**(스카우트는 아래가 흰 바지, 쿼드캐논은 위아래 다 어두움)라 124px에서 문제가 없었다. **머리색이 겹쳐도 값 분포가 다르면 갈린다.**
- **방향별 3좌표가 여기서 값을 했다.** 쿼드캐논은 지금까지 중 가장 극단적이다 — 포를 허리에 낮게 끼어 **정면 y가 −0.03으로 유일하게 음수**이고(앞선 넷은 +0.21~0.29), 정면 x(−0.15)와 후면 x(+0.19)의 **부호가 뒤집힌다**(같은 쪽 옆구리를 반대편에서 본 것). 좌표 하나로 덮던 옛 모델이었으면 정면이 **24px** 어긋났다 — 스카우트 후면(23px)과 같은 급이다.
- **의심했다가 아닌 것으로 판명된 것 둘.** 뷰어에서 어두운 그라데이션 배경이 보였는데 알파는 전부 0이었다(투명 영역에 RGB가 남은 것뿐). **완전 불투명 픽셀이 0개**인 것도 결함으로 의심했으나, **스카우트 원본이 똑같이 최대 254**이고 이미 정상 동작 중이었다 — 1024×1536 시트의 생성 규격이다. 둘 다 §8에 적었다.
- **좌향 칸이 세로 중앙선에 딱 붙었다(여백 0.0%).** 잘린 줄 알았으나 열 프로파일이 점점 좁아지다 끝나 **포니테일 끝이 자연스럽게 뾰족해진 것**이었다. 1px 차이로 안 넘었다. 폭이 유지되다 끊기면 잘린 것이고, 좁아지다 끝나면 아니다.
- **플레이 모드에 걸려 순서를 바꿨다.** `refresh_unity`가 타임아웃돼 보니 에디터가 플레이 중이었다. 그대로 밀면 저장이 막히므로 **Unity를 안 건드리는 작업(분할·측정·검산)을 먼저** 끝내고 종료를 기다렸다. 반복 함정에 적었다.
- **검증:** EditMode **210/210**, 콘솔 0건. 두 중앙선 통과 0 / 클리핑 0, 네 장 높이 752·748·749·744(편차 1.1%). §7-4 방향 확인 통과(마크스맨과 달리 안 바뀜). 정면·측면 모두 총구 4개를 확대해 셌고, 네 방향 화염이 포신에 붙는 것을 그림으로 검산했다.

### 2026-08-15 — M11: 마크스맨(4종째) + 총구 좌표를 방향별로 가르다

`3`을 쿼드캐논의 `4`와 가르는 것이 목표였는데, **넣고 나서 화염 위치가 셋이나 틀린 것이 드러났다.**

- **한 덩어리끼리는 삼각과 사각으로 가른다.** 건슬링어·트윈레인저는 "덩어리 둘"이라 간격으로 갈렸지만, 마크스맨(`3`)과 쿼드캐논(`4`)은 둘 다 덩어리가 하나다. **양손으로 든 긴 총 하나**에 총열을 삼각(위 1 / 아래 2)으로 배치해 사각 블록과 정면에서 갈리게 했다.
- **삼각은 옆에서 겹친다.** 총열 길이를 계단식으로 어긋나게 해 측면에서도 3이 유지되게 했다. 트윈레인저의 상하 엇갈림과 같은 해법이다.
- **체격과 명암을 스카우트와 정반대로 잡았다.** 같은 남성·같은 군복이라 이것 말고는 갈릴 축이 없었다 — 스카우트가 *가장 작고 가벼운* + 검은 머리 + 흰 바지라면, 마크스맨은 가장 크고 단단한 + 은발 + 짙은 바지다.
- **처음으로 종횡비가 판별에 기여했다.** 정면 0.392(가장 좁음) / 측면 0.914(가장 넓음)로 격차가 2.3배다. 앞선 두 시트에서는 종횡비가 무의미했는데 긴 총 하나가 그 축을 만들었다.
- **측면 두 칸이 뒤바뀌어 나왔다.** 프롬프트에 박아도 안 지켜진다. 다시 뽑지 않고 자를 때 엇갈려 배정했다. **§7에 방향 확인 단계가 없어서 못 잡을 뻔했다** — 세 시트가 우연히 맞았을 뿐이다.
- **화염 위치가 세 가지 이유로 틀려 있었다.**
  1. **반동 미동조** — 아트는 발끝 피벗으로 6% 커지는데 화염 좌표는 고정이라 7.6px 어긋난다. 하필 **화염이 보이는 0.06초가 반동이 가장 큰 구간**이라 늘 어긋난 상태로만 보였다. 전 유닛·전 방향 문제였고 마크스맨이 2초에 한 발이라 비로소 눈에 띄었다.
  2. **후면 `x=0` 고정** — 총을 어깨에 메서 총구가 왼쪽 어깨 위에 있는데 등 한가운데에 찍혔다(21.6px). 찾는 김에 재보니 **스카우트가 23px로 더 심했다.**
  3. **정면 y 공유** — 정면에서는 총을 가슴 높이로 내려 겨누는데 측면(어깨 높이)과 y를 공유했다(마크스맨 12.2px, 스카우트 8.8px).
- **좌표를 하나에서 셋으로 늘렸다 — 측면 / 정면 / 후면.** 넷으로 쪼개지 않은 것은 **좌우 실측 차가 1.7~3.6px**이라 나눌 값어치가 없어서다. 비우면 예전 규칙으로 떨어지게 해 아트가 없는 9종은 건드리지 않았다.
- **검증 방법을 바꿨다.** 화염은 0.06초라 눈으로는 못 본다. **코드와 같은 식으로 계산한 점을 반동이 최대인 순간의 아트 위에 찍어** 총구에 붙는지 그림으로 확인했다. §7에 단계로 넣었다.
- **검증:** EditMode **210/210**, 콘솔 0건. 시트는 알파 78% 투명 / 두 중앙선 통과 0 / 클리핑 0, 네 장 높이 609·609·615·604(편차 1.8%). 네 칸 모두 총열 3개를 눈으로 셌고, 정면 삼각과 측면 계단식이 유지되는 것을 확대해 확인했다. 마크스맨·스카우트 네 방향 전부 화염이 총구에 붙는 것을 그림으로 검산했다.

### 2026-08-15 — M11: 트윈레인저(3종째) + 총구 동시 발사

`2+2`가 M11 최대 난제였다 — **4로 뭉치면 쿼드캐논이고 덩어리가 하나면 건슬링어다.**

- **2+2는 개수가 아니라 "두 덩어리 사이의 간격"으로 읽힌다.** 쿼드캐논은 한 덩어리에 4문, 트윈레인저는 떨어진 두 덩어리에 각각 2문으로 갈랐다. 팔마다 총열이 **V자로 벌어지게** 해서 두께가 아니라 형태로 건슬링어와 구분했고, 브레이서를 흰·금으로 밝게 잡아 사이의 붉은 몸통이 간격으로 읽히게 했다.
- **손에 들지 않고 팔에 붙였다.** 건슬링어와 같은 "손에 든 총" 형식이면 총열 수로만 갈려야 하는데 124px에서 그게 안 읽힌다. 장착 무기로 가면 팔 실루엣 자체가 달라진다.
- **시트가 셋 중 가장 깨끗했다.** 세로·가로 중앙선 통과가 **둘 다 0**이라 건슬링어와 달리 분할선 보정이 필요 없었다. **이 검사는 시트마다 다르다** — 상수가 아니다.
- **총구 화염을 동시 발사로 갈랐다.** 트윈레인저는 §10.2대로 **적 둘에게 각각 한 쌍씩** 쏘므로 교대로 터지면 Pair + Pair가 사라진다. 그런데 **무기가 둘이라고 다 동시는 아니다** — 같은 §10.2가 배터리를 *주포 3문 → 보조포 2문 순으로*라고 못 박았다. 패턴으로 유추하면 셋 중 하나에서 반드시 깨져서 `muzzlesFireTogether`로 데이터에 받았다.

### 2026-08-12 — §7-2 재측정: Rapid는 어디서도 최적이 아니다 (계수 조정은 보류)

DESIGN §7-2가 "성급 배수가 바뀌었으므로 재측정이 먼저다"라고 남겨둔 항목을 쟀다. **코드·데이터는 바뀌지 않았다.**

### 2026-08-10 — M9: 딜러 특전 (Dealer Perk)

- **`if`가 흩어질 자리를 먼저 세었다.** 특전 6종이 건드리는 곳은 유지 보너스·확정 보상·지원 소환 비용·웨이브 수입·공격력 다섯이었다. 이 다섯을 **`PerkSet`의 메서드 다섯 개**로 고정하고, 조건은 전부 그 안에만 뒀다. 호출부는 "지금 값이 얼마인가"만 묻고 어떤 특전이 걸렸는지 모른다 — 확장 후보 9종을 붙여도 손댈 곳은 `PerkTable`(수치)과 `PerkSet`(조건) 둘뿐이다.
- **`PerkSet`은 `StageContext`가 소유한다.** 수명이 스테이지와 정확히 같다. `RunStats`를 분리했던 기준(규칙에 관여하지 않는가)을 그대로 적용하면 특전은 **규칙을 바꾸므로** 붙이는 쪽이 맞다.
- **공격력 배수를 `UnitInstance`에 넣지 않았다.** 유닛은 스테이지를 모르는 불변 객체다. 대신 `PerkSet.AttackPowerOf(unit)` 하나를 `CombatContext`와 `BoardScreen`이 함께 부른다 — **전투가 넣는 피해와 상세 블록의 숫자가 어긋나면 §10.3의 "비교하는 곳"이 거짓말이 된다.**

### 2026-08-09 — 전투 중 배치 변경을 정식 규칙으로

- **`UnresolvedEnemies`는 아직 안 나온 적까지 포함한다.** 제한시간이 스폰보다 먼저 끝나면 안 나온 적도 라이프를 깎아야 한다.
- **만들지 않은 것:** 타겟팅 enum(1종 고정), 투사체(즉시 히트), 처치 보상, `TargetRegistry` 클래스.
- **검증:** EditMode 115/115(테스트 28개 추가). 실플레이 — 웨이브 1은 12.81초에 클리어(라이프 유지), 보드를 비운 웨이브 2는 시간 초과로 **라이프 20 → 8**(잔여 12만큼). 콘솔 0건.

### 2026-08-08 — M3: 그리드 + 배치 + 머지

- **`GridBoard`(순수 C#)가 15슬롯 점유와 배치·머지 규칙을 소유한다.** 거부 시 **보드를 건드리지 않는다.** `UnitInstance`는 불변이라 머지는 승급된 새 인스턴스를 만든다.
- **설계 구멍 발견: 그대로 뒀으면 ★3에 영원히 도달할 수 없었다.** 머지가 "소환 유닛을 놓을 때"만 일어나면 소환 유닛은 항상 ★1이라 ★2에 못 얹고, 보드 위 ★2 둘을 합칠 방법이 없다.
  - 처음 쓴 테스트 `board.TryPlace(0, board[1])`는 통과했지만 **UI에 그런 경로가 없었다.** 테스트가 실제 사용을 반영하지 못한 사례이고, 그 호출은 재료 슬롯을 비우지도 않아 유닛이 복제됐다.
  - `TryMergeSlots(from, to)` 추가. UI는 2탭 방식.
- **DESIGN과 달라진 것:** `GridSlot`·`MergeResolver` 클래스를 만들지 않았다. 슬롯은 `UnitInstance[]`면 충분하고 머지는 배치의 일부다. 문서를 실제에 맞게 고쳤다.
- **성급 배수는 사거리에 곱하지 않는다.** 사거리까지 늘면 배치 위치를 고르는 의미가 줄어든다.
- **저등급 편중 실측: 스카우트 4기를 모으는 데 13라운드.** ★3 하나에 같은 유닛 4기가 필요하므로 이 속도로는 머지가 돌아가지 않는다.

### 2026-08-07 — M2: 카드 UI + 드로우/교체 플로우
